# 案例模板（Case Template）

> 适用：AI 辅助问题定位定界系统 · 知识库 · 案例条目
> 版本：v1.0 ｜ 配套文档：`rule-template.md`（规则模板）
> 设计原则：**案例负责"想到"，规则负责"判定"。** 案例只可排序、不可判定；命中案例只产生假设与线索，必须经验证才能进入结论。

## 一、案例是什么

案例 = 一次（或一类）具体问题的完整记录：**过程 + 答案**。

| | 案例 | 规则 |
|---|---|---|
| 声称 | 个案性（"这种情况出现过 X"） | 普遍性（"只要 A、B、C，就是 X"） |
| 判定性质 | 只能排序（相似度） | 可判定（命中 / 不命中 / 待定） |
| 失效方式 | **自明**（带时间戳，天然只是"历史"，不会误导） | **静默**（版本变了悄悄不命中或误命中） |
| 价值重心 | **排查过程比结论保值**（结论会过期，过程不会） | 结论与判据 |
| 使用依赖 | 必须由 Agent / 人解读 | 可独立执行 |

两条使用纪律：

1. **案例命中后必须验证**：案例结论不得直接写进定位报告，只能作为候选假设与采集线索。
2. **未定位的问题也可以入库**（如实记录 + 缺口标注）——它是未来归纳的原料，但**不得作为规则来源**。

## 三、字段详解

### 3.1 frontmatter：检索键与治理元数据

**frontmatter 就是检索画像。** 与规则模板使用同一套字段约定，保证"检索画像"能同时喂给两条通道：

| 检索画像维度 | 对应字段 |
|---|---|
| 问题分类分级 | `domain`、`component` |
| 问题特征 | `tags` |
| 语义匹配 | `title`、`aliases`、`tags` |

**字段逐项说明：**

| 字段 | 必填 | 格式 / 取值 | 说明 | 使用注意 |
|---|---|---|---|---|
| `id` | ✅ | `CASE-<域>-<序号>`，如 `CASE-SCHED-004` | 全局唯一标识 | 一经分配不再修改；报告与规则会引用它 |
| `title` | ✅ | 一句话 | 案例名 | 以现象为主；已知根因时可写成复合式（如"连接池配置下调导致下单超时"），让根因与现象两侧的关键词都能命中 |
| `type` | ✅ | `pattern` / `instance` | 案例类型 | `instance` = 单次原始记录（素材）；`pattern` = 同类归纳（从多条 instance 归并，`occurrence_count ≥ 2`） |
| `status` | ✅ | `draft` / `active` / `deprecated` | 生命周期 | `draft` 仅作线索参考；有验证结果才能升 `active`；被推翻标 `deprecated` 并注明原因 |
| `confidence` | ✅ | `high` / `medium` / `low` | 可信度 | 与验证程度挂钩：有验证结果 → `high`；仅根因明确 → `medium`；未定位 → `low`。不要人为拔高 |
| `occurrence_count` | ✅ | 整数 | 该类问题的出现次数 | `instance` 固定为 1；`pattern ≥ 2`；用于检索排序（高频问题优先参考） |
| `domain` | ✅ | 数组 | 业务域 / 特性 | 与规则模板同一套受控词表；检索硬键、第一道过滤 |
| `component` | ✅ | 数组 | 模块 / 文件 / 接口 | 尽量与代码仓结构对齐；Agent 靠它跳进代码；跨模块用约定值（如 `跨模块`） |
| `tags` | ✅ | 数组，受控词表 | 问题特征 | 与规则模板同一词表：**定性**（必现 / 偶现 / 特定条件必现）、**表现**（报错 / 超时 / 值错误 / 服务不可用 / 数据不一致 / 性能劣化）；禁止写长句 |
| `aliases` | ❌ | 数组 | 同义词 / 别名 | 容纳用户的非规范说法（"数据对不上" → "数据不一致"）；无则留空 |
| `version_range` | ❌ | 字符串，如 `">=3.0"` | 适用版本范围 | 版本大变化后案例可能不再可比；有明确边界时填写 |
| `source_tickets` | ✅ | 单号数组 | 来源单号 | 至少一个；**pattern 必须列全被归并的 instance 单号**——溯源与复核的依据 |
| `closed_at` | ✅ | `YYYY-MM-DD` | 结案日期 | 用于时效判断与检索排序（越近的案例越有参考价值） |
| `updated` | ✅ | `YYYY-MM-DD` | 最后更新日期 | 复核、补录、修订后更新 |
| `verified_by` | ❌ | 字符串 | 验证人 / 验证渠道 | 用于可信度判定；团队规范不允许记录人名时，改记验证方式（如"回归测试报告 XX"） |

### 3.2 正文各节说明

**`## 问题表现` —— 让后人判断"像不像"**

四个小项各有用途，不要合并成一段：

- **触发条件**：什么时候会看到（必现 / 偶现 / 特定条件下必现）。这是检索匹配与假设生成的第一依据。
- **现象**：观察到的客观事实——报错文案、错误码、界面表现、值错误、超时等，并与预期对比。
- **时间**：发生时间、持续 / 恢复情况。
- **影响范围**：哪些业务 / 模块 / 环境受影响；**哪些不受影响**——不受影响的和受影响的一样值钱，它是排除法的主要线索。
- 注意：只写可观测事实，不写推断。"接口超时"是现象；"因为连接池不够"是结论（属于「根因」节）。

**`## 排查过程` —— 案例里最保值的部分**

- 写法：按时间顺序，每条"做了什么 → 得到什么结果"。不求全，但求真实。
- **必须记录走不通的路**：失败的排查方向、被否掉的猜测。这是「排除项」的来源，也是后人避免重走弯路的依据。
- 不确定的步骤标注"未确认"，不要写成确凿结论。
- 为什么强调"最保值"：根因会随版本过期，而"怎么查、先查什么、什么被排除"永远可复用。

**`## 根因` —— 机制级，不是类别词**

- 一句话 + 机制链条：A → B → C，解释"为什么出现这个现象"。
  - ❌"配置问题"（类别词，无信息量）
  - ✅"连接池上限下调导致连接耗尽，请求排队超时"
- `责任点（代码）`：`模块/文件/类`（可带行号）。**只绑代码，不绑人、不绑团队。**
- 未定位时：如实写"**未定位**"，说明当前缩小到的候选方向，并把缺什么写进「信息缺口」。

**`## 决定性证据` —— 当年靠什么确认的**

- 表格四列：证据 ｜ 类型（直接 / 间接 / 排除性）｜ 物理凭据 ｜ **为什么能证明**。
- 物理凭据格式与规则模板一致：
  - `文件:行号@commit`
  - `日志文件:行号@时间戳`
  - `单号`
- "为什么能证明"是关键列：写清证据与结论之间的关联逻辑，而不是复述证据。
- 两个用途：① 定位命中后，直接转成采集清单（告诉 Agent 去采什么、怎么采）；② 结论被推翻时，知道该复核哪一环。
- 硬要求：**没有物理凭据的内容不写进本表**，降级为线索写进「排查过程」。

**`## 排除项` —— 只写"排除了 X"等于没写**

- 格式：**排除**：<假设> ｜ **依据**：<证据或负证据>。
- **负证据是合法依据**，写法："若为 X，应出现 Y；实测 Y 未出现 / 无相关日志"。
- 排除项与规则模板的「反例与边界」呼应：案例的排除项积累到一定程度，就是规则的边界条件。

**`## 修复与验证`**

- 修复方式：改了什么（代码位置 / 配置项）。
- 验证结果：如何确认修复有效（复现步骤不再复现 / 回归测试通过 / 监控观察无异常）。
- 验证凭据：可核验的观察记录（测试报告编号、看板观察周期、关闭的单号）。
- 与 `confidence` 的关系：**无验证的案例 `confidence ≤ medium`**，不能升 `active`。

**`## 信息缺口` —— 如实记录"不知道什么"**

- 未定位或证据不全时**必填**：缺什么信息、可能在哪里获取、下次出现的建议采集动作。
- 三个用途：① 逃生通道的记录出口；② 学习模式判断该条能否升级为规则；③ 下次遇到同类问题时，优先按它去采集。
- 已定位且证据完整时写"无"，不要留空。

**`## 备注`（可选）**

- 适用范围、坑点提醒、关联案例 / 规则编号、后续待办。

## 四、使用注意事项（总则）

1. **案例只排序、不判定。** 命中只产生假设与线索，必须经验证才能进入结论（这条纪律要写进 Agent 的行为约束）。
2. **排查过程比根因保值。** 根因会随版本过期，过程永远可用——不要只写结论。
3. **走不通的路也要记。** 失败的排查方向是排除项，能避免后人重走弯路。
4. **决定性证据必须物理可核验。** 无凭据的内容降级为线索（写进排查过程），不得进证据表。
5. **排除项必须带依据。** 负证据（该出现而没出现）是合法依据。
6. **未定位的案例也可以入库**（`draft` + `low` + 信息缺口），这是逃生通道的设计出口；但**不得作为规则来源**。
7. **如实记录，不编造。** 不美化过程、不补全没发生的事——Agent 尤其容易"脑补"细节，这是知识库最大的污染源。
8. **一个案例记录一个（类）问题。** 多个独立问题拆成多条。
9. **pattern 与 instance 的关系**：instance 是素材，pattern 是归纳产物；归纳时用 `source_tickets` 指回全部原始记录。
10. **结论会过期，要维护。** 版本大变化后复核结论；被推翻的案例标 `deprecated` 并注明推翻原因（推翻原因本身是有价值的学习信号）。
11. **责任只绑代码不绑人。** 写模块 / 文件 / 类，不写人名、团队名。
12. **别抄工单全文。** 案例是结构化提炼，原始信息保留在工单系统（用 `source_tickets` 链接），正文只留定位相关的关键信息。
13. **为"将来被归纳"而写。** `tags`、触发条件、现象、影响范围要规范——学习模式靠这些字段聚类，写乱了就聚不出来。

## 五、示例

> 以下示例中的数据（单号、commit、时间戳）均为示意，实际填写必须使用真实值。

### 示例 1：归纳案例（pattern，含验证）

````markdown
---
id: CASE-SCHED-004
title: 多实例部署下定时任务重复执行导致数据重复写入
type: pattern
status: active
confidence: high
occurrence_count: 3
domain: [订单, 数据同步]
component: [order-job, TaskScheduler.java]
tags: [偶现, 数据不一致]
aliases: [数据写入两次, 重复数据]
version_range: ">=3.2"
source_tickets: [DTS-45321, DTS-47890, DTS-51207]
closed_at: 2026-05-30
updated: 2026-06-02
verified_by: 回归测试报告 RT-2026-118
---

## 问题表现

- **触发条件**：多实例部署（≥2 实例）时；定时任务触发时刻
- **现象**：偶现；同一批次数据被写入两次，无任何报错日志
- **时间**：约每 2~3 天出现一次，持续数周；无人工干预自行"恢复"（下一个批次正常）
- **影响范围**：仅统计同步任务受影响；单实例部署环境未出现；对账模块受影响（出现重复明细）

## 排查过程

1. 查数据库写入记录 → 发现同一批次 ID 存在两条写入记录，时间戳非常接近
2. 查任务调度日志 → 同一触发时刻，两个实例上均出现"任务开始执行"日志 → 指向并发执行
3. 检查调度框架配置 → 配置为"单机语义"，未启用分布式互斥 → 与现象吻合
4. 在单实例环境尝试复现 → 未复现 → 佐证"多实例并发"是必要条件
5. 查上游推送记录 → 无重复推送 → 排除上游原因

## 根因

定时任务缺少分布式互斥，多实例部署下同一时刻多个实例同时抢到执行权，导致重复执行写入。

机制链条：多实例部署 → 触发时刻两个实例同时调度 → 无互斥 → 重复写入 → 下游对账出现重复明细

- **责任点（代码）**：`order-job / TaskScheduler.java`

## 决定性证据

| 证据 | 类型 | 物理凭据 | 为什么能证明 |
|------|------|----------|--------------|
| 同一时刻两个实例均有任务执行日志 | 直接 | `scheduler.log:118 @2026-05-12 02:00:01` | 证明重复执行事实；时间戳完全一致排除巧合 |
| 代码中无分布式锁 | 直接 | `TaskScheduler.java:45@a1b2c3d` | 解释为什么两个实例都能执行——无互斥措施 |
| 单实例环境无法复现 | 排除性 | DTS-45321 评论中的验证记录 | 排除任务调度逻辑自身缺陷；锁定"多实例"为必要条件 |

## 排除项

- **排除**：上游数据重复推送 ｜ **依据**：上游推送记录无重复，单批次仅推送一次
- **排除**：任务被调度中心重复下发 ｜ **依据**：调度中心日志显示单次下发；重复写入发生在同一触发时刻的不同实例上
- **排除**：写入逻辑自身 bug ｜ **依据**：单实例环境连续运行 2 周无重复（负证据）

## 修复与验证

- **修复方式**：引入 Redis 分布式锁（key = 任务 ID，带过期时间）；同时为写入逻辑补充幂等控制
- **验证结果**：上线后连续观察 3 周，未再出现重复数据
- **验证凭据**：监控看板"重复数据检查"连续 21 天为 0；DTS-51207 关闭

## 信息缺口

- 无

## 备注

- 同类定时任务共 6 个，已同步排查：其中 4 个存在同样问题，已一并修复
- 关联规则：`RULE-CONC-008`（"多实例 + 定时触发 + 无互斥 → 重复执行"）
````

### 示例 2：单次案例（instance，完整证据）

````markdown
---
id: CASE-CONC-012
title: 静态 SimpleDateFormat 并发共享导致偶现时间解析异常
type: instance
status: active
confidence: high
occurrence_count: 1
domain: [接口服务, 并发安全]
component: [report-api, DateUtils.java]
tags: [偶现, 值错误, NumberFormatException]
aliases: [时间解析报错, 日期转换异常]
version_range: ""
source_tickets: [DTS-58230]
closed_at: 2026-06-15
updated: 2026-06-15
verified_by: 并发压测报告 PT-2026-091
---

## 问题表现

- **触发条件**：并发请求（压测 QPS ≥ 50 时稳定出现；低并发下难复现）
- **现象**：偶现；少量请求返回时间字段解析失败（`NumberFormatException`），报错内容随请求随机变化
- **时间**：压测期间集中出现
- **影响范围**：仅时间格式化工具类相关的接口；其他接口正常

## 排查过程

1. 定位报错堆栈 → `java.lang.NumberFormatException`，位于 `SimpleDateFormat.parse`
2. 检查工具类实现 → 发现所有调用方共享同一个静态 `SimpleDateFormat` 实例
3. 并发压测复现 → QPS ≥ 50 时稳定复现，低并发难复现 → 指向并发安全
4. 替换为 `DateTimeFormatter` 后压测 → 未再复现

## 根因

`SimpleDateFormat` 非线程安全，被静态共享后被多线程并发调用，解析状态互相污染。

机制链条：静态共享实例 → 并发调用 → 内部 Calendar 状态被并发修改 → 解析结果错乱 → 偶现异常

- **责任点（代码）**：`report-api / DateUtils.java`

## 决定性证据

| 证据 | 类型 | 物理凭据 | 为什么能证明 |
|------|------|----------|--------------|
| 异常堆栈指向 SimpleDateFormat.parse | 直接 | `app.log:347 @2026-06-10 15:22:41` | 锁定异常发生位置 |
| 静态共享实例定义 | 直接 | `DateUtils.java:23@b2c3d4e` | 解释并发污染的来源 |
| 并发压测可稳定复现、替换后消失 | 排除性 | 压测报告 PT-2026-091 | 排除输入数据不合法等其他解释 |

## 排除项

- **排除**：输入时间串格式不合法 ｜ **依据**：同一输入串在低并发下全部解析成功（负证据：若格式问题，应稳定失败）
````
