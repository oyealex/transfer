# 决策点规则

步骤 2、3 使用。

决策点是本 Skill 的原子计量单位：**检测对象引入或修改的一条行为分支**。

## 计入清单

| 类型 | 形态 | 说明 |
|---|---|---|
| 条件分支 | `if (cond) {…}` | `else if` 链每条一个 |
| 否则分支 | `else {…}` | `else` 内非空时单独计一个 |
| 三元取值 | `cond ? a : b` | |
| 多路选择 | `switch` 的每个 `case` / `default` | |
| 提前返回 | 提前 `return` / `continue` / `break` 的守卫条件 | |
| 异常处理 | `catch` / `except` / 错误处理块 | 每个捕获类型一个 |
| 参数校验 | 参数校验失败路径（抛错或返回错误码） | |
| 边界比较 | 显式边界常量比较（`>= MAX`、`< 0`、`== 0`、`len > N`） | 已作为条件分支计入的不重复计 |
| 兜底分支 | 显式降级分支（默认值、兜底逻辑、缓存未命中分支） | |

## 不计入清单

| 形态 | 理由 |
|---|---|
| `&&` / `\|\|` 短路求值 | 除非独立成一条语句，否则属于表达式细节，噪声大 |
| 循环进入 / 退出条件 | 属于遍历机制，不代表业务分支 |
| 预处理条件编译 | 构建期配置，不是运行时行为 |
| 日志级别判断 | 无业务语义 |
| 裸抛出异常 | 守卫它的条件分支已经计过 |
| 空值合并、默认参数展开 | 语言机制 |
| 框架回调注册 | 无分支语义 |
| 测试代码内部的分支 | 只统计生产代码 |
| 纯搬移、提取，条件文本未变的分支 | 语义与搬移前一致，不产生新的验证需求 |

「条件文本未变」指真正的纯搬移。条件本身被改过时，哪怕结构没变，也算一个「修改」来源的决策点，不拆成删除加新增。

## 语言示例

Java，5 个决策点：

```java
public List<Item> pick(List<Item> items, boolean flag) {
    if (items.isEmpty()) {                    // 提前返回
        return Collections.emptyList();
    }
    for (Item i : items) {                    // 不计
        if (i.isValid()) { ... }              // 条件分支
    }
    try { ... }
    catch (IOException e) { ... }             // 异常处理
    catch (RuntimeException e) { ... }        // 异常处理
    int n = flag ? 1 : 0;                     // 三元
    return ...;
}
```

Python，3 个决策点：

```python
def pick(payload, data):
    if not payload:          # 提前返回
        raise ValueError()
    for k, v in data.items():   # 不计
        if v is None:           # 条件分支
            continue
    try:
        ...
    except KeyError:            # 异常处理
        ...
```

C，3 个决策点：

```c
int pick(const char *buf, size_t len, int op) {
    if (len == 0) return -EINVAL;   // 提前返回 + 边界比较，计 1 个
    switch (op) {                   // 2 个：case + default
        case OP_READ: return 1;
        default: return -ENOSYS;
    }
}
```

C++，3 个决策点：

```cpp
auto pick(Map &m, const Key &k) {
    if (auto it = m.find(k); it != m.end()) { ... }  // 条件分支
    else { ... }                                      // 否则分支
    try { ... }
    catch (const std::exception &) { ... }            // 异常处理
}
```

## 字段

| 字段 | 说明 |
|---|---|
| 编号 | 「模块缩写-两位序号」，按文件路径排序后顺序编号，稳定可复现 |
| 文件 / 行号 | 条件所在行，取改动后的行号 |
| 类型 | 上表枚举 |
| 条件 | 条件原文，去多余空白 |
| 分支 | 真 / 假、具体枚举值、捕获类型等 |
| 来源 | 新增 / 修改 |
| 条件变化 | 仅当来源为「修改」时填：新增或删除了哪个子句，如「删除 `enabled()` 前置」「新增 testUrl 校验」 |
| 置信度 | 高 / 低 |

编号里的模块缩写只是排序与交叉引用的锚点，不是分类，不需要在报告里额外解释。

## 置信度

判「低」的情形：

- 条件跨行超过 5 行，或含宏拼接
- C / C++ 模板展开、宏生成的分支
- 条件来自注解或元编程（Java 注解处理器、Python 装饰器生成的分支）
- 结构被大范围重排，无法确认是新增还是原有

低置信决策点计入分母但单独统计。占比超过配置上限时，扣减证据完整度。

## 枚举冻结

分支计数按语法语句固定，不按「有没有执行」或「值不值得测」增减：

- 每个 `if` / `else if` 计一个；`else` 体内非空时另计一个
- 每个 `case` / `default` 计一个
- 每个三元表达式计一个
- 每个 `catch` 计一个
- 每个显式边界常量比较计一个（已作为 `if` 计入的不重复）
- 每个兜底分支计一个

**被替换方法体内的分支按同一规则展开。** 不能因为「反正没执行」就少计，也不能因为「看得更细」就多计——同一个方法在两次运行里必须数出同样的分支数。决策点总数在三次运行里从 57 漂到 62 再漂到 65，主因就是这一条没有冻结。

枚举结果一次写入 `02-决策点.md`，后续步骤只引用编号，不重新计数。

## 条件变化的覆盖要求

来源为「修改」的决策点，必须在「条件变化」字段写清增删了哪个子句，并按下面的规则核对用例：

| 变化 | 必须有的用例 | 找不到时 |
|---|---|---|
| 删除了子句 A | 一条「A 为假」的用例 | 判未观测 |
| 新增了子句 A | 一条「A 为真」的用例 | 判未观测 |

**不能因为其他子句有用例覆盖就算已观测。** 典型反例：条件从 `enabled && invalid` 改成 `invalid`，四个 400 用例都是 `enabled=true`，唯一 `enabled=false` 的用例草稿又合法——这条决策点仍然是未观测，因为「删掉 enabled 前置」这件事没有任何用例验证。

## 抽取流程

逐个生产改动片段：

1. 只取新增侧与成对修改侧的代码。
2. 按语法结构提取条件，不要按行号硬匹配。
3. 条件被修改但结构未变 → 来源记「修改」，整条算一个决策点。
4. 片段里判不出结构的（宏、模板、超长表达式）→ 该片段标「无法判定」。

## 与语言能力的对应

Java / Python（能力档「完整」）：符号级抽取 + 观测率。

C / C++（能力档「受限」）：只做文件级关联，不计算观测率。仍然抽取决策点，但结果只用于报告附录的观测矩阵，不进入判定公式。
