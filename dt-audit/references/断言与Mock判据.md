# 断言与 Mock 判据

步骤 3 使用。

## 判据是产出对账

判一条断言对一条分支的档位，只做三步。两侧都从代码读，断言的期望值不参与判断：

1. **列产出项**（只看分支代码）：这条分支正常走下去会产生什么？只从五类里取——返回值、抛出的异常、写入或改变的状态、发起的协作（是否调用、调给谁、用什么参数、几次）、产出的产物（对象、文件、报文）。通常 1–3 项，逐项标出哪几项**决定性**：改错它，业务就错。
2. **列读取量**（只看断言）：这条断言实际读到什么，是不是上面某一项。
3. **对账**：读到决定性产出项 → **有效**；只读到非决定性量 → **形状 / 存活**；一项也没读到 → 这条断言不覆盖该分支。

**决定性默认成立。** 只有下列量算非决定性，名单封闭、不再扩写——非空 / 是否 `null`、类型或类名、长度 / 条数 / `size()`、裸异常类型（不看错误码）、日志 / 耗时 / 时间戳、「跑通了 / 没抛异常」。落进名单的按形状或存活判，名单之外一律按决定性算。

**读到一项就够。** 不要求每一项产出都被断言，也不追问「还有没有别的错法没被覆盖」。本 Skill 只回答「这条分支的产出有没有被读到」，不回答「断言够不够强」——后者静态分析判不了，硬判只能靠猜。

**不按断言取反判档。** 「把实现改错一处，这条断言会红吗」不能当中枢判据：照着断言的期望值取反，任何断言都必然红；随便找一处代码改坏，任何断言都必然漏。两种结果都不携带信息。取反只作自检，见文末「自检」。

常见对账：

| 分支产出项 | 用例里的断言 | 对账结果 |
|---|---|---|
| 产物：压缩包及其内容 | 先断言压缩包存在，同一用例解压后断言文件内容 | 有效。存在性断言本身按存活记；同用例的内容断言读到「产物」这一项，绑定到产出压缩包的逻辑点后，该点即已断言。下游断言可以为上游产出作证，按数据流判断 |
| 产物：压缩包 | 只断言压缩包存在 | 存活。存在 / 非空在名单里 |
| 列表元素 | 只断言 `assertEquals(3, list.size())`，后面没有元素断言 | 形状。长度在名单里；补上元素断言即升为有效 |
| 协作：是否调用 `router.route(msg)` | `verify(router).route(msg)` | 有效。这条分支能错的只有「调没调」，`verify` 读到的正是它 |
| 协作：调用参数 `route(msg, priority)` | `verify(router).route(any())` | 存活。参数在产出项里、断言没读到，该逻辑点落断言偏弱 |
| 返回值：订单金额 | `assertEquals(99.00, order.getAmount())` | 有效 |
| 抛出的异常：带错误码的 `InvalidOrderException` | `assertThrows(Exception.class, ...)` | 存活。裸异常类型在名单里 |

## 三档：有效 / 形状 / 存活

| 档位 | 定义 | 对账结果 |
|---|---|---|
| 有效 | 断言读到这条分支的决定性产出项 | 交集里有决定性项 |
| 形状 | 只读到长度、条数、类型、集合形状这类非决定性量 | 交集里只有名单内的形状量 |
| 存活 | 只读到「不为空」「没抛异常」「跑通了」 | 交集里只有名单内的存活量 |

注意 **`assertNotNull` 属于存活档，不属于形状档**：非空只说明拿到了东西，不说明拿到的是对的。形状看的是大小 / 类型 / 长度 / 集合形状。

**档位是相对逻辑点的，不是绝对的。** 同一条断言，对逻辑点甲可能读到决定性产出项，对逻辑点乙只读到长度。裁定必须绑定到具体逻辑点和具体分支。

**一条断言的身份是「用例 + 断言行号」**：它可以在证据表里绑定多个逻辑点，但计数时只算一条，档位取它在所绑定逻辑点上的**最高档**（有效 > 形状 > 存活）。这样拆行与合并写的结论一致。

## 交互验证不是单独一类

`verify(...)` / `expect(...)` 就是一条断言，按同一套对账判，不预设档位：

- 分支产出是「**是否发起这次协作**」→ `verify` 读到它，**有效**。中间件没有参数、没有返回值，或者参数对当前结论无关，都不影响这条结论：这条分支能错的只有「调没调」。
- 分支产出是「**协作的参数值**」→ 不带 matcher 的 `verify` 读不到参数，落**存活**，该逻辑点记断言偏弱；带 matcher 才有效。
- 分支产出是「**本对象自己算出的值或状态**」，用例却只断言了 mock 交互 → 产出没被读到，该逻辑点落**未断言**，用例层记「只用交互验证」。

「只证明调用了，不证明结果对」这句话只在第三种情形成立，不能推广到前两种。

## Mock 判定：只看能否拦截缺陷

对每个 mock 点只问一句：**它让用例拦不住什么？**

1. 被替换的方法体内含本对象的逻辑点，覆盖这些逻辑点的用例又全走假实现 → **测试对象偏移 · 实现被替换**。
2. 假实现的行为与真实实现不一致，使断言可能对假实现绿、对真实实现红 → **测试对象偏移 · 契约漂移**。
3. 断言只落在假实现的交互上，而被测分支的产出是本对象自己算出的值或状态，没有断言读到它 → **断言质量低 · 只用交互验证**。产出就是「是否发起这次协作」时不算，回到上面的对账。
4. 以上都不成立 → **不判**。

用例的测试目标决定哪些路径必须覆盖；路径没覆盖记场景覆盖不足，不另立 mock 问题。mock 的是外部还是内部依赖、mock 参数是否硬编码、接缝是否优雅，都不进结论。

## Mock 情形七类

**计数单位统一为「处」**，一处 = 「Mock 清单」里的一行记录。同一个替换方法体里含多个逻辑点时，不按逻辑点数放大。

| 类 | 情形 | 判断 | 理由 |
|---|---|---|---|
| 1 | 隔离外部边界（三方接口、时间、随机、文件、消息队列） | 不判 | 不影响拦截能力 |
| 2 | 替换同模块内部协作者 | 不判；含本对象逻辑点且覆盖用例全走假实现 → 测试对象偏移 | mock 的位置不是判据 |
| 3 | 替换被测对象自身的一部分 | 同上 → 测试对象偏移 | 同上 |
| 4 | 用假对象代替值对象或数据结构 | 不判 | 用例设计问题，不影响拦截能力 |
| 5 | 假实现返回的契约与真实不一致 | 测试对象偏移 · 契约漂移 | 可能对假实现绿、对真实实现红 |
| 6 | 用交互验证代替结果断言 | 断言质量低 · 只用交互验证 | 只证明「调用了」，而被测分支的产出是它自己算出的值或状态 |
| 7 | **替换掉带业务分支的真实实现** | **测试对象偏移 · 实现被替换，最高危** | 用例执行的不是生产代码，该处缺陷拦不住 |

第 7 类是本 Skill 最看重的一类，单独定义。第 6 类只在上面的第三种情形登记：交互验证读的正是分支产出时，它是有效证据，不记 Mock 问题。

### 实现被替换的判定

命中任一即计入「被替换实现」：

- 用 `@Override` 探针子类覆盖被测类的取数、计算、判定方法
- `spy()` 后对内部方法 `doReturn` / `doThrow`
- `MockedStatic` 替换承担业务逻辑的静态入口
- `mockConstruction` 替换参与计算的对象构造
- Python 对被审计类的内部方法 `patch.object`，或 `monkeypatch` 替换生产模块函数
- C / C++ 链接期替换、弱符号覆盖生产函数

再把替换点与被替换方法体内的逻辑点逐个对起来：**被替换方法体里含几个逻辑点，就逐个判**。对每个逻辑点看覆盖它的用例：全部执行假实现 → 记「实现被替换」；只要有一条覆盖该逻辑点的用例走真实实现，就按那条用例判档，不记测试对象偏移。

判定时注意**零覆盖不算「全部执行假实现」**：「全部」的前提是至少有一条覆盖该逻辑点的用例。一条都没有的情况落「无测试」，不落「实现被替换」。

不构成实现被替换的例外：替换纯 IO、时间、随机、三方调用、工具类的静态方法——这些本身不含业务分支，归第 1 类。

区分的问句：**被替换掉的那段代码里，有没有本报告要盯住的逻辑点？** 有 → 实现被替换；没有 → 边界隔离。

## 七类与问题类型的对应

对应关系见上表「判断」列，不再单列一张表。「七类」只是识别用的情形表，不是判据表；判定只按「Mock 判定」那 4 条走，同一处证据只归一个根因类型。

## 与断言档位的关系

三档只在**绑定到具体逻辑点的具体分支时**判一次，不设「先全文通档」的阶段。步骤 2 只把断言的行号与原文录进清单；档位与最终状态都由步骤 3 裁定：把断言绑定到逻辑点的分支上，回答「这条分支的产出被读到没有、读到的是哪一项」。

「断言偏弱」的典型形态：

- 只读到名单里的非决定性量（长度、类型、集合形状、非空、裸异常）
- 分支产出是参数值，断言只确认了调用发生
- 只覆盖了该分支的一半（真支测了、假支没测）
- 断言被假实现的返回值主导，读到的是假实现给的值而非本分支的产出

## 不判的情形

下列情形**不构成**降档理由，命中即维持原档：

- 存在性断言之后，同一用例对同一产物还有内容断言
- `verify` 盯的是分支控制的「是否调用」，中间件没有参数或返回值，或参数与该分支的结论无关
- 断言分散在辅助方法、`assertAll`、参数化里，单看一行不完整
- 断言只覆盖该分支唯一可能抛出的异常类型
- 断言只读了一个字段，而该字段就是这条分支唯一的产出
- 一条断言同时像形状又像存活，取高档

## 已断言的举证要求

判 `已断言` 必须给出四样，缺一即为不合格的证据：

1. 逻辑点编号
2. 用例方法名
3. 断言行号
4. **读到的是哪一项产出**

不要求回答「改错会不会红」——那是充分性问题，答不上来不构成降档。判 `断言偏弱` 一样要举证：指出断言读到的具体是哪一项非决定性量，或说清分支产出为什么没被它读到。举证不出来的，维持 `已断言`。

对账示例：`SYS-14` 的分支产出项是「是否安装认证器」，断言读的是 `outcome.success()`——不在这条分支的产出清单里。删掉 username 守卫这条断言照样绿，交集为空，按未断言判。

## 自检：取反只用来复核

结论写完后可以取反一次做自检，但不进判据：

- 取反后断言红了 → 说明对账对上了，维持原档。
- 取反后断言不红 → 先回查是不是读的另一个产出项（产出常有 1–3 项），或归属判错了；**不直接降档**。

## 一致性检查

每个逻辑点在证据表里只有一个状态，「同一事实两处取值不同」由单表结构本身排掉。剩下两条交给 `stats` 脚本开跑时校验，不另做人工对表：

1. 「触达用例」列写了用例，状态却是「无测试」，二者不能共存
2. 「已断言」「断言偏弱」的「断言证据」列不能为空（必须写出用例、断言行号与读到的产出项）

校验不通过时以更保守的状态为准，改证据表后重跑脚本。
