# 断言与 Mock 判据

步骤 3 使用。

## 断言判别力三档

| 档位 | 定义 | 判定问句 |
|---|---|---|
| 判别性 | 能区分对错 | 把实现改错一处，这条断言会红吗？会 → 判别性 |
| 结构性 | 校验了形状，没校验内容 | 断言是否只看了大小、类型、非空、集合长度？是 → 结构性 |
| 存在性 | 只证明「跑通了」 | 断言里出现了被测对象的返回值、状态或异常吗？没有 → 存在性 |

写法对照：

| 档位 | 正例 | 反例 |
|---|---|---|
| 判别性 | `assertEquals(200, resp.getStatus())`；`assertThat(total).isEqualByComparingTo("99.00")`；`assertThrows(InvalidOrderException.class)` 并校验错误码 | — |
| 结构性 | `assertEquals(3, list.size())` 加元素内容校验后升为判别性 | 只写 `assertEquals(3, list.size())` |
| 存在性 | — | `assertNotNull(result)`；`assertTrue(list.size() > 0)`；`assertThrows(Exception.class)`；`assertDoesNotThrow(...)` |

**档位是相对决策点的，不是绝对的。** 同一条断言，对决策点甲可能是判别性，对决策点乙只是存在性。裁定必须绑定到具体决策点和具体分支。

## Mock 判定：只看能否拦截缺陷

对每个 mock 点只问一句：**它让用例拦不住什么？**

1. 被替换的方法体内含本对象的决策点，覆盖这些决策点的用例又全走假实现 → **测试对象偏移 · 实现被替换**。
2. 假实现的行为与真实实现不一致，使断言可能对假实现绿、对真实实现红 → **测试对象偏移 · 契约漂移**。
3. 断言只落在假实现的交互上，没有观察被测目标的结果 → **断言质量低 · 只用交互验证**。
4. 以上都不成立 → **不判**。

用例的测试目标决定哪些路径必须覆盖；路径没覆盖记场景覆盖不足，不另立 mock 问题。mock 的是外部还是内部依赖、mock 参数是否硬编码、接缝是否优雅，都不进结论。

## Mock 情形七类

| 类 | 情形 | 判断 | 理由 |
|---|---|---|---|
| 1 | 隔离外部边界（三方接口、时间、随机、文件、消息队列） | 不判 | 不影响拦截能力 |
| 2 | 替换同模块内部协作者 | 不判；含本对象决策点且覆盖用例全走假实现 → 测试对象偏移 | mock 的位置不是判据 |
| 3 | 替换被测对象自身的一部分 | 同上 → 测试对象偏移 | 同上 |
| 4 | 用假对象代替值对象或数据结构 | 不判 | 用例设计问题，不影响拦截能力 |
| 5 | 假实现返回的契约与真实不一致 | 测试对象偏移 · 契约漂移 | 可能对假实现绿、对真实实现红 |
| 6 | 用交互验证代替结果断言 | 断言质量低 · 只用交互验证 | 只证明「调用了」，不证明「结果对」 |
| 7 | **替换掉带业务分支的真实实现** | **测试对象偏移 · 实现被替换，最高危** | 用例执行的不是生产代码，该处缺陷拦不住 |

第 7 类是本 Skill 最看重的一类，单独定义。

### 架空的判定

命中任一即计入「被替换实现」：

- 用 `@Override` 探针子类覆盖被测类的取数、计算、判定方法
- `spy()` 后对内部方法 `doReturn` / `doThrow`
- `MockedStatic` 替换承担业务逻辑的静态入口
- `mockConstruction` 替换参与计算的对象构造
- Python 对被审计类的内部方法 `patch.object`，或 `monkeypatch` 替换生产模块函数
- C / C++ 链接期替换、弱符号覆盖生产函数

再把替换点与被替换方法体内的决策点逐个对起来：**被替换方法体里含几个决策点，就逐个判**。对每个决策点看覆盖它的用例：全部执行假实现 → 记「实现被替换」；只要有一条覆盖该决策点的用例走真实实现，就按那条用例判档，不记测试对象偏移。

不构成架空的例外：替换纯 IO、时间、随机、三方调用、工具类的静态方法——这些本身不含业务分支，归第 1 类。

区分的问句：**被替换掉的那段代码里，有没有本报告要观测的决策点？** 有 → 架空；没有 → 边界隔离。

## 七类与问题类型的对应

对应关系见上表「判断」列，不再单列一张表。「七类」只是识别用的情形表，不是判据表；判决只按「Mock 判定」那 4 条走，同一处证据只归一个根因类型。

## 与判别力的关系

三档只在**绑定到具体决策点的具体分支时**判一次，不设「先全文通档」的阶段。步骤 2 只把断言的行号与原文录进清单；档位与最终状态都由步骤 3 裁定：把断言绑定到决策点的分支上，回答「这条分支走了没有、走对了没有」。

「部分观测」的典型形态：

- 断言了该分支的副作用但没断言结果值
- 断言了结果但没覆盖该分支特有的错误路径
- 断言被假实现的返回值主导，真实实现改错也不会红
- 只覆盖了该分支的一半（真支测了、假支没测）

## 已观测的举证要求

判 `已观测` 必须同时给出三样：

1. 决策点编号
2. 用例方法名
3. 断言行号

并且能回答一句：**把这条分支改错，是这个断言行会红吗？** 答不上来就不是已观测，按 [SKILL.md](../SKILL.md) 的判档顺序落到部分观测或未观测。

反例：`SYS-14 / get200_returnsSuccess / ProxyConnectivityTesterTest.java:48` 断言的是 `outcome.success()`；删掉 username 守卫后这条断言照样绿，而守卫的产出（是否安装认证器）没有被任何断言引用，按判档顺序是 `未观测`。

## 一致性检查

每个决策点在证据表里只有一个状态，「同一事实两处取值不同」由单表结构本身排掉。剩下两条交给 `stats` 脚本开机校验，不另做人工对表：

1. 被架空的决策点不得同时记为「分支未观测」
2. 「触达用例」列写了用例，状态却是「无测试」，二者不能共存

校验不通过时以更保守的状态为准，改证据表后重跑脚本。
