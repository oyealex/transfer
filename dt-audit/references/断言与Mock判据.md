# 断言与 Mock 判据

步骤 2 初判、步骤 3 裁定共用。

## 断言判别力三档

| 档位 | 定义 | 判定问句 |
|---|---|---|
| 判别性 | 能区分对错 | 把实现改错一处，这条断言会红吗？会 → 判别性 |
| 结构性 | 校验了形状，没校验内容 | 断言是否只看了大小、类型、非空、集合长度？是 → 结构性 |
| 存在性 | 只证明「跑通了」 | 断言里出现了被测对象的返回值、状态或异常吗？没有 → 存在性 |

写法对照：

| 档位 | 正例 | 反例 |
|---|---|---|
| 判别性 | `assertEquals(200, resp.getStatus())`；`assertThat(total).isEqualByComparingTo("99.00")`；`assertThrows(InvalidOrderException.class)` 并校验错误码 | — |
| 结构性 | `assertEquals(3, list.size())` 加元素内容校验后升为判别性 | 只写 `assertEquals(3, list.size())` |
| 存在性 | — | `assertNotNull(result)`；`assertTrue(list.size() > 0)`；`assertThrows(Exception.class)`；`assertDoesNotThrow(...)` |

**档位是相对决策点的，不是绝对的。** 同一条断言，对决策点甲可能是判别性，对决策点乙只是存在性。裁定必须绑定到具体决策点和具体分支。

## Mock 情形七类

| 类 | 情形 | 判断 | 理由 |
|---|---|---|---|
| 1 | 隔离外部边界（三方接口、时间、随机、文件、消息队列） | 合理，鼓励 | 隔离不确定性，测试才稳定 |
| 2 | 替换同模块内部协作者 | 可疑，需理由 | 往往说明接缝没设计好，测试退化成接线检查 |
| 3 | 替换被测对象自身的一部分 | 反模式 | 测的是假实现的行为 |
| 4 | 用假对象代替值对象或数据结构 | 冗余 | 直接构造真实对象更便宜也更真 |
| 5 | 假实现返回的契约与真实不一致 | 高危 | 「测试绿、线上炸」的经典来源 |
| 6 | 用交互验证代替结果断言 | 高危 | 只证明「调用了」，不证明「结果对」 |
| 7 | **替换掉带业务分支的真实实现** | **架空，最高危** | 用例执行的不是生产代码，覆盖率与观测全部失真 |

第 7 类是本 Skill 最看重的一类，单独定义。

### 架空的判定

命中任一即计入「被替换实现」：

- 用 `@Override` 探针子类覆盖被测类的取数、计算、判定方法
- `spy()` 后对内部方法 `doReturn` / `doThrow`
- `MockedStatic` 替换承担业务逻辑的静态入口
- `mockConstruction` 替换参与计算的对象构造
- Python 对被审计类的内部方法 `patch.object`，或 `monkeypatch` 替换生产模块函数
- C / C++ 链接期替换、弱符号覆盖生产函数

再把替换点与被替换方法体内的决策点对起来：**被替换方法体里含几个决策点，就记几个「实现被替换」**。前提是该方法的全部触达用例都替换了它；只要有一条用例走真实实现，该决策点就按那条用例判档，不记 C1。

不构成架空的例外：替换纯 IO、时间、随机、三方调用、工具类的静态方法——这些本身不含业务分支，归第 1 类。

区分的问句：**被替换掉的那段代码里，有没有本报告要观测的决策点？** 有 → 架空；没有 → 边界隔离。

## 附加提示（不进问题分布）

以下现象写进维度章节作为提示，不计数、不参与任何比率。它们影响的是测试的未来有效性，不是本次改动的证据强度：

1. 快照全量比对但无基线来源说明
2. 测试体内 `try { … } catch (Exception e) { }` 吞掉异常
3. 用固定等待替代断言
4. 断言依赖执行顺序或共享状态

## 与判别力的关系

三档是步骤 2 的规则级初判，只用于生成断言清单。**最终状态由步骤 3 裁定**：把断言绑定到决策点的分支上，回答「这条分支走了没有、走对了没有」。

「部分观测」的典型形态：

- 断言了该分支的副作用但没断言结果值
- 断言了结果但没覆盖该分支特有的错误路径
- 断言被假实现的返回值主导，真实实现改错也不会红
- 只覆盖了该分支的一半（真支测了、假支没测）

## 已观测的举证要求

判 `已观测` 必须同时给出三样：

1. 决策点编号
2. 用例方法名
3. 断言行号

并且能回答一句：**把这条分支改错，是这个断言行会红吗？** 答不上来就不是已观测，按 [SKILL.md](../SKILL.md) 的判档顺序落到部分观测或未观测。

反例：`SYS-14 / get200_returnsSuccess / ProxyConnectivityTesterTest.java:48` 断言的是 `outcome.success()`；删掉 username 守卫后这条断言照样绿，而守卫的产出（是否安装认证器）没有被任何断言引用，按判档顺序是 `未观测`。

## 跨行一致性检查

报告定稿前跑一遍，四种矛盾必须为零：

1. 同一守卫的两个方向不能互相打脸：一行说「假支从未执行」，另一行不能说该守卫「已观测」
2. C1 的决策点不得同时出现在 D1
3. 同一方法若全部触达用例都替换了它，其体内决策点必须全部是「实现被替换」，不能有「已观测」
4. 「触达用例」列写了用例，状态却是「无测试」，二者不能共存

发现矛盾时以更保守的状态为准，并在 `04-观测矩阵.md` 里记一条复核说明。

## C / C++ 的额外限制

- 链接期替换只能识别「存在替换」，不能确认替换点覆盖了哪条分支
- 宏与模板生成的断言难以静态解析，标低置信
- 文件级关联下，「部分观测」与「未观测」的边界比 Java / Python 粗，报告里必须标注「受限检测」
