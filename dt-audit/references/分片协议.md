# 分片协议

步骤 2、3 使用，只在体量超过阈值时读这一份。阈值与触发条件见 [SKILL.md](../SKILL.md) 的「检测对象过大时的处理」。

分两个角色：**枚举片**负责看清，**裁定片**负责判。分片只降低单次上下文峰值，不降低总 token；低于阈值不要切。

## 何时分片

| 角色 | 判据 | 切法 |
|---|---|---|
| 枚举片 | **生产改动行** > 800 | 生产文件簇，每片 ≤ 500 改动行（> 2,000 行时 600） |
| 裁定片 | 合并编号后逻辑点 > 50 | 按点数，每 50 点一批，末批可少于 50 点 |

**生产改动行** = 范围表里「分类 = 生产代码且语言为 Java / Python」的「新增」+「删除」之和，只用于判分片。它与「变更生产代码行数」（只算新增、用于 KLOC）不是一个量，不要混用。

不触发时：≤ 800 行由主流程自己枚举，≤ 50 点由主流程自己裁定。

## 枚举片

### 切片

- 单位是**生产文件簇**：同目录或同包的文件聚在一起，一个类不拆。
- 单文件 > 500 改动行：独占一片，允许超均值。
- 测试文件跟随生产文件：`Foo.java` → `FooTest.java`、同包测试、以及 diff 里 import 了片内类的测试。
- 一个测试文件命中多片时**复制给每一片**（测试文件通常远小于生产代码，复制比协调便宜）。
- 片数多时（> 8）先按 MR / 仓分组再切，保证**一片不跨仓**——跨仓的片读不到对方的调用关系，判不出触达。

### 做什么

| 做 | 不做 |
|---|---|
| 读片内 diff，枚举逻辑点 | 不判状态、不判档位 |
| 读片内测试，录用例 / 断言 / Mock 清单 | 不写 `只验交互`、不写问题类型 |
| 既有用例的断言也录（供裁定用） | 不编号、不合并、不写 `evidence.md` |
| 给 `snippet`（5–12 行分支代码） | 不读片外文件、不猜片外触达 |
| 给片内能看到的触达候选 | 不跑脚本 |

`snippet` 是硬要求：裁定片只靠它判分支产出，没有它就得回读 diff，枚举和裁定都白做。

### 输出契约

```json
{
  "片号": "shard-01",
  "files": ["src/main/java/demo/OrderService.java"],
  "points": [
    {
      "位置": "src/main/java/demo/OrderService.java:42",
      "类型": "条件分支",
      "条件摘要": "amount > 100（新增 count > 0）",
      "来源": "修改",
      "snippet": "if (amount > 100 && count > 0) { return discount(total); }",
      "触达候选": ["OrderServiceTest#appliesDiscount"]
    }
  ],
  "cases": [
    {"用例": "OrderServiceTest#appliesDiscount", "位置": "OrderServiceTest.java:20", "变更类型": "新增", "断言数": 1}
  ],
  "assertions": [
    {"用例": "OrderServiceTest#appliesDiscount", "断言行号": "OrderServiceTest.java:30", "原文": "assertEquals(99.00, order.getAmount())", "进清单": "是", "行变更": "是", "绑定位置": ["src/main/java/demo/OrderService.java:42"]}
  ],
  "mocks": [
    {"类型": "Mock", "位置": "OrderServiceTest.java:22", "被替换方法": "OrderRepository#load", "情形类": "7"}
  ]
}
```

- `进清单`：新增或修改用例内的断言填「是」，既有用例的断言填「否」。两者都录，前者进证据表，后者只供裁定。
- `行变更`：该断言行落在本次新增或修改的测试代码行里填「是」，否则「否」。主流程用它算 `断言随动`。
- `files`：本片实际处理过的生产文件，哪怕一个逻辑点都没枚举出来也要列——主流程靠它核对「有没有漏片」。
- `cases.断言数` 记该用例的断言总条数，含不进清单的既有断言。
- `触达候选` 只写片内能确认的；跨片或没有的留空数组，由主流程补。
- 不写 `编号`、`状态`、`档位`、`问题类型`、`只验交互`。

### 合并

合并由 `assemble --mode merge` 执行（见 [scripts/README](../scripts/README.md)），主流程只需按下面几条复核：

1. **校验**：JSON 可解析、必填字段非空、`位置` 形如 `路径:行号`、`files` 覆盖本片的生产文件。不合格退回该片重跑一次；仍不合格，主流程自己读这一片（该片上限：≤ 600 行，或独占片按实际大小），并在「取数备忘」记片号与原因。
2. **去重**：按「位置 + 条件摘要」合并，和逻辑点的身份（路径 + 条件文本 + 改动后行号）一致；同一行上的两个分支（如 `catch (A | B e)`）必须保留成两条。同一身份出现在多片时，取 `断言` 与 `snippet` 更完整的一条，`触达候选` 取并集。
3. **编号**：按 [逻辑点规则](逻辑点规则.md) 的编号规则一次性分配，不看片号，只看路径排序。
4. **断言清单**只收 `进清单 = 是` 的行，`绑定位置` 换成编号。
5. **覆盖核对**：各片 `files` 的并集必须等于范围表里的生产文件集合；缺文件的片退回补跑。

## 关联（主流程，派发裁定片之前）

- **补触达**：`触达候选` 为空的点，按生产符号做一次全局测试检索（`git grep <符号> -- '*Test*'`，有索引时用 codegraph），区分「真的没有用例」和「用例在片外」；片外找到的用例要补读断言行，一起进裁定输入。
- **对替换**：把 Mock 清单对应到点，标出哪些方法被替换、替换者是谁。
- **算随动**：覆盖该点的断言里只要有一条 `行变更 = 是` → `断言随动 = 是`，否则 `否`。
- **打包**：每批 50 点，带上 `snippet` 与断言原文。

## 裁定片

### 批次

- 每批 50 点，按位置排序切；文件边界尽量不拆，但凑不满 50 点时不跨文件硬凑，单个文件超过 50 点时按 50 切批。
- 批间不共享上下文，只共享规则摘录。
- 批数随点数增长，不再往下嵌套。

### 输入

每点一份，主流程打包：

```json
{
  "编号": "ORD-01",
  "位置": "src/main/java/demo/OrderService.java:42",
  "类型": "条件分支",
  "条件摘要": "amount > 100（新增 count > 0）",
  "来源": "修改",
  "断言随动": "否",
  "被替换": {"方法": "OrderService#reserve", "替换者": "OrderServiceTest.java:22"},
  "snippet": "if (amount > 100 && count > 0) { return discount(total); }",
  "触达用例": [
    {"用例": "OrderServiceTest#appliesDiscount", "断言": [{"断言行号": "OrderServiceTest.java:30", "原文": "assertEquals(99.00, order.getAmount())", "进清单": "是"}]}
  ]
}
```

### 做什么

- 按产出对账判：列分支产出项 → 看断言读到哪一项 → 落状态。
- 每条断言给一个档位与「读到」；每个点给一条 `归属依据`（断言里的哪个标识符追到哪个产出）。
- 每个用例给一个 `只验交互`（判定口径见「Mock 判定」第 3 条）。
- `断言随动 = 否` 的点，写 `随动：` 理由。

不做：不读生产 diff、不判触达、不编号、不改清单、不跨批。

### 输出契约

```json
{
  "批号": "judge-01",
  "points": [
    {
      "编号": "ORD-01",
      "状态": "已断言",
      "断言证据": "OrderServiceTest#appliesDiscount / OrderServiceTest.java:30（读到：返回的 finalAmount）",
      "档位": [
        {"用例": "OrderServiceTest#appliesDiscount", "断言行号": "OrderServiceTest.java:30", "档位": "有效", "读到": "返回的 finalAmount"}
      ],
      "归属依据": "order.getAmount() 的数据流追到 finalAmount",
      "复核": "随动：断言读的是返回金额，与改动后的分支产出一致"
    }
  ],
  "cases": [
    {"用例": "OrderServiceTest#appliesDiscount", "只验交互": "否"}
  ]
}
```

### 合并

裁定片返回后由 `assemble --mode judge` 统一回填（见 [scripts/README](../scripts/README.md)）；主流程按下面几条复核：

1. **校验**：`状态` 在六档内；`已断言 / 断言偏弱` 必有 `断言证据`；`无法判定` 的 `复核` 必带 `缺失：`。不合格退回该批重跑一次；仍不合格，主流程自己判这一批。
2. **写回**：状态、断言证据、复核写进点行；问题类型由状态推出，主流程填；`无测试` 的断言证据由主流程按关联时的检索范围补。
3. **汇总档位**：按「用例 + 断言行号」取最高档（有效 > 形状 > 存活），只汇总 `进清单 = 是` 的断言，填断言清单的「档位」列；既有断言的档位只用于判状态，不写清单。
4. **只验交互**：同一用例在任一批被判「是」即记「是」。
5. **冲突**：同一断言在不同批给出不同档位时取最高档；同一用例的 `只验交互` 取「是」。

### 枚举片

```
你是 dt-audit 的枚举片，只处理下面这片文件，不读也不写其他文件。

## 片内文件
生产：<逐行列出路径>
测试：<逐行列出路径>
diff：<逐行列出 manifest 里的 diff_path>

## 任务
1. 逐个读 diff，按【逻辑点计入清单】枚举逻辑点；判不出结构的片段折算 1 个「不可解析」占位点。
2. 读测试文件：新增 / 修改用例的断言标「进清单 = 是」，既有用例的断言标「否」，两者都录；断言落在新增或修改行上的标「行变更 = 是」。

- 不判状态、不判档位、不编号、不写文件、不跑脚本、不读片外文件。
- 跨片触达不要猜，留空就行，主流程会补。

## 输出
<贴枚举输出契约>

## 规则摘录

```

### 裁定片

```
你是 dt-audit 的裁定片，只判状态，不枚举、不读生产 diff。

## 输入
<贴本批 JSON>

## 任务
1. 对每个点，列出这条分支的产出项，标出哪几项是决定性的。
2. 看触达用例的断言读到哪一项，按【判档顺序】落状态。
3. 每条断言给一个档位与「读到」；每个点给一条 `归属依据`；每个用例给一个 `只验交互`。
4. `断言随动 = 否` 的点，写 `随动：` 理由。
5. 只输出一个 JSON 对象，不写解释文字。

## 禁止
- 不读生产 diff、不判触达、不编号、不改清单、不跨批。
- 分支代码读得到、只是决定性判不准时，按「已断言」判，**不要**落「无法判定」；代码读不到或缺触达证据时才落「无法判定」，复核写 `缺失：<缺什么>`。

## 输出
<贴裁定输出契约>

## 规则摘录
<贴「裁定规则」>
```

模板本身不进报告，也不要贴整份 `SKILL.md`——每片重复 11k token 的规则，三片就把分片省下的上下文吃回去了。

## 规则摘录

### 枚举规则

**逻辑点计入**：条件分支（`else if` 每条一个）、非空 `else`、三元取值、`switch` 每个 `case` / `default`、提前返回的守卫条件、每个捕获类型的异常处理、参数校验失败路径、显式边界常量比较、兜底分支。

**逻辑点不计入**：短路求值、循环进出条件、条件编译、日志级别判断、裸抛异常、空值合并与默认参数、框架回调注册、测试代码内部分支、条件文本未变的纯搬移。

**测试识别**：`@Test` / `@ParameterizedTest` / `def test_` / `TEST(` 等用例入口；`assert*` / `verify` / `expect` 开头的调用算断言；`mock` / `spy` / `@MockBean` / `patch` 算 Mock 点。

### 裁定规则

**产出对账**：一条分支的产出项只从五类取——返回值、抛出的异常、写入的状态、发起的协作、产出的产物；改错它业务就错的是决定性产出项。非决定性只有这些：非空、类型、长度、裸异常、日志、耗时、时间戳、「跑通了 / 没抛异常」（名单与 `断言与Mock判据.md` 一致，改一处必须同步另一处）。

**判档顺序**（落档即停）：覆盖用例全部执行假实现 → 实现被替换（零覆盖不算，落无测试）；证据不在手上 → 无法判定；没有用例执行到 → 无测试；断言读到决定性产出项 → 已断言；有断言但只读到非决定性量 → 断言偏弱；没有任何断言读到产出项 → 未断言。

## 成本

| 规模 | 分片 | 片内上下文 | 主上下文峰值 |
|---|---|---|---|
| 1,200 改动行 / 40 点 | 枚举 3 片，不派裁定 | ~30k | ~88k |
| 3,000 改动行 / 100 点 | 枚举 6 片 + 裁定 2 批 | 枚举 ~35k，裁定 ~20k | ~85k |

不分片时 1,200 行约 119k。峰值降下来的代价是总 token 涨四到五成，所以阈值以下不要切。

## 与步骤 4–5 的衔接

- 步骤 4 用裁定片给的 `归属依据` 做纸面核对，不再回读测试方法体；没有 `归属依据` 的项才回源。
- 步骤 4 的抽样与改判全部由主流程做，不再派发。
- 分片运行要在「取数备忘」记下枚举片数、裁定批数与切分依据，步骤 5 写进 3.1 的「额外限制」。
