# 报告结构

步骤 5 使用。报告由 `render` 装配，不再手写。

**分工与裁决**：章节骨架、表头、列顺序以 [报告模板](报告模板.md) 为准；字段含义、计算口径、判定规则以本文为准。两者冲突时：骨架冲突听模板，含义冲突听本文。

**数据与判断分离**：指标、分布、定性来自 `stats.json`；3.1 的 per-MR 文件数与增删来自 `manifest.json`，抽检计数来自 `evidence.md` 的「复核」列。表格结构与行序由 `render` 决定；只有判断类文案（总评、一句话判断、Top3、问题清单、建议）来自 `narrative.json`。这样同一份证据无论跑几次，数字和结构都一致。

报告分三大章：整体结论、DT 质量评估、附录。

默认写入工作目录下的 `.dt-audit/<对象>/DT-AUDIT-REPORT.md`；用户指定路径时以用户为准。对话里只贴结论区和文件路径，不重复粘贴全文。

## 一、结论不是单一短语

整体结论陈列**命中的问题类型和命中数量**，不给合成结论、不给总分。问题类型固定为 4 类，见 [问题类型](问题类型.md)；证据缺口单列在分布表之外。

这样做的原因：多个问题会同时存在（比如断言有效但实现被替换、分支大量未断言），压成一个短语必然丢掉信息；分布表既能一眼看出主症，也不丢信息。

## 二、指标定义

| 指标 | 公式 | 用途 |
|---|---|---|
| 变更生产代码量（KLOC） | `evidence.md` 范围表里**分类为生产代码、且语言为 Java / Python** 的文件的「新增」之和 ÷ 1000 | 必报，仅陈述 |
| 全部逻辑点数 | 按 [逻辑点规则](逻辑点规则.md) 枚举、按身份去重后的逻辑点总数 | **所有逻辑点类指标的唯一分母** |
| 可判定逻辑点数 | 排除「无法判定」后的逻辑点数 | 只作证据完整度的分子 |
| 断言覆盖率 | （已断言 + 断言偏弱）÷ **全部逻辑点数** | 覆盖口径 |
| 有效断言率 | 已断言 ÷ **全部逻辑点数** | 有效性口径 |
| 实现被替换率 | 实现被替换的逻辑点数 ÷ **全部逻辑点数** | 问题分布与维度总评 |
| 证据完整度 | 可判定逻辑点数 ÷ 全部逻辑点数 | 置信度 |
| 新增 DT 数 | 本对象新增的测试方法数（新增用例数） | 1.1 与密度计算 |
| 新增 DT 密度 | 新增 DT 数 ÷ 变更生产代码 KLOC；KLOC 为 0 时写「不适用」 | 1.1 陈述 |

> **别把两个「有效」搞混**：`有效断言率` 按**逻辑点**计（分母是全部逻辑点）；`有效断言条数` 按**断言行**计（只统计新增/修改用例内的断言）。前者是覆盖口径，后者是计数。

**分母只有一个**：逻辑点类的比率一律除以「全部逻辑点数」，包括读不到的那部分。核心要看护的是业务代码里所有需要断言的分支，看不见的那些不能从分母里悄悄消失，否则比率会虚高。读不到多少由证据完整度单独说明。

**由此必然成立的一条链**：`有效断言率 ≤ 断言覆盖率 ≤ 证据完整度`。三者同分母，分子依次扩大。`stats` 会校验它，违反即报错。

**KLOC 按范围表逐文件累加**：范围表已按逻辑点身份去重过，同一文件只出现一次，所以这里不再去重；不含删除行、不含测试文件、不含 C / C++、不含被排除的分类。`stats` 会用范围表反算并与「变更生产代码行数」对账，对不上给 warning。它只用于 1.1 陈述与密度计算，不参与任何判定。

**一条断言的身份是「用例 + 断言行号」**：同一身份在一个对象里只计一次，档位取它在所有绑定逻辑点上的**最高档**（有效 > 形状 > 存活）。这样无论把它写成一行绑多个逻辑点、还是拆成多行，有效断言条数都相同。

档位怎么判见 [断言与 Mock 判据](断言与Mock判据.md) 的「产出对账」：只看分支代码列出产出项、标出决定性，再看断言读到哪一项。断言质量只判「产出有没有被读到」，不判「断言够不够强」。

**覆盖与有效性两个口径的分工**：断言覆盖率是**覆盖口径**——只要有一条断言在看就计入，断言偏弱也算；有效断言率是**有效性口径**——只算「已断言」（断言读到这条分支的决定性产出项）。两者并列呈现，不做合成，也不互相替代：前者说明覆盖到哪，后者说明真能拦住多少。

**C / C++**：不枚举逻辑点，只给文件级结论，不进任何分母，也不进 KLOC；受限数量按**文件数**统计，报告里写「C/C++ 受限文件 N 个」。

**判定水位**（数值以这里为准；3.4.7 是给报告读者看的副本，改动必须两处同步）：

- 证据完整度下限 **0.60**，低于它按「证据缺口」提示；分档为 ≥**0.90**「完整」、≥**0.60**「较完整」、其余「不完整」。
- 维度总评的档位来源固定为：**2.2 用实现被替换率**、**2.3 用断言覆盖率**（良好 **0.70**、低 **0.40**）；**2.1 不判高/中/低**，只陈述断言条数与主要问题——有效断言率没有水位，拿它判档会与 1.2 的定性混淆。
- 实现被替换率是**越高越差**的指标：≥ **0.15** 为高、等于 0（且可判定 > 0）为低、其余为中。仅 diff 档读不到未被改动的 Mock，这个数可能偏低，在 2.2 总评与 3.1 里说明即可，不改写数值。
- 有效断言率不设水位，只陈述数值，仅用于 1.2 的定性判定。
- 新增 DT 密度参考带 **5–30** 个/KLOC，仅用于措辞，不参与判定。

**断言统计范围（唯一口径）**：

- **状态判定**可以使用既有用例的断言：既有测试也是本对象自己的测试，能看到就记为已断言。
- **有效断言条数只统计新增或修改用例内的断言**；既有用例的断言不进这个计数。
- 不冻结就不可比：同一套用例在三次运行里分别被数成 89、77、111 条断言，有效断言率从 74.2% 漂到 80.5% 再漂到 85.6%，看起来像质量在变，其实只是分母在变。问题类型、测试框架识别与报告 2.1 一律引用本节，不另写。

断言覆盖率把「断言偏弱」算作已覆盖，因为它至少有一条断言在看。**不计入断言覆盖率的逻辑点 = 无测试 + 实现被替换 + 未断言**，三者之和应当等于可判定逻辑点数减去已断言与断言偏弱，报告里要能对上。

## 三、章节结构

章节、表头、顺序见 [报告模板](报告模板.md)，不在此重复。

报告顶部写一行「与默认口径的偏差声明」：检测对象是 **AR 或 MR** 时必写，写明对象类型；跳过了某一步时追加写清跳过了哪一步、为什么。

## 四、各章规则

### 1.1 基本信息

按对象类型二选一，不混用：

- **SR / AR**：对象类型、标识、原始输入、变更的生产代码（KLOC）、新增 DT 数、新增 DT 密度（个/KLOC）、涉及代码仓、证据来源分布，另附**关联 MR 清单**（地址、标题、作者）。
- **MR**：对象类型、地址、标题、作者、原始输入、涉及代码仓、变更的生产代码（KLOC）、新增 DT 数、新增 DT 密度（个/KLOC）、证据来源分布。

「变更的生产代码」按 §二 的 KLOC 口径取，数据取 `manifest.json` 的 `additions`。证据来源按**单元数**统计：含本地仓 / 仅 diff / 无法获取。

### 1.2 结论

第一行给 **DT 质量定性**，按下面顺序判定，命中即停：

| 步 | 条件 | 结论 |
|---|---|---|
| 前置 | 全部变更单元均为「无法获取」 | 证据不足（不产出质量结论） |
| R0 | 全部逻辑点 = 0 | 合格 |
| R1 | 新增 + 修改用例 = 0 且 证据完整度 < 60% | 待改进 |
| R2 | 证据完整度 < 60% | 证据不足 |
| R3 | 有效断言率 < 50% 或 **计入的**测试退化 > 2 条 | 待改进 |
| R4 | 有效断言率 ≥ 75% 且 全部逻辑点 ≥ 8 且 计入的测试退化 = 0 | 优秀 |
| R5 | 其余 | 合格 |

定性的三个取向：

- **优秀要少**：三个条件同时满足才给，任一条差一点就落合格。
- **待改进看可见的问题**：R1 把「没带测试又看不清覆盖」算成待改进而不是证据不足——提交代码该带用例，看不清是提交方的责任。
- **证据不足只做兜底**：只有带了测试、却确实读不到足够内容时才用，不拿它当「不想判」的出口。

R4 里不再单列「证据完整度」条件：有效断言率的分母是全部逻辑点，有效断言率 ≥ 75% 已经意味着完整度 ≥ 75%。

「测试退化」只统计证据表信号段里「计入 = 是」的条数——即三段证据齐全、确实让本次变更的分支失去防护的那些。「计入 = 否」的只作提示，不进定性。1–2 条不足以判待改进，但会挡住优秀。

依据写一行，说清命中哪条规则、卡在哪个条件，取自 `stats.json` 的「定性」，不重新推导。

其后四块内容按顺序：问题分布表、证据缺口提示、三个率、一句话判断。**证据完整度低于下限时第（4）块整段省略**——这是既定规则，`render` 自动处理，`narrative.json` 里仍要写一句话判断，只是不会被渲染。

占比的分母按单位取：逻辑点类用**全部逻辑点数**（与三个率同分母），用例类用**新增 + 修改用例数**（既有用例不进分母），信号条不填占比，写「—」。

分布表覆盖 4 类（场景覆盖不足、断言质量低、测试对象偏移、测试退化）与严重度升级理由；证据缺口单列在提示行，不进分布表，也不计入「其余 N 类未命中」。表下写「其余 N 类未命中」，N = 4 − 命中类数。

证据缺口的提示行分三段：无法判定的逻辑点数、无法获取的 MR 数、证据完整度及其档位。

三个率一行陈列，不做合成、不排序、不加权：断言覆盖率、有效断言率、实现被替换率。

**零逻辑点与零可判定的处理（唯一口径）**：

- 逻辑点总数为 0：定性写「合格」；问题分布位置写「无可枚举分支」；证据缺口写「证据完整度：不适用（无逻辑点）」；三个率写「不适用」；2.1 / 2.2 / 2.3 总评写「无行为分支，不评估」；跳过步骤 4，原因记入 3.1。若本次存在 C / C++ 受限文件，必须同时写「C/C++ 受限文件 N 个」，且**不得**写「本次改动未引入行为分支」。
- 逻辑点总数大于 0 但可判定为 0：保留 3.3 矩阵，不写「无可枚举分支」；**三个率照常给数值**（同分母，此时为 0.0%），不再抹成「不适用」；2.1 / 2.2 / 2.3 总评写「全部无法判定，不评估」；定性按 R1 / R2 判，依据里写明是哪一条。读者看到 0.0% 时要能从紧邻的证据缺口行看出「不是没测，是看不到」。

### 1.3 主要缺口（Top 3）

按影响档降序取 3 条，每条一行：位置 + 问题 + 影响档 + 建议动作。不足 3 条时按实际条数列出，不留空位。影响档判据见「影响排序」。

### 2.x 维度章节

三个维度用同一个四段式：

1. **一句话总评**，不超过 40 字，说清整体水平和一个最突出的问题。水平按 §二 的判定水位判断，不写分数。2.2 用实现被替换率判水平；实现被替换率为「无法评估」时不判水平，直接写无法评估的原因。
2. **数据块**，每个维度各自固定，见下表「必含内容」。
3. **问题清单**，严重度由高到低。每条含：文件行号、现象、证据原文、后果、问题类型与子类。
4. **本维度补测建议**，2–3 条，每条带落点（`文件:行号` 或逻辑点编号）。

| 维度 | 必含内容 | 覆盖的问题类型 |
|---|---|---|
| 2.1 DT 断言质量 | 断言总数与有效断言条数、无断言用例、只用交互验证的用例、测试退化（计入条数与提示条数分开）、断言抽检结果（归属成立 / 归属不符） | 断言质量低、测试退化 |
| 2.2 Mock 质量 | Mock 情形分布（提示信息）、实现被替换率、实现被替换的逻辑点清单、契约漂移 | 测试对象偏移 |
| 2.3 分支覆盖 | 断言覆盖率、有效断言率、未覆盖清单（只列无测试与分支未断言，按影响档排序，实现被替换交叉引用 2.2）、异常路径与边界细分；测试脱靶命中时另起一行 | 场景覆盖不足 |

**去重规则**：同一个问题只在根因所在的维度展开，其他维度用逻辑点编号交叉引用，不复述。例如探针替换导致 9 个逻辑点未断言，根因在 2.2，2.3 只列编号并注明「见 2.2」。

### 影响排序（只用于排序，不计入任何数字）

1.3 的 Top 3 与 2.3 的未覆盖清单按**影响档**降序排列。影响档看这条分支控制什么，不看问题类型：

| 影响档 | 判据 |
|---|---|
| 高 | 安全 / 权限 / 鉴权、金额 / 计费 / 配额、数据写入或删除、状态迁移、对外契约（返回结构、错误码） |
| 中 | 业务计算、数据转换、字段默认值、缓存与降级 |
| 低 | 日志、文案、埋点、调试开关、纯展示 |

只在列进这两处的条目上判一次，不写进证据表，不参与任何计数。

### 3.1 分析范围与证据来源

按 MR 逐行列出的来源表，另加八条说明：取数、去重、证据完整度、无法判定清单、无法获取清单、仅 diff 的 MR、受限语言、关联能力（索引级 / 静态级 / 文件级）。没有条目时写「无」。

限制说明必须包含两条固定内容：**未运行测试，用例当前是否通过未知**；**结论只覆盖实现自证能力**。

### 3.4 枚举释义

3.4 的固定内容在 [3.4 枚举释义](3.4-枚举释义.md)。`render` 在装配时用该文件的正文（**不含文件开头的维护注释**，从 `#### 3.4.1` 开始）替换模板里的 `{{include: 3.4-枚举释义}}`，逐字照搬；`render --check` 会确认它确实出现在生成的报告里。

## 五、固定声明

报告的 3.1 节必须原样包含 [报告模板](报告模板.md) 里的固定声明句，不改写。
