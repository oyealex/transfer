# 测试框架识别

步骤 2 使用。目标：从测试文件里稳定识别用例、断言、Mock，以及**被测试替换掉的真实实现**。

## Java

| 项 | 识别特征 |
|---|---|
| 用例 | 方法上的 `@Test`、`@ParameterizedTest`、`@RepeatedTest`、`@TestFactory`；TestNG `@Test` |
| 断言 | JUnit `assertEquals` / `assertTrue` / `assertThrows` / `assertAll`；AssertJ `assertThat(...)`；Hamcrest `assertThat(x, is(...))` |
| Mock | Mockito `mock()` / `@Mock` / `@InjectMocks` / `when(...).thenReturn` / `verify(...)` / `InOrder`；EasyMock `expect(...)`；PowerMock |
| 替换方式 | `@Override` 探针子类、`spy()` 后 `doReturn` 掉内部方法、`MockedStatic` 替换静态业务入口、`mockConstruction` |

## Python

| 项 | 识别特征 |
|---|---|
| 用例 | 模块级或类内 `def test_*`；`unittest.TestCase` 子类的 `test_*` 方法 |
| 断言 | 裸 `assert`；`self.assertEqual` / `assertTrue` / `assertRaises` / `assertIn`；`pytest.raises` / `pytest.approx` / `pytest.warns` |
| Mock | `unittest.mock.patch` / `Mock` / `MagicMock` / `patch.object`；pytest-mock `mocker.patch`；`responses` / `requests_mock` / `respx` |
| 替换方式 | 对被审计类的内部方法 `patch.object`、对业务函数的 `patch`、`monkeypatch.setattr` 替换生产模块函数 |

## C / C++

C / C++ 不做用例、断言、Mock 盘点，也不枚举逻辑点（见 [逻辑点规则](逻辑点规则.md) 的「与语言能力的对应」）。需要用到的只有两件事：

- **判测试文件**：引用 CMocka / Unity / GoogleTest / Catch2 / doctest / Boost.Test / CppUTest / CppUnit 的头文件或宏，判据见 [范围规则](范围规则.md)。
- **测试退化的「新增禁用」与「断言被注释」信号**：跳过宏与断言宏的完整清单见 [问题类型](问题类型.md) 的六条信号表，本节不再单列，避免两处枚举漂移。

**C / C++ 的测试方法不计入「新增 DT 数」**：它们在报告里只体现在 3.1 的受限清单与 3.2 的文件数，不进密度计算。

## 自定义断言与封装

命中以下任一，视为断言调用：

- 方法名以 `assert`、`verify`、`expect`、`check`、`should` 开头
- 项目自带的辅助方法，如 `assertOrderValid(...)`、`verifyResponse(...)`

这类封装的断言档位由步骤 3 判，不要因为「不认识这个框架」就降级成无断言。

**`verify(...)` 与 `expect(...)` 就是断言**：它们既是 Mock 框架的交互验证调用，也是一条断言。处理方式固定为——

- 在「断言清单」记一条，原文录进清单
- 档位在步骤 3 按产出对账判，不预设：分支产出是「是否发起这次协作」时，它就是有效档
- 只有断言落在假实现交互上、而被测分支的产出是本对象自己算出的值或状态时，才在「Mock 清单」按情形类 6 记一行

若把交互验证一律记成情形 6、或一律按存活档算，交互驱动写法的用例集会被算成「断言很多但有效断言率极低」，把定性拉到待改进——那是判据误用，不是用例的问题。

## 计数口径

| 口径 | 定义 |
|---|---|
| 用例数 | 测试方法数，一个方法算一个；参数化方法按方法计，不展开 |
| 用例标识 | `<类名>#<方法名>`，无类时用 `<文件名>#<方法名>`。同一对象内必须唯一 |
| 断言数 | 断言调用条数，一行一条；参数化展开、`assertAll` 内部的分支不拆分 |
| 断言标识 | `<用例标识>@<断言行号>`，用于去重与绑定多个逻辑点 |

新增 DT 数、新增 DT 密度、断言统计范围见 [报告结构](报告结构.md) §二。新增 DT 密度是事实陈述，不参与判定：既有测试已充分覆盖时新增 DT 为 0 也合理。
