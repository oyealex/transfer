# 测试框架识别

步骤 2 使用。目标：从测试文件里稳定识别用例、参数化、断言、Mock，以及**被测试替换掉的真实实现**。

## Java

| 项 | 识别特征 |
|---|---|
| 用例 | 方法上的 `@Test`、`@ParameterizedTest`、`@RepeatedTest`、`@TestFactory`；TestNG `@Test` |
| 参数化 | `@ParameterizedTest` 加 `@ValueSource` / `@CsvSource` / `@MethodSource` / `@EnumSource` |
| 断言 | JUnit `assertEquals` / `assertTrue` / `assertThrows` / `assertAll`；AssertJ `assertThat(...)`；Hamcrest `assertThat(x, is(...))` |
| Mock | Mockito `mock()` / `@Mock` / `@InjectMocks` / `when(...).thenReturn` / `verify(...)` / `InOrder`；EasyMock `expect(...)`；PowerMock |
| 被替换实现 | `@Override` 探针子类、`spy()` 后 `doReturn` 掉内部方法、`MockedStatic` 替换静态业务入口、`mockConstruction` |

## Python

| 项 | 识别特征 |
|---|---|
| 用例 | 模块级或类内 `def test_*`；`unittest.TestCase` 子类的 `test_*` 方法 |
| 参数化 | `@pytest.mark.parametrize`，展开组数 = 参数列表长度；叠加时取笛卡尔积 |
| 断言 | 裸 `assert`；`self.assertEqual` / `assertTrue` / `assertRaises` / `assertIn`；`pytest.raises` / `pytest.approx` / `pytest.warns` |
| Mock | `unittest.mock.patch` / `Mock` / `MagicMock` / `patch.object`；pytest-mock `mocker.patch`；`responses` / `requests_mock` / `respx` |
| 被替换实现 | 对被审计类的内部方法 `patch.object`、对业务函数的 `patch`、`monkeypatch.setattr` 替换生产模块函数 |

## C

| 项 | 识别特征 |
|---|---|
| 用例 | Unity `RUN_TEST` / `void test_*(void)` 约定；CMocka `cmocka_unit_test` / `cmocka_unit_test_setup`；CppUTest `TEST(...)` |
| 参数化 | C 生态罕见；通常用数组加循环手写，识别为「手写参数化」，组数不计 |
| 断言 | Unity `TEST_ASSERT_*`；CMocka `assert_*` / `assert_int_equal`；CppUTest `CHECK_*` / `STRCMP_*` |
| Mock | CMocka `will_return` / `expect_*`；FFF `FFF_FAKE_*` / `FAKE_VOID_FUNC` |
| 被替换实现 | 链接期替换、弱符号覆盖、手写桩替换生产函数 |

## C++

| 项 | 识别特征 |
|---|---|
| 用例 | GoogleTest `TEST(` / `TEST_F(` / `TEST_P(`；Catch2、doctest `TEST_CASE(`；Boost.Test `BOOST_AUTO_TEST_CASE`；CppUnit `CPPUNIT_TEST` |
| 参数化 | GoogleTest `TEST_P` 加 `INSTANTIATE_TEST_SUITE_P`；Catch2 `GENERATE(...)`；doctest `TEST_CASE_TEMPLATE` |
| 断言 | GoogleTest `EXPECT_*` / `ASSERT_*`；Catch2、doctest `REQUIRE*` / `CHECK*`；Boost.Test `BOOST_CHECK_*`；CppUnit `CPPUNIT_ASSERT*` |
| Mock | GoogleMock `MOCK_METHOD` / `EXPECT_CALL`；FakeIt `FAKE_METHOD`；Trompeloeil `REQUIRE_CALL`；HippoMocks `MOCK_BASE_CLASS` |
| 被替换实现 | 链接期替换、模板注入桩、函数指针注入 |

## C / C++ 的链接期替换

这些不是 Mock 框架，但功能等价，识别到就记为「替换真实实现」，不判可达性：

| 手法 | 识别特征 |
|---|---|
| 链接期包装 | 构建文件里的 `-Wl,--wrap=<符号>` |
| 弱符号 | `__attribute__((weak))` 加另一处强定义 |
| 手写桩 | `stub_*.c` / `fake_*.c`，或构建文件里链接顺序替换 |
| 函数指针注入 | 结构体成员赋值假实现，如 `ops->read = &fake_read` |
| 头文件替换 | 测试目录里同名头文件覆盖真实头文件 |

## 自定义断言与封装

命中以下任一，视为断言调用：

- 方法名以 `assert`、`verify`、`expect`、`check`、`should` 开头
- 项目自带的辅助方法，如 `assertOrderValid(...)`、`verifyResponse(...)`

这类封装的判别力档位由步骤 3 判，不要因为「不认识这个框架」就降级成无断言。

## 无框架的手写测试

C / C++ 常见：自己写 `main` 加 `if (!cond) return 1;`。

识别特征：文件不含任何已知测试框架的头或宏，但存在 `main` 与比较语句。

处理：标「自定义测试入口」，能力降到「存在性加文本级断言扫描」，不计入用例数。报告里注明。

## C / C++ 的关联线索

用于把测试文件与生产文件连起来（文件级关联）：

- CMake：`add_executable`、`target_sources`、`target_link_libraries`、`add_test`、`gtest_discover_tests`
- Makefile：测试目标的源文件列表
- meson：`test()`、`executable()`

构建文件本身不进分母，只作线索。

## 计数口径

| 口径 | 定义 |
|---|---|
| 用例数 | 测试方法数，一个方法算一个 |
| 参数化展开组数 | `@ParameterizedTest` / `parametrize` / `TEST_P` 的实际展开组数，只作附加数字 |
| 新增 DT 数 | 本对象**新增**的测试方法数，不含修改、不含既有 |
| 新增 DT 密度 | 新增 DT 数 ÷ 变更生产代码千行 |

**断言统计范围（冻结）**：只统计本对象新增用例与修改用例里新增或修改的断言行；既有用例、未改动的断言行不计入断言分母。同一行内多条断言按条计。报告里必须写出「X 个用例 / Y 条断言」的算式。

这条不冻结，判别性占比就不可比：同一套用例在三次运行里分别被数成 89、77、111 条断言，判别性从 74.2% 漂到 80.5% 再漂到 85.6%，看起来像质量在变，其实只是分母在变。

新增 DT 密度是事实陈述，不参与判定。既有测试已充分覆盖时新增 DT 为 0 也合理，两者不冲突。
