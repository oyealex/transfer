# 逻辑点规则

步骤 2、3 使用。

逻辑点是本 Skill 的原子计量单位：**检测对象引入或修改的一条行为分支**。

## 计入清单

| 类型 | 形态 | 说明 |
|---|---|---|
| 条件分支 | `if (cond) {…}` | `else if` 链每条一个 |
| 否则分支 | `else {…}` | `else` 内非空时单独计一个 |
| 三元取值 | `cond ? a : b` | |
| 多路选择 | `switch` 的每个 `case` / `default` | |
| 提前返回 | 提前 `return` / `continue` / `break` 的守卫条件 | |
| 异常处理 | `catch` / `except` / 错误处理块 | 每个捕获类型一个（`catch (A \| B e)` 计 2 个） |
| 参数校验 | 参数校验失败路径（抛错或返回错误码） | |
| 边界比较 | 显式边界常量比较（`>= MAX`、`< 0`、`== 0`、`len > N`） | 作为 `if` 条件出现的不重复计；出现在守卫返回、三元、校验式里的单独计 |
| 兜底分支 | 显式降级分支（默认值、兜底逻辑、缓存未命中分支） | |

## 不可解析的占位点

判不出结构的片段（宏、模板、超长表达式、生成代码式写法）**不产出行为分支**，但为了让分母反映「看不到的部分」，按**每个片段折算 1 个逻辑点**：

- 位置取片段起始行
- 条件摘要写不可解析的原因（如「宏展开，无法静态判定分支数」）
- 「问题」记「不确定」，「原因」记「结构不可解析」，说明写 `证据不足：结构不可解析（宏 / 模板 / 超长表达式）`

这个占位点不是行为分支，只用于让「不确定」占住它那一份分母，避免有效占比被高估。整个文件都判不出时，按文件汇总为一个占位点，并在「取数备忘」注明覆盖的文件数。

## 不计入清单

| 形态 | 理由 |
|---|---|
| `&&` / `\|\|` 短路求值 | 除非独立成一条语句，否则属于表达式细节，噪声大 |
| 循环进入 / 退出条件 | 属于遍历机制，不代表业务分支 |
| 预处理条件编译 | 构建期配置，不是运行时行为 |
| 日志级别判断 | 无业务语义 |
| 裸抛出异常 | 守卫它的条件分支已经计过 |
| 空值合并、默认参数展开 | 语言机制 |
| 框架回调注册 | 无分支语义 |
| 测试代码内部的分支 | 只统计生产代码 |
| 纯搬移、提取，条件文本未变的分支 | 语义与搬移前一致，不产生新的验证需求 |

「条件文本未变」指真正的纯搬移。条件本身被改过时，哪怕结构没变，也算一个「修改」来源的逻辑点，不拆成删除加新增。

## 语言示例

Java，5 个逻辑点：

```java
public List<Item> pick(List<Item> items, boolean flag) {
    if (items.isEmpty()) {                    // 提前返回
        return Collections.emptyList();
    }
    for (Item i : items) {                    // 不计
        if (i.isValid()) { ... }              // 条件分支
    }
    try { ... }
    catch (IOException e) { ... }             // 异常处理
    catch (RuntimeException e) { ... }        // 异常处理
    int n = flag ? 1 : 0;                     // 三元
    return ...;
}
```

其余语言只列形态差异，计数规则相同：

| 语言 | 形态 | 计数 |
|---|---|---|
| Python | `if not payload: raise`、`except KeyError` | 提前返回 1、异常处理 1 |

循环进入/退出条件与遍历语句本身不计。C / C++ 不抽取逻辑点，本表不列。

## 字段

| 字段 | 说明 |
|---|---|
| 编号 | 「模块缩写-序号」，见下节 |
| 位置 | 条件所在行，取改动后的行号，写「文件:行号」 |
| 条件摘要 | 条件原文，去多余空白；来源为「修改」时在括号里写增删了哪个子句 |
| 来源 | 新增 / 修改 |
| 覆盖用例 | 能执行到该分支的用例，写 `用例名(文件:行号)`，多个用顿号分隔；确认没有的留空 |
| 问题 | 有效 / 未覆盖 / 无效 / 低价值 / 不确定 |
| 原因 | 见 [问题分类与判定](问题分类.md) 的枚举；有效留空 |
| 说明 | 一句话：现象 + 读到或没读到什么；方向原因必须写清被改动的 `文件:行号` |

「类型」（条件分支、多路选择等）只用于回答「算不算一条分支」，不进证据表，报告也不再记录。

## 编号规则

**模块缩写**：取该文件所在最深层目录名，去掉非字母字符后取前 3 个字符并大写；目录名为空或不足 3 个字母时，取文件名（去扩展名）前 3 个字符大写；仍与已有缩写冲突时，后出现的依次追加 `2`、`3`。缩写可能只有 1–2 个字符（如 `X.java` → `X`），编号形如 `X-01`。

**序号**：两位，超过 99 时自然进位为三位。按文件路径排序后顺序编号，稳定可复现。

**分片时由主流程统一分配**：各片按 [分片协议](分片协议.md) 的输出契约产出候选行（位置、条件摘要、来源与 `触达候选`），不写编号；合并去重后由主流程一次性编号。否则各片独立从 01 起编，跨片必然撞号。

编号只是排序与交叉引用的锚点，不是分类，不需要在报告里额外解释。

## 枚举冻结

按「计入清单」逐条对照，不加不减，也不按「有没有执行」或「值不值得测」增减。**被替换方法体内的分支按同一规则展开**：不能因为「反正没执行」就少计，也不能因为「看得更细」就把同一条分支拆成几个——同一个方法在两次运行里必须数出同样的分支数。逻辑点总数在三次运行里从 57 漂到 62 再漂到 65，主因就是这一条没有冻结。

枚举结果一次写入 `evidence.md` 的逻辑点证据段，后续步骤只引用编号，不重新计数。

## 条件变化的覆盖要求

来源为「修改」的逻辑点，必须在「条件摘要」的括号里写清增删了哪个子句，并按下面的规则核对用例：

| 变化 | 必须有的用例 | 找不到时 |
|---|---|---|
| 删除了子句 A | 一条「A 为假」的用例 | 没有用例执行到该分支 → 未覆盖（无对应用例）；执行到了但缺这一支 → 无效（断言没看这个点的结果） |
| 新增了子句 A | 一条「A 为真」的用例 | 同上 |

**不能因为其他子句有用例覆盖就算有效。** 典型反例：条件从 `enabled && invalid` 改成 `invalid`，四个 400 用例都是 `enabled=true`，唯一一个 `enabled=false` 的用例，其请求体又合法——这条逻辑点仍然是无效，因为「删掉 enabled 前置」这件事没有任何用例验证。

## 抽取流程

逐个生产改动片段：

1. 只取新增侧与成对修改侧的代码。
2. 按语法结构提取条件，不要按行号硬匹配。
3. 条件被修改但结构未变 → 来源记「修改」，整条算一个逻辑点。
4. 片段里判不出结构的 → 按「不可解析的占位点」折算 1 个逻辑点。

## 与语言能力的对应

Java / Python（能力档「完整」）：符号级抽取 + 逐点判定。

C / C++（能力档「受限」）：**不抽取逻辑点**，只统计文件数与语言分类。报告 1.1 只记「C/C++ 受限文件数」，不做用例关联、不进占比分母、也不进逻辑点证据表。
