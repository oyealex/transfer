# 范围规则

步骤 1 使用。目标是让**每个变更文件**都有分类结论，且排除项可解释、可复核。

## 语言白名单

只审计以下扩展名，其余一律排除：

| 语言 | 扩展名 |
|---|---|
| Java | `.java` |
| Python | `.py` |
| C | `.c`、`.h` |
| C++ | `.cc`、`.cpp`、`.cxx`、`.hpp`、`.hh`、`.hxx` |

`.h` 归 C 还是 C++，看同目录实现的源码语言；判不出时按 C++ 处理并标注。头文件与内联模板里的逻辑**计入生产代码**。

`.py` 先判测试、再判生产，两者都不命中才排除（构建脚本、运维脚本不属于审计范围）。

## 文件分类

| 分类 | 判据 | 处理 |
|---|---|---|
| 测试代码 | 见下节 | 进测试证据池 |
| 生产代码 | 白名单扩展名且非测试 | 进分母 |
| 生成代码 | 见下节 | 排除，列清单 |
| 配置 / 资源 | `.yaml` `.yml` `.json` `.xml` `.properties` `.ini` `.conf` `.toml` `.env` 等 | 排除 |
| 文档 | `.md` `.txt` `.adoc` `.rst` 等 | 排除 |
| 脚本 | `.sh` `.bat` `.ps1` `.cmd` | 排除 |
| 二进制 / 子模块 | 二进制标志或子模块标志为真 | 排除 |
| 构建文件 | `CMakeLists.txt`、`Makefile`、`pom.xml`、`build.gradle*`、`setup.py`、`pyproject.toml`、`meson.build` | 不计入分母，列入排除项 |
| 其他语言 | 不在白名单 | 排除并注明语言 |

## 测试文件识别

路径约定与内容特征**双判据**，命中其一即视为测试文件；两者冲突时取并集并标注来源。

路径约定：

- Java：`src/test/`、`src/it/`、`*Test.java`、`*Tests.java`、`*IT.java`、`*Spec.java`
- Python：`tests/`、`test/`、`test_*.py`、`*_test.py`、`conftest.py`
- C / C++：`test/`、`tests/`、`unittest/`、`*_test.c`、`*_test.cpp`、`*Test.cpp`、`*_unittest.cc`

内容特征：

- Java：`@Test`、`@ParameterizedTest`、`@TestFactory`、`extends TestCase`
- Python：`def test_`、`class Test`、`import pytest`、`import unittest`、`@pytest.mark`
- C / C++：引用 CMocka / Unity / GoogleTest / Catch2 / doctest / Boost.Test / CppUTest / CppUnit 的头文件，或出现对应测试宏

## 生成代码识别

命中任一即排除：

- 文件头含 `@Generated`、`DO NOT EDIT`、`Code generated by`、`此文件由…自动生成`
- 路径含 `/generated/`、`/gen/`、`/build/`、`/target/`、`/out/`
- 文件名模式：`*.pb.h`、`*.pb.cc`、`*_generated.*`、`*Mapper.xml`、`*.g.cs`

Lombok 一类注解处理器不落盘生成文件，不涉及本规则。

## 单元分类

变更单元（MR 或提交）的分类由文件分类聚合得出：全为测试 → 纯测试单元，全为生产 → 纯实现，两类都有 → 混合，全为配置文档或生成代码 → 整体排除。提交批次没有 MR 概念，按单个提交做同样聚合。

纯测试单元在 SR 粒度是合法的：实现 MR 不写测试、另一个 MR 补，在 SR 层面成立。

## 输出

纳入的文件逐个进证据表「范围」段与报告 3.2，一行一个：

```
路径 | 分类 | 来源档位 | 新增 | 删除
```

排除的文件**只在证据表「变更概览」里按分类汇总数量**（如 `排除：配置 → 8`），报告 3.2 的构成表直接引用。不逐个列路径，也不逐个写理由：排除项只用来知道有多少东西没进审计范围，不参与任何判定。
