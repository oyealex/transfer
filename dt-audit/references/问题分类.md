# 问题分类与判定

步骤 2、3、5 使用。判定的唯一依据是**逻辑点与用例的关联**：先看用例能不能跑到这条分支，再看它的断言有没有核对这条分支的结果。

## 关联

关联回答「哪些用例会执行到这条分支」。只追一层入口（controller → service），按入参、枚举值、构造器判可达，不要求证明执行。

| 步 | 做法 | 证据 |
|---|---|---|
| 1 | 从用例主体找到包含该分支的方法，只经一层入口 | 测试里的调用行号 |
| 2 | 看入参能否走到这条分支 | 入参取值 + 条件原文 |
| 3 | 写一句「这条分支的结果」，再看断言有没有核对它 | 断言行号 |

四条边界：

1. **来源为「修改」的点**：用例必须落到改动后的条件上；只命中旧条件的不算。
2. **被测对象被替换**：调用路径指向了该方法、真实实现没执行，仍算关联，判「未核对」，原因记「只测假实现」——否则「看着测了其实没测」会被记成「未覆盖」。
3. **参数化**：按参数组判可达，覆盖仍记在该测试方法名下。
4. **间接调用**：追一层；超过一层、反射、动态分派、随机输入 → 判不清。

判不清的格不写成「未核对」，整行都判不清时才落「不确定」。

## 格：四个取值

对每个（逻辑点，覆盖用例）判一格：

| 格 | 判据 | 例子 |
|---|---|---|
| **核对到** | 断言引用了这条分支的结果并判定其内容 | `assertEquals(90, result)`、`assertThrows(IAE.class)`、`assertThat(o.getStatus()).isEqualTo(PAID)`、`verify(repo).save(argThat(...))` |
| **只到形态** | 引用了结果，但只判非空、大小、类型、长度、不抛异常 | `assertNotNull(result)`、`assertTrue(list.size() > 0)` |
| **未核对** | 断言没引用这条分支的结果 | 断言别的对象、只 `verify(mock)` 假实现被调用、方法内无断言 |
| **判不清** | 引用的值来源不明 | 二次组装对象、跨方法计算的值 |

两条特例：

- **协作本身是结果**时（这条分支的结果就是「必须调用审计」），`verify` 带参数校验记「核对到」。
- **断言镜像实现**（在测试里重算生产公式）按「未核对」计，原因记「断言镜像实现」——它永远跟着错。

「这条分支的结果」指：返回值、抛出的异常、写入的状态、发起的协作、产出的产物。写不出来的记「判不清」，不要猜。

## 点：取最好

一个点被多条用例覆盖时，按下面的优先级取最好的一格：

```
核对到  >  只到形态  >  判不清  >  未核对
```

「判不清」排在「未核对」之前：判不清说明可能没问题，按疑罪从无处理。

| 最好的格 | 分类 |
|---|---|
| 核对到 | **有效** |
| 只到形态 | **低价值** |
| 判不清 | **不确定** |
| 未核对（全部） | **无效** |
| 没有覆盖用例 | **未覆盖**（查证过没有用例可达）/ **不确定**（判不出可达） |

分类只有这一层，不再有「状态」或第二层类型。

## 原因枚举

原因只解释「为什么归这一类」，不计数、不进分布表。**加粗的是方向原因**，表示「这次改坏的」。

| 分类 | 原因 | 判据 |
|---|---|---|
| 未覆盖 | 无对应用例 | 这条分支没有任何用例能到达；新增分支从来没人测 |
| | **原有用例不再执行** | 本次删了测试文件、加了禁用、清空方法体，或削弱输入到不了 |
| 无效 | 无断言 | 用例到达了，但方法体内没有断言 |
| | 断言没看这个点的结果 | 断言在读别的对象、别的分支 |
| | 只验交互 | 只断言假实现被调用，而这条分支的结果不是这次协作 |
| | 只测假实现 | 覆盖它的用例全部走探针 / 桩 / Mock，真实实现没被执行 |
| | 断言镜像实现 | 在测试里重算生产公式 |
| | **断言被注释** | 本次把原本读这条结果的断言注释掉了 |
| 低价值 | 只判形态 | 只核对非空、大小、类型、长度、集合形状、不抛异常 |
| | **断言被弱化** | 同一断言行本次由精确改宽泛 |
| 不确定 | 证据不足 | 拿不到既有测试、调用方、契约，或判不出用例是否触达 |
| | 断言归属判不清 | 被断言的值来源不明 |
| | 结构不可解析 | 宏、模板、超长表达式折算的占位点 |

规则：

1. 一个点只选一条原因；同一分类命中多条时，**方向原因优先**。
2. 原因是方向原因时，说明里必须写清被改动的 `文件:行号`。
3. 「有效」的原因留空。

## 用例侧派生名单

不单独判定用例，由点表按列投影派生，只用于报告 2.2 点名：

| 名单 | 规则 |
|---|---|
| 无效用例 | 它覆盖的点全部是「无效」 |
| 低价值用例 | 它覆盖的点里没有「有效」，且至少有一个「低价值」 |
| 未涉及本次改动的用例 | 它没有覆盖任何点（不参与判定，只作提示） |

## 方向原因的识别

方向原因来自本次 diff 的删除侧或新增侧。`scan` 只覆盖其中四条字面线索（测试文件删除、新增禁用、断言被注释、断言弱化），方法体留空与测试输入弱化需要读语义，由人判：

| 信号 | 来源 | 对应原因 |
|---|---|---|
| 测试文件删除、新增禁用 | `scan` | 原有用例不再执行 |
| 方法体留空、测试输入弱化 | 人工 | 原有用例不再执行 |
| 断言被注释 | `scan` | 断言被注释 |
| 同一断言行由精确改宽泛 | `scan` | 断言被弱化 |

只认显式改动：能指得出被删 / 被改的那一行，且该点确实因此变差。新增生产代码但没有对应用例，记「无对应用例」，不算方向原因。

## 定性

分母一律是全部逻辑点，按序判定，命中即止：

| 序 | 取值 | 条件 |
|---|---|---|
| 0 | 证据不足（前置） | 没有变更单元，或全部变更单元都是「无法获取」 |
| 1 | 合格 | 逻辑点 = 0 |
| 2 | 证据不足 | 不确定 > 40% |
| 3 | 待改进 | 未覆盖 ≥ 30%，或无效 ≥ 30%，或有效 < 50% |
| 4 | 优秀 | 有效 ≥ 75%、未覆盖 = 0、无效 = 0、不确定 ≤ 10%，且逻辑点 ≥ 8 |
| 5 | 合格 | 其余 |

只数**问题类**：未覆盖、无效、低价值三类；有效不是问题，不确定是证据状态，单列。

阈值只在 `stats.py` 定义，`stats.json` 的 `水位` 块原样输出；报告 3.4.3 是读者副本。
