# DT 质量审计

审计一个检测对象的实现代码与 DT 之间的证据关系，回答两个问题：**代码被自己的测试盯住了吗？盯住的是真实实现吗？**

每条结论都要落到一个逻辑点编号和一处位置；证据原文只对命中的问题项要求。

## 输入与检测对象

从用户消息里取检测对象。只有两类：

| 标识形态 | 对象类型 |
|---|---|
| `SR1234`、`AR77` 这类编号 | SR / AR |
| 含 `merge_requests` / `pull` / `pulls` 的地址 | MR |

按标识形态判断。识别不出就追问，用户给不出就终止——**不要猜一个编号**。

SR 与 AR 的层级关系由脚本负责解析，Skill 不解释、不校验，只把返回的 MR 清单照收。

**变更单元恒为 MR**，没有提交批次这个概念。每个单元带：仓、首个提交、末提交。所有单元的改动并集就是检查范围。

报告开头必须写明检测对象；对象是 AR 或 MR 时，在 1.1 与偏差声明里写明对象类型，避免被读成 SR 结论。

## 前置条件：改动一律由脚本取

不管输入是 SR/AR 还是 MR，最后都归约成同一份东西：

1. 脚本拿 MR 元数据（`index` 或 `mr`）
2. 脚本取改动（`fetch`），产出 `<out>/manifest.json` 与 `<out>/<mr_id>/*.diff`

**检查以 manifest 与 diff 为主，两种输入没有区别。** 本地代码仓是可选的补充，不是改动内容的来源：

- 本地仓可达 → 允许按需读取仓内文件，补上 diff 里看不到的上下文（调用方、接口定义、既有测试方法体）
- 本地仓不可达 → 只看 diff 与 manifest

`fetch` 失败的 MR 记「无法获取」，不进分母、不计数、也不当作零。全部 MR 都拿不到时终止，不产出质量结论。

不要用「本地能看到」去推翻 diff 记录的改动，也不要把「没取到」当成「没问题」。

**工作目录**指会话当前工作目录；下文所有 `.dt-audit/...` 相对路径都相对它，执行命令前先确认 CWD。

## 边界

审计范围：检测对象中修改的 Java / Python / C / C++ 代码，以及为它们新增或修改的测试。

分析时可以按需读取未被改动的代码——调用方、接口定义、既有测试、构建目标——用作关联依据。它们只提供上下文，不进分母。

审计全程只读源码与 git 历史，不编译、不运行测试。改动内容一律来自 `fetch` 落盘的 manifest 与 diff；本地仓只用来补读上下文。读本地仓只用只读命令：`git show` / `git log` / `git cat-file` / `git remote -v` / `git grep <符号> <末提交> -- <路径>`；不切换分支、不改工作区、不 stash。读文件一律用 `git show <提交>:<路径>` 读 MR 末提交的版本，不读工作区——工作区可能已经切到别的分支。

用例当前是否通过，本 Skill 无法判断：被禁用的能识别出来，跑起来会失败但没被禁用的不能。红色的用例和绿色的用例在证据上一视同仁，报告的限制说明里必须写明这一点。

以下内容不进结论：

- 需求设计阶段的用例覆盖
- 仓库历史 DT 质量
- 提交或评审过程
- DT 规范性（命名、目录、结构）

因此结论只覆盖**实现自证能力**：代码自己引入的分支，有没有被自己的测试盯住。漏实现、设计缺陷不在覆盖范围内，报告的限制说明里必须写明这一点，避免被读成需求质量结论。

断言质量只回答一个问题：**这条分支的产出有没有被断言读到**。不评估断言是否充分——同一分支还有没有别的错法没被覆盖，静态分析判不了，硬判只会制造误报。

## 贯穿全程的两个机制

### 证据来源三档

| 档位 | 条件 | 能读到什么 |
|---|---|---|
| 含本地仓 | `fetch` 成功，且本地仓可达、`git remote -v` 归一化后与 MR 的仓匹配 | manifest + diff，外加仓内任意文件 |
| 仅 diff | `fetch` 成功，但本地仓不可达或 remote 不匹配 | 只有 manifest 与 diff |
| 无法获取 | `fetch` 失败 | 什么都没有，只计未分析 |

档位以 `fetch` 成功为前提：`fetch` 失败一律记「无法获取」，即使本地仓可达。

remote 匹配的归一化规则：去掉 `.git` 后缀，把 `git@host:group/repo` 与 `https://host/group/repo` 都归一成 `host/group/repo`，忽略大小写后与 manifest 里的 `repo` 比较。

**档位只说明能读到多少上下文，不决定能不能判。** 判不了的唯一理由是「这个逻辑点需要的证据不在手上」：

- 一条分支的判断只需要 diff 里那一行条件与产出 → 两档都够，照常判。
- 需要读本 MR 没改、diff 里也没有的代码（既有测试的方法体、调用方、接口契约）→ 只有「含本地仓」能读，「仅 diff」读不到。
- 「仅 diff」读不到时才落「不确定」，并在说明列写明缺的是哪一项。

每条「不确定」都必须写清缺失项，不许只写「文件不全」。

### 逻辑点与问题分类

全流程的原子计量单位是**逻辑点**：检测对象引入或修改的一条行为分支，不是文件、不是方法、不是行数。清单、不可解析占位点与语言能力档见 [逻辑点规则](references/逻辑点规则.md)。

每个逻辑点最终落一个分类，定义只在这里出现一次：

| 分类 | 定义 | 判据 |
|---|---|---|
| 有效 | 至少一条覆盖它的用例，断言核对到了这条分支的结果 | 格为「核对到」 |
| 低价值 | 断言引用了结果，但只判非空、大小、类型、长度这类形态 | 最好的格是「只到形态」 |
| 无效 | 有用例执行到了，但断言没核对该分支的结果，或跑的是假实现 | 全部格是「未核对」 |
| 未覆盖 | 没有任何用例能执行到这条分支 | 没有覆盖用例 |
| 不确定 | 证据不足以判出上面任一类 | 最好的格是「判不清」 |

分类即状态，不再有第二层类型。判定顺序、13 条原因、用例侧派生名单与「格」的定义见 [问题分类与判定](references/问题分类.md)。

**分母一律是全部逻辑点**：`有效 + 未覆盖 + 无效 + 低价值 + 不确定 = 全部`。定性只看这五个数，见步骤 5。


## 开跑之前：建待办

进入步骤 1 之前，先用 `todo_write` 建一份五项待办，与五个步骤一一对应：

1. 确定范围与取数
2. 盘点逻辑点与用例
3. 给每个逻辑点定问题
4. 自检
5. 出报告

清单规则：

- 同一时间只允许一项是 `in_progress`，其余是 `pending`。
- 一项标 `completed` 的条件，是它对应步骤的**完成标准全部满足**，且 `.dt-audit/<对象>/evidence.md` 里对应内容已落盘；不满足就保持 `in_progress`，不要提前标完成。
- 某项跑得久、用户看不出进展时，只改这一项的说明文字（如「步骤 1 确定范围与取数（正在定位本地仓）」），待办列表保持五项不变。
- 中途终止时，把当前项文字改成「已终止：<原因>」，保留后面的项，让用户看到停在哪一步。
- 每完成一项，除了更新待办，用一句话说明本步产出落在 `evidence.md` 的哪一段。
- 每步只更新自己那一项，不要攒到最后一起改。
- 报告写完再标最后一项完成。

环境里没有待办工具时，用一段普通清单在对话里同步进展，规则相同。

## 执行步骤

五个步骤，前三步建立证据，第四步验证证据，第五步出结论。每一步的**分析产出**写进同一个文件 `.dt-audit/<对象>/evidence.md`，不另立中间文件；`_diffs/` 由脚本落盘，`stats.json` 由脚本生成，报告是最终交付物。

### 步骤 1 确定范围与取数

（1）–（4）按顺序做完，再判一次短路，本步才算完成。

**（1）取变更单元**

`<skill_dir>` 指本 SKILL.md 所在目录。

| 对象 | 命令 |
|---|---|
| SR / AR | `python "<skill_dir>/scripts/run.py" index --id <编号> --pretty` |
| MR | `python "<skill_dir>/scripts/run.py" mr --url <地址> --pretty` |

MR 状态处理：

- SR / AR 关联出来的 MR：只保留 `merged`（已合入）与 `opened`（开启中）；`closed`、`locked`、`unknown` 剔除，剔除数量与状态记入「取数备忘」。
- 用户显式给出的 MR 地址：照单全收。`closed` 在「取数备忘」备注「改动可能未合入，证据以其差分内容为准」。

各子命令共用的退出码处理（`scope` / `scan` / `assemble` / `stats` / `render` 只会返回 1 或 64，2 / 3 由三个取数命令产生）：

| 码 | 含义 | 处理 |
|---|---|---|
| 0 | 成功 | 继续 |
| 2 | 对象不存在或地址无法解析 | 终止，不产出质量结论 |
| 3 | 平台不可达 | 终止，不产出质量结论 |
| 1 | 脚本内部异常 | 保留已落盘的部分并记入「取数备忘」；全部失败则终止 |
| 64 | 命令写错 | 改正后重跑 |

**（2）取改动**

- 把全部 MR 地址一次传给 `fetch`，`<out>` 取 `.dt-audit/<对象>/_diffs`：

  ```bash
  python "<skill_dir>/scripts/run.py" fetch --url <地址1> --url <地址2> --out .dt-audit/<对象>/_diffs --pretty
  ```

  MR 数量超过命令行长度上限时，按批调用 `fetch`，每批用不同的 `<out>`，再合并 manifest。

- 读 `<out>/manifest.json`：每个 MR 的文件清单、变更类型、增删行数、二进制与截断标记、`diff_path`、`warnings` 都在这里。**文件清单以它为准**，不要靠列目录反推。diff 的完整路径 = `<out>/<diff_path>`。
- **失败单元**：`warnings` 里列出的、或输入地址里没有出现在 `mrs` 里的 MR，记「无法获取」。
- 变更生产代码量（KLOC）：**在范围收敛之后**再算。只累加分类为生产代码、且语言为 Java / Python 的文件的 `additions`；不含删除行、不含测试文件、不含 C/C++。多个 MR 改动同一文件时，范围表按去重后的较大量计一次（`scope` 会 warning），不是把各 MR 相加。只用于陈述与密度，不参与判定。不要自己跑 `git diff --numstat`——两种口径混用会让 KLOC 对不上。
- 先从变更单元按仓去重得到仓集合，再用**一次**批量提问（`ask_user_question`，一次列全）问出每个仓的本地路径，不要一个仓问一次；按上面的归一化规则校验 remote。匹配上记「含本地仓」，匹配不上或用户没有该仓记「仅 diff」。这**不影响改动内容的来源**，只决定能额外读到多少上下文。
- **截断**：`truncated` 为真的文件，其上的逻辑点一律标「不确定」，说明列写 `证据不足：diff 被平台截断`，并在「取数备忘」记文件数。
- **删除 / 重命名**：生产文件删除不产生逻辑点（没有新增侧）；重命名按新增侧判，用 `old_path` 判断是否纯搬移——条件文本未变的不计逻辑点。测试文件删除是步骤 3 判「原有用例不再执行」的线索。

**（3）范围收敛**

按 [范围规则](references/范围规则.md) 的判定顺序给**每个**变更文件一个分类和一个结论。判不准的一律排除。**纳入的文件逐个落进证据表「范围」段；排除的只在「变更概览」里按分类汇总数量**，不逐个列路径、不逐个写理由。

**脚本**：`python "<skill_dir>/scripts/run.py" scope --manifest .dt-audit/<对象>/_diffs/manifest.json --out .dt-audit/<对象>/scope.json` 按路径与扩展名给出分类、排除计数与体量指标（生产改动行、KLOC）。内容特征（`@Test`、生成代码文件头）它判不了，默认按路径给结论，由你复核后修正；单文件改动行从 manifest 的文件清单直接累加。范围表与概览可用 `assemble --mode init` 从 scope + manifest + index 生成，不要手抄。

**（4）去重**

多个 MR 的改动可能重叠：后一个 MR 常常建立在前一个的分支上，会把前一个的改动一并带进来。**不要重建净差分，也不要逐段 `git blame`**，按身份去重：

1. 本步只对**变更文件与变更片段**去重，不枚举逻辑点——逻辑点的身份去重放到步骤 2 枚举冻结之后做。
2. 同一文件的改动来自多个 MR 时，来源档位取高者（含本地仓 > 仅 diff > 无法获取）。
3. 被后续提交 revert 掉的改动不产生逻辑点。判定方式：含本地仓档在末个 MR 的末提交上确认该条件仍存在（`git show <last_commit>:<path>`）；仅 diff 档无法确认，按证据计入并在「取数备忘」声明。

**（5）短路：没有生产代码变更**

范围表建好后先算**生产改动行**（分类 = 生产代码、语言为 Java / Python 的「新增」+「删除」）。**等于 0 就短路**：这次改动没有动到可审计的生产代码，跳过步骤 2–4，直接进步骤 5，定性记「合格」。

短路时仍要落齐结构：

- 用例清单与逻辑点证据两段写空表（保留表头与分隔行）。
- `取数备忘` 记「无有效生产代码变更（0 行），跳过步骤 2–4」。
- `narrative.json` 的 `偏差声明` 写明跳过步骤 2–4 及原因；两个维度的总评写「无行为分支，不评估」；Top3 给空数组。
- 有 C/C++ 受限文件时，报告的 1.1 会列出「C/C++ 受限文件数」，不能写「本次改动未引入行为分支」。
- 待办里的步骤 2–4 直接标完成，说明写「短路跳过」；不要留着 `in_progress`。

**完成标准**，下列内容全部满足，并把结果写入 `evidence.md` 的变更概览、变更单元与范围三段：

- `## 变更概览` 的表已写全，键名逐字使用「中间产物」一节的**精确键名**
- `## 变更单元` 每个 MR 一行，五个字段都填
- 每个变更单元都有唯一来源档位
- 每个变更文件都判过分类与结论，没有「未分类」
- 范围表只列纳入文件，每行有：路径、分类、语言、来源档位、新增、删除
- 排除项在变更概览里按分类给数量，没有逐个列文件
- 变更生产代码行数 = 范围表里「分类=生产代码且语言为 Java/Python」的新增行之和（`stats` 会交叉核对，对不上会给 warning）

**失败处理**：单个单元失败记「无法获取」后继续；没有单元或全部无法获取 → 输出证据不足（前置）说明并终止。

**待办**：按「清单规则」更新第 1 项。

### 步骤 2 盘点逻辑点与用例

盘两样东西：逻辑点与用例，顺带把两者的关联建起来。本步**只产清单，不判定**——分类、原因、说明都留到步骤 3。

按 manifest 的 `diff_path` 逐个读 diff，不要跳过。**读之前先按「检测对象过大时的处理」判分片**：超过阈值就派发子代理，本步变成派发与收口，主流程不再逐份读 diff。

**实现侧**：按 [逻辑点规则](references/逻辑点规则.md) 的封闭清单抽逻辑点，只算行为分支；C/C++ 不抽逻辑点。每个点给位置（文件 + 行号）、来源（新增 / 修改）与条件摘要；来源为「修改」时把增删的子句内联进条件摘要。判不出结构的片段按「不可解析的占位点」折算。

**测试侧**：按 [测试框架识别](references/测试框架识别.md) 列用例清单：用例、位置、变更类型（新增 / 修改 / 既有）。用例名用 `<类名>#<方法名>`，同一对象内必须唯一。

**建关联**：粗判哪些用例能执行到哪个点——只追一层入口，按入参、枚举值、构造器判可达，不要求证明执行。写进逻辑点证据的「覆盖用例」列，格式 `用例名(文件:行号)`，多个用例用顿号分隔。判不清的先留空，到步骤 3 记「不确定」。

两条边界：

- **被测对象被替换**时仍算关联：调用路径指向了该方法，只是真实实现没执行，步骤 3 记「只测假实现」，不记「未覆盖」。
- 来源为「修改」的点，用例必须落到**改动后的条件**上；只命中旧条件的不算关联（见 [逻辑点规则](references/逻辑点规则.md) 的「条件变化的覆盖要求」）。

**脚本**：

- `scan --manifest .dt-audit/<对象>/_diffs/manifest.json --out .dt-audit/<对象>/signals.json` 扫退化候选（删测试、禁用、注释断言、断言弱化）。它只是步骤 3 判方向原因的检查单，**不进证据表**。
- `assemble --mode merge --evidence .dt-audit/<对象>/evidence.md --shards <片 JSON…>` 合并枚举片：去重、编号，并用片里的候选用例填「覆盖用例」。编号与去重由它算，不要手抄。

**完成标准**：

- 每个纳入的 Java / Python 生产文件都产出逻辑点清单（可以为空），或产出「不可解析」占位点；C/C++ 只记受限文件，不进逻辑点表
- 用例清单区分新增 / 修改 / 既有
- 每个点的「覆盖用例」写清了用例名与行号；确认没有用例可达的留空
- 逻辑点计数按固定规则一次冻结，按身份（文件路径 + 条件文本 + 改动后行号）去重，后续只引用编号
- 分片运行时：各片通过校验，每个纳入的生产文件都至少被一片覆盖
- 已写入 `evidence.md` 的用例清单与逻辑点证据段

**仅 diff 档的豁免**：既有用例清单写空表，并在「取数备忘」记「既有用例清单无法获取」。缺失项只在**足以改变本点结论**时按「不确定」处理；本 MR 新增或修改的用例已经覆盖并核对到结果的点，照常判「有效」。

**待办**：按「清单规则」更新第 2 项。

### 步骤 3 给每个逻辑点定问题

关联与判定连着做，只做一遍。**先定谁判**：合并编号后逻辑点 > 50 个时，裁定按批派给**裁定片**（每 50 点一批，末批可少于 50 点），主流程只做关联、编号、打包与收口；≤ 50 个时主流程自己判。裁定片的输入输出契约见 [分片协议](references/分片协议.md)。

**（1）判格**

对每个（逻辑点，覆盖用例）判一个格：这条用例的断言，有没有核对到这条分支的结果。

| 格 | 判据 | 例子 |
|---|---|---|
| **核对到** | 断言引用了这条分支的结果并判定其内容 | `assertEquals(90, result)`、`assertThrows(IAE.class)`、`assertThat(o.getStatus()).isEqualTo(PAID)`、`verify(repo).save(argThat(...))` |
| **只到形态** | 引用了结果，但只判非空、大小、类型、长度、不抛异常 | `assertNotNull(result)`、`assertTrue(list.size() > 0)` |
| **未核对** | 断言没引用这条分支的结果 | 断言别的对象、只 `verify(mock)` 假实现被调用、方法内无断言 |
| **判不清** | 引用的值来源不明 | 二次组装的对象、跨方法计算的值 |

两条特例：**协作本身是结果**时（这条分支的结果就是「必须调用审计」），`verify` 带参数校验记「核对到」；**断言镜像实现**（在测试里重算生产公式）按「未核对」计，原因写「断言镜像实现」。

判格前先写一句**「这条分支的结果」**——返回值、抛出的异常、写入的状态、发起的协作、产出的产物。写不出的记「判不清」。

**（2）点取最好**

一个点常被多条用例覆盖，按下面的优先级取最好的一格：

```
核对到  >  只到形态  >  判不清  >  未核对
```

| 最好的格 | 分类 |
|---|---|
| 核对到 | **有效** |
| 只到形态 | **低价值** |
| 判不清 | **不确定** |
| 未核对（全部） | **无效** |
| 没有覆盖用例 | **未覆盖**（查证过没有用例可达）/ **不确定**（判不出可达） |

「判不清」排在「未核对」之前：判不清说明可能没问题，按疑罪从无处理。

**（3）落表**

每个点一行，填「覆盖用例、问题、原因、说明」：

- 原因从该分类的枚举里选一条，见 [问题分类与判定](references/问题分类.md)；**有效的原因留空**。
- **方向原因**（原有用例不再执行 / 断言被注释 / 断言被弱化）必须在说明里写清被改动的 `文件:行号`。
- 说明写一句话：现象 + 读到或没读到什么，例如 `T.java:88 只断言了 assertNotNull`。
- 同一分类命中多条原因时，**方向原因优先**——报告要说清是这次改坏的。

用例侧名单（无效用例 / 低价值用例 / 未涉及本次改动的用例）由脚本从点表派生，不要手写，也不要单独判定用例。

**脚本**：裁定片返回后，用 `assemble --mode judge --evidence .dt-audit/<对象>/evidence.md --judges <裁定 JSON…>` 回填「覆盖用例、问题、原因、说明」。不要手工拼表。

**完成标准**：

- 每个逻辑点都有分类与原因，且先写过「这条分支的结果」
- 有效 / 低价值 / 无效 都写了覆盖用例；未覆盖 留空；不确定 可以留空（判不出可达或占位点时）
- 有效 的原因留空；其余分类的原因都在枚举内
- 方向原因的说明里带了 `文件:行号`
- 每个点只有一个分类，同一事实不在两处取值不同
- 逻辑点总数为 0 时本步不适用，原因写入「取数备忘」
- 裁定片运行时：每批通过校验，未通过的批已由主流程补判并在「取数备忘」标注
- 已写入 `evidence.md` 的逻辑点证据段

**待办**：按「清单规则」更新第 3 项。

### 步骤 4 自检

只做三件事，不另立产物、不输出比率：

1. **跑脚本**：`stats --evidence .dt-audit/<对象>/evidence.md`，把报错逐条修掉——覆盖用例是否都在用例清单里、原因是否在枚举内、方向原因是否带行号、五类计数是否等于逻辑点总数。
2. **抽看 3 条**：从「无效 / 低价值 / 不确定」里各抽最多 1 条，回读断言原文，核对分类与原因是否对得上、说明里的行号是否真指向那条断言。对不上就改判并改正说明。
3. **补关联**：对「未覆盖」的点，在测试里再搜一次入口与入参；找到能到达的用例就补进「覆盖用例」并重判。

自查结论不单独占列，直接体现在修正后的「问题 / 原因 / 说明」里。没有可抽看项时跳过第 2 步，原因写进「取数备忘」。

**完成标准**：`stats` 校验通过；抽看项都核对过；未覆盖的点都重新搜过。

### 步骤 5 出报告

先算数，再写判断，最后交给脚本装配。**不要手写 Markdown 骨架**。

1. **算数**：跑 `python "<skill_dir>/scripts/run.py" stats --evidence .dt-audit/<对象>/evidence.md --out .dt-audit/<对象>/stats.json`。它按 [scripts/README](scripts/README.md) 的「报告口径」算五类占比、用例名单、缺口文件与 DT 质量定性，并校验合计与交叉关系。校验不过就修证据表，不要绕过、不要手改数字。

2. **写判断**：读 `stats.json`，把只有人能判的部分写进 `.dt-audit/<对象>/narrative.json`。固定 schema，只写这些字段：

   | 字段 | 内容 |
   |---|---|
   | `偏差声明` | 字符串；默认口径是 SR，对象为 AR / MR 或跳过某步时**必须**写 |
   | `一句话判断` | ≤50 字，点出数量最多的 1–2 类 |
   | `top3` | 数组，每项 `{文件, 问题, 建议}`，≤3 条；`文件` 必须是 `stats.json` 缺口文件里的路径；零缺口给空数组 |
   | `维度.2.1` | 含 `总评`、`建议`（字符串数组） |
   | `维度.2.2` | 含 `总评`、`建议`（字符串数组） |
   | `3.1` | `{取数, 去重, 额外限制}`；素材取自 `evidence.md` 的「取数备忘」 |

   **报告是唯一交付物**：任何字段都不要引用读者拿不到的内部文件（`evidence.md`、`stats.json`、`manifest.json`、`narrative.json`）、内部目录（`.dt-audit/`、`_diffs/`）、脚本命令或 skill 文档；要指证据时写报告内的章节号（如「见 3.3」）。

   **判断类字段不许留空**：2.1 / 2.2 的总评、一句话判断都必须给出内容，没有问题的维度也要写一句「未命中」。

   维度总评的口径：2.1 陈述问题分布与主要原因；2.2 陈述用例名单与修法。**不判高 / 中 / 低，不判严重度**——这两类概念已经取消。逻辑点为 0 时两个维度的总评写「无行为分支，不评估」。

3. **装配**：

   ```bash
   python "<skill_dir>/scripts/run.py" render \
     --stats .dt-audit/<对象>/stats.json \
     --evidence .dt-audit/<对象>/evidence.md \
     --narrative .dt-audit/<对象>/narrative.json \
     --out .dt-audit/<对象>/DT-AUDIT-REPORT.md --check
   ```

   模板默认取 `references/报告模板.md`。`--check` 会回读报告，核对：定性、数据行、合计、命中类数是否与 `stats.json` 一致；3.3 与分布表的行数；1.3 是否按点数降序且不超过 3 条；3.4.1–3.4.4 是否齐全；有无残留占位符与 HTML 注释。**校验不通过就不要交付**，修完重跑；改了证据表要先重跑 `stats`。

4. **终检**（脚本判不了的四条）：

   1. 一句话判断是否只点 1–2 类，且与分布表首位一致
   2. Top3 的文件与点数是否与 2.1 对得上，有没有凭空建议
   3. 有无自相矛盾：2.2 说没有无效用例而 2.1 有无效点
   4. 措辞是否越界：不得出现「测试通过」「功能正确」这类本 Skill 无权给出的结论

5. **交付**：在对话里贴出结论区（检测对象、定性、问题分布、主要缺口），并给出报告文件的绝对路径；完整报告不重复粘贴。

按分类陈列命中数量，类型之间不做加权、不给总分。

**完成标准**：

- `stats.json` 校验通过；`render --check` 通过；两者都没有被绕过
- 报告里的数字全部来自脚本，没有手改；`narrative.json` 只含判断类字段
- 1.2 的定性取自 `stats.json` 的「定性」，依据写清命中的规则与卡住的条件
- 五个占比齐全，分母都是全部逻辑点，百分比之和为 100%（零逻辑点时不出分布表）
- 1.1 一张表里合并了对象信息、来源分布与用例/体量数据；变更单元、构成与未纳入文件在 3.2
- 三大章齐全；2.1 按分类分组、每组一张表；2.2 三份名单齐全
- 1.3 按问题点数降序，最多 3 条
- 3.4.1–3.4.4 齐全，没有残留 `{{}}` 或 HTML 注释
- 3.3 的行数等于全部逻辑点数
- 上面「终检」四条逐条过一遍，没有留下矛盾
- 报告文件已落盘，对话里贴出了结论区与文件路径

默认写入文件，不等用户要。用户指定路径时把 `--out` 换成用户给的路径。

## 中间产物

手写产物有两个：`evidence.md`（步骤 1–4 的分析与判定）与 `narrative.json`（步骤 5 的判断类文案）。其余由脚本产出：`_diffs/` 来自 `fetch`，`scope.json` 来自 `scope`，`signals.json` 来自 `scan`，`stats.json` 来自 `stats`，报告来自 `render`；分片输入（`shard-*.json` / `judge-*.json`）由子代理产出。全部放在工作目录下的 `.dt-audit/<对象>/`，不要另立文件、不要在上下文里攒着：

```
.dt-audit/
└── SR1234/
    ├── evidence.md          # 分析产物，步骤 1–4 共同写
    ├── scope.json           # 步骤 1 由 scope 产出（可选，assemble init 读它）
    ├── index.json           # 步骤 1 的 index / mr 输出（可选，assemble init 读它）
    ├── signals.json         # 步骤 2 由 scan 产出（可选）
    ├── shard-*.json         # 枚举片 / 裁定片的输入输出（分片时才有）
    ├── stats.json           # 步骤 5 由 stats 算出
    ├── narrative.json       # 步骤 5 手写，只放判断类文案
    ├── DT-AUDIT-REPORT.md   # 步骤 5 由 render 装配，交付物
    └── _diffs/              # 脚本落盘，两种输入都有
        ├── manifest.json    # 文件清单与落盘位置，检查以它为准
        └── <mr_id>/*.diff   # 逐文件改动的正文
```

对象标识的取法：SR / AR 用 `(SR|AR)\d+`，即 `SR1234`、`AR77`；**MR 是地址**，直接填 MR 地址原文（`https://…/merge_requests/12`）。

### `evidence.md` 的结构

一张 `项 ｜ 值` 概览表 + 四张表，共 5 段；另有一个可选的自由文本段 `## 取数备忘`。段名、表头、列顺序都固定，`stats` 脚本依赖它，不要改名或调序。**5 个段即使没有内容，也必须保留表头与分隔行**（写空表），否则脚本报「没有表格」。

| 段 | 表头 | 内容 | 由哪一步写 |
|---|---|---|---|
| `## 变更概览` | 项 ｜ 值 | 见下方键名清单 | 步骤 1 |
| `## 变更单元` | MR 地址 ｜ 标题 ｜ 作者 ｜ 仓 ｜ 来源档位 | 每个 MR 一行；报告 3.2 的变更单元表直接取这里 | 步骤 1 |
| `## 范围` | 路径 ｜ 分类 ｜ 语言 ｜ 来源档位 ｜ 新增 ｜ 删除 | 只列纳入的文件，一行一个；语言填 Java / Python / C / C++ | 步骤 1 |
| `## 用例清单` | 用例 ｜ 位置 ｜ 变更类型 | 新增 / 修改 / 既有；位置写「文件:行号」 | 步骤 2 |
| `## 逻辑点证据` | 编号 ｜ 位置 ｜ 条件摘要 ｜ 来源 ｜ 覆盖用例 ｜ 问题 ｜ 原因 ｜ 说明 | 每逻辑点一行；覆盖用例写 `用例名(文件:行号)`，多个用顿号分隔 | 步骤 2 写前五列，步骤 3 补问题 / 原因 / 说明 |

`## 取数备忘` 没有表格，`stats` 不解析、也不要求存在；没有内容时整段省略。但凡是「记入 3.1」的信息，都必须先落到这里——否则跨到步骤 5 就只能靠上下文回忆。

`## 变更概览` 的键名**必须逐字使用**下列字符串，写成别的样子脚本会读成空值：

| 键 | 值 |
|---|---|
| `对象类型` | SR / AR / MR |
| `对象标识` | SR / AR 为 `(SR\|AR)\d+`，如 `SR1234`；MR 为地址原文，如 `https://…/merge_requests/12` |
| `变更单元数` | 整数 |
| `涉及仓` | `2 个（a/b、c/d）` |
| `含本地仓单元数` | 整数 |
| `仅 diff 单元数` | 整数 |
| `无法获取单元数` | 整数 |
| `变更生产代码行数` | 整数 |
| `生产文件数` | 整数 |
| `纳入文件数` | 整数 |
| `测试文件数` | 整数 |
| `C/C++ 受限文件数` | 整数 |
| `排除：<分类>` | 文件数；每个分类单独一行 |

写作要求：

- 用 Markdown 表格，表头与列顺序固定；`stats` 靠表头定位，改一个列名就会解析失败。
- 表头与分隔行必须用 **ASCII 的 `|`**。文档里为了排版写的全角 `｜` 只是示意，照抄会导致解析失败。
- **单元格内出现的 `|` 必须写成 `\|`**，条件摘要里的 `a || b` 尤其常见。不转义会把一行拆成多格，报错还指不到原因。
- 空单元格留空或写 `—`，不要写「无」「N/A」等其他占位。列表类条目（如 3.1 的清单）没有内容时写「无」，与表格单元格的规则不同。
- 目录不存在时先创建，不要因为缺目录就退回对话输出。
- `stats.json` 与报告对不上时，以 `evidence.md` 为准，改证据表后重跑脚本。
- 同一对象重复运行覆盖同名文件，不新建时间戳副本。

`.dt-audit/` 应在忽略清单里。若当前目录是代码仓，创建目录后检查 `.gitignore`，没有忽略规则就提醒用户添加，不要提交。

## 检测对象过大时的处理

步骤 2 开始前，用**生产改动行**判分片：范围表里「分类 = 生产代码且语言为 Java / Python」的「新增」+「删除」之和。它和「变更生产代码行数」（只算新增、用于 KLOC）不是一个量，不要混用。

| 生产改动行 | 处理 |
|---|---|
| ≤ 800 | 不分片，主流程逐个读 diff |
| 801–2,000 | 每片 ≤ 500 行，2–4 片 |
| 2,001–5,000 | 每片 ≤ 600 行，4–9 片 |
| > 5,000 | 先按仓分组，组内再按上面的档细分；单个仓仍 > 5,000 时按文件簇继续切，单文件片按下面的例外处理 |

两条例外只在**已触发分片**时生效：**单文件 > 500 改动行**的独占一片，允许超过每片上限，一个类不拆；**单个测试文件改动后 > 2,000 行**的只读命中变更类或变更方法名的测试方法，不整文件读（仅 diff 档判不出总行数时，按整文件读）。

切分单位是**生产文件簇**（同目录或同包），不按 MR、不按行切——按行会把一个方法拆到两片，两片都判不出分支结构。

枚举完之后还有一道分片：**步骤 3 的裁定**按逻辑点数量派给裁定片。

| 合并后的逻辑点 | 裁定 |
|---|---|
| ≤ 50 | 主流程自己判 |
| > 50 | 裁定片，每 50 点一批（末批可少于 50 点） |

裁定片只判问题、原因与说明，分工见步骤 3（1）–（3）。

**调度不做规定**：什么时候派、一次派几片、用 `subagent` 逐个派还是用 `workflow` 扇出、要不要分批等待，由运行的 agent 按环境和工具自行决定。本节只约束切片标准与每片的输入输出，不约束并发。

枚举片只做盘点，裁定片只做裁定：编号、合并、落盘、自检都由主流程做；子代理不嵌套，片内不再开子代理。切片规则、两份输出契约与提示词模板见 [分片协议](references/分片协议.md)；分片运行要在「取数备忘」记枚举片数与裁定批数，步骤 5 写进 3.1 的「额外限制」。

分片只降峰值，不降总量。低于阈值不分片，切了反而更贵。

不单独设配置文件。数值只在定义它的那一处出现，其他位置只放指针：

|---|---|---|
