# DT 质量审计

审计一个检测对象的实现代码与 DT 之间的证据关系，回答两个问题：**代码被自己的测试观测到了吗？观测住的是真实实现吗？**

每条结论都要能复核：带文件行号、带证据原文、带判定依据。

## 输入

从用户消息里取两样：检测对象类型，和它的标识。类型按标识形态判断，识别不出再问：

| 标识形态 | 对象类型 |
|---|---|
| `SR-1234` 这类编号 | SR |
| 含 `merge_requests` 的地址 | MR 批次 |
| 40 或 64 位十六进制，或 `A..B` 区间 | 提交批次 |

完全没线索时才按 SR 默认。一批里混了多种对象时，按类型分开处理，最后合并成一份报告；混合批次的对象标识用 `MIX-<首个标识>-<对象数>`。

提交批次要所属仓：先按 SHA 分组，再一次性问全所有仓路径。`A..B` 用 `git rev-list --no-merges A..B` 枚举；`git cat-file -e` 失败的对象直接报给用户，不猜。

## 检测对象

三种，其余步骤完全相同：

| 对象 | 输入 | 取数方式 |
|---|---|---|
| SR（默认） | SR 编号 | 调 `index` 脚本，拿它关联的全部 MR |
| MR 批次 | MR 地址列表 | 调 `mr` 脚本，逐个解析成 MR 详情 |
| 提交批次 | SHA 列表，或 `A..B` 区间，附所属仓 | 只用本地 `git`，不调脚本 |

只有 SR 走 `index`。MR 批次走 `mr`，提交批次不调脚本。

三种对象最后都归约成同一组**变更单元**：每个单元带一个仓、一个基准提交、一个头提交、一组提交。SR 与 MR 批次的单元是 MR；提交批次的单元是单个提交，基准取它的第一父提交。

目标提交集合 = 所有单元的提交之并集。后面的范围收敛与净变更重建都只在这个集合里做。

报告开头必须写明检测对象；对象不是 SR 时，在 1.1 与偏差声明里写明对象类型，避免被读成 SR 结论。

## 边界

审计范围：检测对象中修改的 Java / Python / C / C++ 代码，以及为它们新增或修改的测试。

分析时可以按需读取未被改动的代码——调用方、接口定义、既有测试、构建目标——用作关联依据。它们只提供上下文，不进分母。

审计全程只读源码与 git 历史，不编译、不运行测试。读取只用只读命令：`git show` / `git diff` / `git log` / `git cat-file` / `git remote -v` / `git merge-base` / `git blame` / `git rev-list`；不切换分支、不改工作区、不 stash。

用例当前是否通过，本 Skill 无法判断：被禁用的能识别出来，跑起来会失败但没被禁用的不能。红色的用例和绿色的用例在证据上一视同仁，报告的限制说明里必须写明这一点。

以下内容不进结论：

- 需求设计阶段的用例覆盖
- 仓库历史 DT 质量
- 提交或评审过程
- DT 规范性（命名、目录、结构）

因此结论只覆盖**实现自证能力**：代码自己引入的分支，有没有被自己的测试观测到。漏实现、设计缺陷不在覆盖范围内，报告的限制说明里必须写明这一点，避免被读成需求质量结论。

## 贯穿全程的四个机制

### 证据来源四档

每条变更来源都带一个来源档位，下游判断按档位准入：

| 档位 | 来源 | 准入 |
|---|---|---|
| 本地精确 | 本地仓 + MR 基准提交的精确差分 | 全部判断 |
| 本地推导 | 本地仓 + 以首个提交的父提交推导基准 | 全部判断 |
| 平台兜底 | 平台接口返回的文件级差分 | 只做文件级与字面级信号；需要完整文件的判断标「未检测」 |
| 无法获取 | 仓不可达且平台取数失败 | 只计「未分析」，不进分母 |

### 决策点

全流程的原子计量单位。一个决策点 = 检测对象引入或修改的一条行为分支，不是文件、不是方法、不是行数。清单见 [决策点规则](references/决策点规则.md)。

### 观测状态六档

每个决策点最终落一个状态，定义只在这里出现一次：

| 状态 | 定义 | 计入观测率 |
|---|---|---|
| 无测试 | 没有任何用例执行到该分支 | 否 |
| 已观测 | 有判别性断言，能区分对错 | 是 |
| 部分观测 | 有断言，但不区分对错，或只覆盖部分分支 | 是 |
| 实现被替换 | 真实实现被 Mock、桩或探针替换，用例没有执行到它 | 否 |
| 未观测 | 执行到了，但没有任何断言观察 | 否 |
| 无法判定 | 证据不足或结构不可解析 | 不进分母 |

「无测试」「实现被替换」「未观测」必须分开：无测试根本没有用例执行，实现被替换执行了但跑的是假实现，未观测跑的是真实实现但没人看。混在一起会把最该修的问题藏进覆盖率里。

判档按下面的顺序，落档即停：

0. 覆盖该决策点的全部用例都执行假实现（方法被整体替换）→ **实现被替换**；只要有一条触达用例走真实实现，就对那条用例继续走 2–5 步。
1. 结论依赖**本次没有验证过的运行前提**（测试会话是否初始化、旧 JAR 是否在类路径、环境变量、执行顺序），且该前提会改变本决策点的结论 → **无法判定**；结构不可解析、触达无法确认、归属存疑同样落这一档。前提或缺失项写进 04，并在 3.1 说明。
2. 没有任何用例执行到该分支 → **无测试**。
3. 该决策点被执行过，且把这条分支改错有断言会红 → **已观测**。
4. 没有断言会红，但该分支的产出（返回值、异常、写入的状态、外部副作用）被至少一条断言引用 → **部分观测**。
5. 产出没有被任何断言引用 → **未观测**。

### 双轮裁定

只有判断类步骤（步骤 3 的裁定）双跑，抽取类不双跑。两轮由**两个独立子代理**执行，互不可见。

- 输入相同：`02-决策点.md`、`03-测试盘点.md`、[断言与 Mock 判据](references/断言与Mock判据.md)，以及相关的生产与测试源码。
- 两个子代理**同时派出**，各拿一份任务书；除遍历顺序外逐字相同，独立给出每个决策点的触达结论与观测状态，回传固定表格。
- 遍历顺序一个设为编号升序、一个设为编号降序；除此之外提示词不做任何差异。
- 用独立子代理，不要用继承上下文的 fork 方式——上下文共享会让两轮高度相关，测不出分歧。
- 主代理逐条比对：一致采纳；不一致按固定保守序取靠左的一档：`无法判定 > 实现被替换 > 无测试 > 未观测 > 部分观测 > 已观测`，并标「需复核」。
- 不一致率 = 不一致条数 ÷ 两轮都给出状态且证据齐全的决策点数（不要求可判定）。
- 超过配置上限时，在报告的 3.1「双轮裁定」行写明「一致性不足（不一致率 X%，上限 Y%）」，并列出分歧明细。

子代理任务书至少写清五件事：读哪些文件、按什么顺序、输出哪五列（编号 / 触达 / 观测状态 / 证据 / 不确定标记）、证据怎么给、不确定时统一写「无法判定」并在标记列写「需复核」。并且要求只读不写，结果直接回传。

环境不支持子代理时，退回单代理双跑：同一份证据，升序一轮、逆序一轮，规则相同。

## 开跑之前：建待办

进入步骤 1 之前，先用 `todo_write` 建一份五项待办，与五个步骤一一对应：

1. 确定范围与证据
2. 盘点实现与测试
3. 给每个决策点定状态
4. 抽检判别力
5. 出报告

清单规则：

- 同一时间只允许一项是 `in_progress`，其余是 `pending`。
- 一项标 `completed` 的条件，是它对应步骤的**完成标准全部满足**，且 `.dt-audit/` 下对应文件已落盘；不满足就保持 `in_progress`，不要提前标完成。
- 某项跑得久、用户看不出进展时，只改这一项的说明文字（如「步骤 1 确定范围与证据（正在定位本地仓）」），待办列表保持五项不变。
- 中途终止时，把当前项文字改成「已终止：<原因>」，保留后面的项，让用户看到停在哪一步。
- 每完成一项，除了更新待办，用一句话说明本步产出落在 `.dt-audit/` 的哪个文件。
- 报告写完再标最后一项完成。

环境里没有待办工具时，用一段普通清单在对话里同步进展，规则相同。

## 执行步骤

五个步骤，前三步建立证据，第四步验证证据，第五步出结论。每一步的产出都按「中间产物」一节的约定落盘到工作目录下的 `.dt-audit/`。

### 步骤 1 确定范围与证据

四件事按顺序做完，本步才算完成。

**（1）取变更单元**

按检测对象选入口。`<skill_dir>` 指本 SKILL.md 所在目录。

| 对象 | 命令 |
|---|---|
| SR | `python "<skill_dir>/scripts/run.py" index --sr <SR编号> --pretty` |
| MR 批次 | `python "<skill_dir>/scripts/run.py" mr --url <地址1> --url <地址2> --pretty` |
| 提交批次 | 不调脚本，直接用 `git cat-file -e <SHA>` 校验 |

SR 只保留状态为已合入或开启中的 MR。用户显式给出的 MR 地址照单全收；状态为已关闭的，在报告里标注「改动可能未合入，证据以其差分内容为准」。

退出码处理：2 → 对象不存在或全部地址无法解析，终止；3 → 平台不可达，终止；1 → 取数脚本未实现或内部异常，明确告知用户后终止，不要改走别的入口硬试；64 → 命令写错，改正后重跑。前三种都不产出质量结论。

**（2）取证**

- 从变更单元去重出仓集合，用**一次**批量提问（`ask_user_question`，一次列全）问出每个仓的本地路径，不要一个仓问一次。
- 逐仓校验：`git -C <路径> remote -v` 的地址与仓路径归一化后匹配（协议、`.git` 后缀、大小写）；`git cat-file -e <提交>` 确认提交存在。
- 逐 MR 定差分基准并落来源档位：
  - 精确基准提交齐备且仓可达 → **本地精确**
  - 无精确基准 → `git diff <首个提交^> <末提交>` → **本地推导**；首个提交是合并提交时改用 `git merge-base <目标分支> <末提交>`
  - 仓不可达 → `python "<skill_dir>/scripts/run.py" detail --mr <编号> --project <平台项目路径> --pretty` → **平台兜底**；`--project` 取 `MrRef.repo.project_path`，不是本地路径
  - 仓可达但既无基准也无提交 → **无法获取**
  - 仍失败 → **无法获取**

按文件记录 `git diff --numstat <基准> <头>` 的新增/删除行数，写入 01。变更生产代码量取新增侧行数（含修改），不含删除与测试行。

**（3）范围收敛**

按 [范围规则](references/范围规则.md) 给**每个**变更文件一个分类和一个结论。判不准的一律排除并记录理由。

**（4）净变更重建**

检测对象可能跨多个 MR，且存在并行开发交错提交，不能把 MR 差分直接拼起来。按文件重建：

1. 取该文件在本检测对象内最早、最晚触及的提交。
2. 净差分 = `git diff <首提交的单父> <末提交> -- <文件>`；首提交是合并提交时用 `git merge-base`。
3. `git log <首提交>^..<末提交> -- <文件>` 查窗口内有无非本对象的提交。
4. 无混杂 → 归属记「确定」。有混杂 → 逐片段用 blame 加提交说明判归属。
5. 判不了的标「归属存疑」：不计入分母，计入证据完整度扣减。

**完成标准**，四项内容全部满足，并把范围表写入 `.dt-audit/<对象>/01-范围与证据.md`：

- 每个变更单元都有唯一来源档位
- 每个变更文件都有分类与结论，表里没有「未分类」行
- 每个生产变更片段都有归属结论（本对象 / 非本对象 / 存疑）
- 范围表每行都有：路径、分类、纳入或排除、理由、来源档位、新增/删除行数

**失败处理**：单个单元失败记「无法获取」后继续；没有单元或全部无法获取 → 输出证据不足提示并终止。

**待办**：开始本步时把第 1 项标 `in_progress`；四项内容与落盘都完成后**立即**标 `completed`，不要留到后面一起更新。

### 步骤 2 盘点实现与测试

两侧同时盘点，缺一侧不算完成。

**实现侧**：按 [决策点规则](references/决策点规则.md) 的封闭清单抽决策点，只算行为分支。每个决策点给编号、文件、行号、类型、条件、分支、来源、条件变化（修改来源必填）、置信度。

**测试侧**：按 [测试框架识别](references/测试框架识别.md) 识别用例、断言、Mock；按 [问题类型](references/问题类型.md) 逐类采集证据；断言与 Mock 的分类定义见 [断言与 Mock 判据](references/断言与Mock判据.md)。

盘点时必须单独标出**被测试替换掉的实现**：`@Override` 探针、被 Mock 的静态入口、被桩替换的生产函数、被链接替换的 C/C++ 符号。记住它们替换掉的方法体内有哪些决策点。

**完成标准**：

- 每个纳入的生产文件要么产出决策点清单，要么标「无法判定」
- 每个测试文件都有用例、断言、Mock、被替换实现四张清单
- 可初筛的类型（B1/B2/B3/C2/C3/A3）逐类给结论；A1/A2/D1 等步骤 3 的触达与状态，A4 等步骤 5 的证据完整度，这三组写「待步骤 3/5 裁定」，不要写「无」。数量留到步骤 5 统计
- 决策点写入 `02-决策点.md`，测试盘点写入 `03-测试盘点.md`
- 决策点计数按固定规则一次冻结（见 [决策点规则](references/决策点规则.md) 的「枚举冻结」），后续只引用编号，不重新计数

**待办**：开始本步时把第 2 项标 `in_progress`；完成标准全部满足后**立即**标 `completed`，不要留到后面一起更新。

### 步骤 3 给每个决策点定状态

关联与裁定连着做，中间不换任务。

**（1）关联**

每个决策点落四态之一：

| 状态 | 含义 |
|---|---|
| 直接触达 | 用例明确调用或经过该决策点 |
| 可能触达 | 静态链路无法完全确认，但语义上高度相关 |
| 未触达 | 用例与该决策点无关 |
| 无法确认 | 跨仓不可见、动态派发无法排除 |

关联能力三档：

| 能力 | 条件 | 粒度 |
|---|---|---|
| 索引级 | 仓有 `.codegraph/` 索引 | 符号级 + 调用边 |
| 静态级 | 仓可达、无索引 | 静态启发式 + 语义推断 |
| 文件级 | 仓不可达（平台兜底） | 文件级 |

「无法确认」从观测率的分子分母同时剔除，计入证据完整度。C/C++ 默认只到文件级。

关联时先标记被替换：如果该决策点所在方法被测试替换掉了，记「所属方法被替换」，到裁定环节直接落「实现被替换」，不再判断言。

**（2）裁定**

判据见 [断言与 Mock 判据](references/断言与Mock判据.md)。

对每个（决策点，触达用例）连问三个问题：

1. 该用例是否真的执行了这条分支？
2. 断言是否观察了这条分支产生的可观测结果？
3. 该断言能否区分「分支走向正确」与「走向错误或结果错误」？

落六态之一：无测试、已观测、部分观测、实现被替换、未观测、无法判定。

**（3）双轮**

按「双轮裁定」一节派两个独立子代理，各自回传表格；主代理逐条比对后写入 `04-观测矩阵.md`。

每个条目必须带四样：决策点编号、触达结论、观测状态、证据。证据按状态给，不是所有状态都有断言可引：

| 状态 | 证据 |
|---|---|
| 已观测 / 部分观测 | 用例方法名 + 断言行号 |
| 未观测 | 用例方法名 + 「无断言」 |
| 无测试 | 检索范围与结论（查了哪些测试文件、为何没有执行） |
| 实现被替换 | 替换者位置 + 被替换方法 |
| 无法判定 | 缺失的前提或证据项 |

证据缺失的条目按「需复核」处理，不进一致率统计。

既有测试计入证据，但报告里必须分列「新增 / 修改用例」与「既有用例」。

**完成标准**：

- 每个决策点都有触达结论和观测状态
- 已观测 / 部分观测 / 未观测都引用了断言或「无断言」证据；无测试 / 实现被替换 / 无法判定引用了各自的替代证据（检索范围、替换点、缺失前提）
- 每个「已观测」都有决策点、用例、断言行三元组，且能回答「改错什么会红」
- 条件被修改的决策点，已核对被删子句与新增子句的用例（见 [决策点规则](references/决策点规则.md) 的「条件变化的覆盖要求」）
- 跨行一致性检查通过：C1 不出现在 D1、同一守卫两个方向不矛盾、被整体替换的方法体内没有「已观测」
- 双轮不一致的条目都标了「需复核」并取了保守档

### 步骤 4 抽检判别力

从决策点里随机抽样：优先已观测与部分观测的（验证断言是不是花架子），另抽一部分未观测的（佐证缺口）。样本量按配置的抽样数量，C/C++ 用受限档。

对每个样本构造一到两个合理的错误实现——条件取反、边界加减一、删分支、返回值替换、异常类型替换、分支顺序调换——判断现有断言是否会变红。

**完成标准**：样本数 = min(配置的抽样数量, 可抽样决策点数)；某一分层为 0 时该层不抽并注明；抽样清单写明抽样方式或种子；每个样本都有「捕获」或「未捕获」的结论和理由；已写入 `.dt-audit/<对象>/05-抽检.md`。可判定决策点为 0 时本步不适用，不抽样，原因写入 05。

只输出「抽查 n 个，捕获 m 个」和未捕获明细，不输出比率。抽检结果写进断言的维度章节，作为判别力结论的实证。

## 中间产物

每一步的产出都落盘到**工作目录下的 `.dt-audit/`**，不要在上下文里攒着。01–06 是复核与二次运行的依据，`DT-AUDIT-REPORT.md` 是最终交付物。

目录按检测对象分：

```
.dt-audit/
└── SR-1234/
    ├── 01-范围与证据.md
    ├── 02-决策点.md
    ├── 03-测试盘点.md
    ├── 04-观测矩阵.md
    ├── 05-抽检.md
    ├── 06-问题统计.md
    └── DT-AUDIT-REPORT.md
```

对象标识的取法：SR 用 `SR-1234`；MR 批次用 `MR-<首个MR编号>-<数量>`；提交批次用 `commit-<首个SHA前7位>-<数量>`；混合批次用 `MIX-<首个标识>-<对象数>`。

| 文件 | 内容 | 由哪一步产生 |
|---|---|---|
| 01-范围与证据 | 变更单元清单与来源档位、文件分类与排除清单、每文件新增/删除行数、净变更片段归属 | 步骤 1 |
| 02-决策点 | 决策点全表：编号、位置、类型、条件、分支、来源、条件变化、置信度 | 步骤 2 |
| 03-测试盘点 | 用例、断言、Mock、被替换实现四张清单；11 类问题的初筛结论 | 步骤 2 |
| 04-观测矩阵 | 决策点 → 触达用例 → 观测状态；两份独立判定的比对与分歧记录 | 步骤 3 |
| 05-抽检 | 抽样清单、构造的错误实现、捕获结论 | 步骤 4 |
| 06-问题统计 | 11 类的计数与算式、各指标、证据不足项 | 步骤 5 |
| DT-AUDIT-REPORT.md | 最终报告，三大章。交付物 | 步骤 5 |

写作要求：

- 用 Markdown 表格，表头固定，方便二次读取和人工复核。
- 03 的四张清单表头固定：用例（方法名｜位置｜断言数｜参数化组数）、断言（行号｜档位）、Mock（类型｜位置｜被替换方法）、被替换实现（方法｜替换者位置）；05 固定为（编号｜错误实现｜预期变红用例｜结论）。
- 目录不存在时先创建，不要因为缺目录就退回对话输出。
- 报告的数字逐项摘自 `06-问题统计.md`，不重新推导；两者对不上时，以 `.dt-audit/` 为准并修报告。
- 同一对象重复运行覆盖同名文件，不新建时间戳副本；需要保留历史时由用户自己复制。
- 报告文件在忽略目录里，要分享或留档时复制到别处。

如果工作目录是代码仓，提醒用户把 `.dt-audit/` 加进忽略清单，不要提交。

## 大检测对象的处理

规格过大时按 MR 或按文件切分给子代理，合并以决策点编号为键去重、冲突取来源档位高者；落盘由主流程统一写。编号规则见 [决策点规则](references/决策点规则.md)。

子代理不嵌套：分片盘点由主流程派发，双轮裁定也由主流程另派两个子代理做全量，不在分片内部再开。
