# DT 质量审计

审计一个检测对象的实现代码与 DT 之间的证据关系，回答两个问题：**代码被自己的测试观测到了吗？观测住的是真实实现吗？**

每条结论都要落到一个决策点编号和一处位置；证据原文只对命中的问题项要求。

## 输入与检测对象

从用户消息里取检测对象类型和标识。类型按标识形态判断，识别不出再问；完全没线索时才按 SR 默认。

| 标识形态 | 对象类型 | 取数方式 |
|---|---|---|
| `SR-1234` 这类编号 | SR | 调 `index` 脚本，拿关联的全部 MR |
| 含 `merge_requests` 的地址 | MR 批次 | 调 `mr` 脚本，逐个解析成 MR 详情 |
| 40 或 64 位十六进制，或 `A..B` 区间 | 提交批次 | 只用本地 `git`，不调脚本 |

只有 SR 走 `index`。提交批次要所属仓：先按 SHA 分组，再**一次**问全所有仓路径。`A..B` 用 `git rev-list --no-merges A..B` 枚举；`git cat-file -e` 失败的对象直接报给用户，不猜。

一批里混了多种对象时，按类型分开处理，最后合并成一份报告；对象标识用 `MIX-<首个标识>-<对象数>`。

三种对象最后都归约成同一组**变更单元**：每个单元带一个仓、一个基准提交、一个头提交、一组提交。SR 与 MR 批次的单元是 MR；提交批次的单元是单个提交，基准取它的第一父提交。目标提交集合 = 所有单元的提交之并集。

报告开头必须写明检测对象；对象不是 SR 时，在 1.1 与偏差声明里写明对象类型，避免被读成 SR 结论。

## 前置条件：必须有本地仓

详细修改内容**只从本地代码仓取**，不通过平台接口取 diff。因此：

- 每个变更单元必须先落到一个本地仓路径，且提交在该仓里存在。全部单元都落不到本地仓时**终止**，不产出质量结论。
- 单个单元落不到（仓不可达或提交缺失）→ 记「无法获取」，不进分母、不计数、也不当作零。
- 不要用别的提交凑数，不要靠读平台页面上的 diff 补。

## 边界

审计范围：检测对象中修改的 Java / Python / C / C++ 代码，以及为它们新增或修改的测试。

分析时可以按需读取未被改动的代码——调用方、接口定义、既有测试、构建目标——用作关联依据。它们只提供上下文，不进分母。

审计全程只读源码与 git 历史，不编译、不运行测试。读取只用只读命令：`git show` / `git diff` / `git log` / `git cat-file` / `git remote -v` / `git merge-base` / `git blame` / `git rev-list`；不切换分支、不改工作区、不 stash。

用例当前是否通过，本 Skill 无法判断：被禁用的能识别出来，跑起来会失败但没被禁用的不能。红色的用例和绿色的用例在证据上一视同仁，报告的限制说明里必须写明这一点。

以下内容不进结论：

- 需求设计阶段的用例覆盖
- 仓库历史 DT 质量
- 提交或评审过程
- DT 规范性（命名、目录、结构）

因此结论只覆盖**实现自证能力**：代码自己引入的分支，有没有被自己的测试观测到。漏实现、设计缺陷不在覆盖范围内，报告的限制说明里必须写明这一点，避免被读成需求质量结论。

## 贯穿全程的三个机制

### 证据来源三档

每条变更来源都带一个来源档位，下游判断按档位准入：

| 档位 | 来源 | 准入 |
|---|---|---|
| 本地精确 | 本地仓 + MR 基准提交的精确差分 | 全部判断 |
| 本地推导 | 本地仓 + 以首个提交的父提交推导基准 | 全部判断 |
| 无法获取 | 仓不可达或提交缺失 | 只计「未分析」，不进分母 |

### 决策点

全流程的原子计量单位。一个决策点 = 检测对象引入或修改的一条行为分支，不是文件、不是方法、不是行数。清单与语言能力档见 [决策点规则](references/决策点规则.md)。

### 观测状态六档

每个决策点最终落一个状态，定义只在这里出现一次：

| 状态 | 定义 | 计入观测率 | 计入可拦截率 |
|---|---|---|---|
| 无测试 | 没有任何用例执行到该分支 | 否 | 否 |
| 已观测 | 有判别性断言，能区分对错 | 是 | 是 |
| 部分观测 | 有断言，但不区分对错，或只覆盖部分分支 | 是 | 否 |
| 实现被替换 | 真实实现被 Mock、桩或探针替换，用例没有执行到它 | 否 | 否 |
| 未观测 | 执行到了，但没有任何断言观察 | 否 | 否 |
| 无法判定 | 证据不足或结构不可解析 | 不进分母 | 否 |

「无测试」「实现被替换」「未观测」必须分开：无测试根本没有用例执行，实现被替换执行了但跑的是假实现，未观测跑的是真实实现但没人看。混在一起会把最该修的问题藏进覆盖率里。

判档按下面的顺序，落档即停：

0. 覆盖该决策点的全部用例都执行假实现 → **实现被替换**；只要有一条覆盖该决策点的用例走真实实现，就对那条用例继续走 2–5 步。
1. 结论依赖**本次没有验证过的运行前提**（测试会话是否初始化、旧 JAR 是否在类路径、环境变量、执行顺序），且该前提会改变本决策点的结论 → **无法判定**；结构不可解析、触达无法确认同样落这一档。缺失项写进证据表的「复核」列，并在 3.1 汇总。
2. 没有任何用例执行到该分支 → **无测试**。
3. 该决策点被执行过，且把这条分支改错有断言会红 → **已观测**。
4. 没有断言会红，但该分支的产出（返回值、异常、写入的状态、外部副作用）被至少一条断言引用 → **部分观测**。
5. 产出没有被任何断言引用 → **未观测**。

判档只做一遍，不做重复判定。覆盖不到的部分由步骤 4 的定点自查补。

## 开跑之前：建待办

进入步骤 1 之前，先用 `todo_write` 建一份五项待办，与五个步骤一一对应：

1. 确定范围与取数
2. 盘点实现与测试
3. 给每个决策点定状态
4. 抽样自查
5. 出报告

清单规则：

- 同一时间只允许一项是 `in_progress`，其余是 `pending`。
- 一项标 `completed` 的条件，是它对应步骤的**完成标准全部满足**，且 `.dt-audit/<对象>/evidence.md` 里对应内容已落盘；不满足就保持 `in_progress`，不要提前标完成。
- 某项跑得久、用户看不出进展时，只改这一项的说明文字（如「步骤 1 确定范围与取数（正在定位本地仓）」），待办列表保持五项不变。
- 中途终止时，把当前项文字改成「已终止：<原因>」，保留后面的项，让用户看到停在哪一步。
- 每完成一项，除了更新待办，用一句话说明本步产出落在 `evidence.md` 的哪一段。
- 每步只更新自己那一项，不要攒到最后一起改。
- 报告写完再标最后一项完成。

环境里没有待办工具时，用一段普通清单在对话里同步进展，规则相同。

## 执行步骤

五个步骤，前三步建立证据，第四步验证证据，第五步出结论。每一步的产出都写进**同一个文件** `.dt-audit/<对象>/evidence.md`，不另立中间文件。

### 步骤 1 确定范围与取数

四件事按顺序做完，本步才算完成。

**（1）取变更单元**

按检测对象选入口。`<skill_dir>` 指本 SKILL.md 所在目录。

| 对象 | 命令 |
|---|---|
| SR | `python "<skill_dir>/scripts/run.py" index --sr <SR编号> --pretty` |
| MR 批次 | `python "<skill_dir>/scripts/run.py" mr --url <地址1> --url <地址2> --pretty` |
| 提交批次 | 不调脚本，直接用 `git cat-file -e <SHA>` 校验 |

SR 只保留状态为已合入或开启中的 MR。用户显式给出的 MR 地址照单全收；状态为已关闭的，在报告里标注「改动可能未合入，证据以其差分内容为准」。

退出码处理：2 → 对象不存在或全部地址无法解析，终止；3 → 平台不可达，终止；1 → 取数脚本未实现或内部异常，明确告知用户后终止，不要改走别的入口硬试；64 → 命令写错，改正后重跑。前三种都不产出质量结论。

**（2）取证**

- 从变更单元去重出仓集合，用**一次**批量提问（`ask_user_question`，一次列全）问出每个仓的本地路径，不要一个仓问一次。
- 逐仓校验：`git -C <路径> remote -v` 的地址与仓路径归一化后匹配（协议、`.git` 后缀、大小写）；`git cat-file -e <提交>` 确认提交存在。匹配不上就向用户再要一次路径；要不到 → 该单元「无法获取」。
- 逐变更单元定差分基准并落来源档位：
  - 精确基准提交齐备且仓可达 → **本地精确**
  - 无精确基准 → `git diff <首个提交^> <末提交>` → **本地推导**；首个提交是合并提交时改用 `git merge-base <目标分支> <末提交>`
  - 仓不可达、提交缺失、基准推导失败 → **无法获取**
- 按文件记录 `git diff --numstat <基准> <头>` 的新增/删除行数。变更生产代码量取新增侧行数（含修改），不含删除与测试行。

**（3）范围收敛**

按 [范围规则](references/范围规则.md) 给**每个**变更文件一个分类和一个结论。判不准的一律排除。**纳入的文件逐个落进证据表「范围」段；排除的只在「变更概览」里按分类汇总数量**，不逐个列路径、不逐个写理由。

**（4）归属去重**

检测对象可能跨多个 MR，且存在并行开发交错提交。**不要重建净差分，也不要逐片段 blame**，按下面的办法拿到不重复的决策点集合：

1. 每个变更单元各自枚举自己的变更文件与新增侧改动。
2. 决策点的身份 = 文件路径 + 条件文本 + 改动后行号。同一身份在多个单元里出现只算一次，来源档位取高者（本地精确 > 本地推导）。
3. `git log <基准>..<头> -- <文件>` 查该文件的窗口内有无非本对象的提交。**只有确实存在外来提交的文件**，才对该文件做一次 `git blame` 确认改动归属；归属仍判不清的，该文件记「无法获取」，不进分母。
4. 被后续提交 revert 掉的改动不产生决策点——它不在头提交的新增侧里。

**完成标准**，下列内容全部满足，并把结果写入 `evidence.md` 的变更概览与范围段：

- 每个变更单元都有唯一来源档位
- 每个变更文件都判过分类与结论，没有「未分类」
- 决策点集合已按身份去重，没有重复计数
- 范围表只列纳入文件，每行有：路径、分类、来源档位、新增/删除行数
- 排除项在变更概览里按分类给数量，没有逐个列文件

**失败处理**：单个单元失败记「无法获取」后继续；没有单元或全部无法获取 → 输出证据不足提示并终止。

**待办**：按全局待办规则更新第 1 项。

### 步骤 2 盘点实现与测试

两侧同时盘点，缺一侧不算完成。本步**只产清单，不判定**：10 类问题的命中数量、断言的判别力档位都留到步骤 3 绑定后再定，断言这一步只记行号与原文。

**实现侧**：按 [决策点规则](references/决策点规则.md) 的封闭清单抽决策点，只算行为分支；C/C++ 不抽决策点（见该文件的「与语言能力的对应」）。每个决策点给编号、位置（文件 + 行号）、类型、来源（新增 / 修改），条件与分支写进条件摘要；来源为「修改」时把增删的子句一并内联进去。

**测试侧**：按 [测试框架识别](references/测试框架识别.md) 识别用例、断言、Mock。只收本对象**新增或修改**用例内的断言；既有用例只作触达证据，其断言不进分母。

盘点时必须单独标出**被测试替换掉的实现**：`@Override` 探针、被 Mock 的静态入口、被桩替换的生产函数、被链接替换的 C/C++ 符号。记住它们替换掉的方法体内有哪些决策点。

按 [问题类型](references/问题类型.md) 的 A3 六条信号做**字面扫描**（删测试、新增禁用、断言被注释、测例留空体、断言弱化、输入弱化）——这一步便宜，不要留到后面补。

**完成标准**：

- 每个纳入的生产文件要么产出决策点清单，要么标「无法判定」
- 用例、断言、Mock 三张清单齐全，被替换实现记在 Mock 清单里
- 用例清单区分新增 / 修改 / 既有，断言清单只含新增或修改用例内的断言
- A3 六条信号逐条扫过，命中项写入信号与问题表
- 决策点计数按固定规则一次冻结（见 [决策点规则](references/决策点规则.md) 的「枚举冻结」），后续只引用编号，不重新计数
- 已写入 `evidence.md` 的对应段

**待办**：按全局待办规则更新第 2 项。

### 步骤 3 给每个决策点定状态

关联与裁定连着做，中间不换任务，只做一遍。

**（1）关联**

给每个决策点标一个关联结论，只有两种：

| 结论 | 含义 |
|---|---|
| 有 | 用例明确调用或经过该决策点 |
| 无 | 用例与该决策点无关，或静态链路无法确认 |

「无」按判档顺序落「无测试」；因跨仓不可见、动态派发无法排除而判不出的，落「无法判定」，不再单设一档。

关联能力三档：

| 能力 | 条件 | 粒度 |
|---|---|---|
| 索引级 | 仓有 `.codegraph/` 索引 | 符号级 + 调用边 |
| 静态级 | 仓可达、无索引 | 静态启发式 + 语义推断 |
| 文件级 | 只有文件级信息可用 | 文件级 |

C/C++ 不枚举决策点，关联也只到文件级。

关联时先标记被替换：如果该决策点所在方法被测试替换掉了，记「所属方法被替换」，到裁定环节直接落「实现被替换」，不再判断言。**只有让用例拦不住缺陷的 mock 才计数**：被替换的方法体内含本对象的决策点、且覆盖它的用例全走假实现 → C1；mock 的是外部还是内部依赖本身不是判据。

**（2）裁定**

判据见 [断言与 Mock 判据](references/断言与Mock判据.md)。断言的判别力档位在这一步、**绑定到具体决策点的具体分支时**判一次，不做全文通档。

对每个（决策点，触达用例）连问三个问题：

1. 该用例是否真的执行了这条分支？
2. 断言是否观察了这条分支产生的可观测结果？
3. 该断言能否区分「分支走向正确」与「走向错误或结果错误」？

落六态之一：无测试、已观测、部分观测、实现被替换、未观测、无法判定。

**（3）落表**

每个决策点在证据表里一行，带编号、位置、类型、条件摘要、来源、触达用例、观测状态、问题类型、严重度。证据按状态给，不是所有状态都有断言可引：

| 状态 | 证据 |
|---|---|
| 已观测 / 部分观测 | 用例方法名 + 断言行号 |
| 未观测 | 用例方法名 + 「无断言」 |
| 无测试 | 检索范围与结论（查了哪些测试文件、为何没有执行） |
| 实现被替换 | 替换者位置 + 被替换方法（两者都写，报告 2.2 直接取用） |
| 无法判定 | 缺失的前提或证据项 |

「问题类型」一列把该决策点命中的类型写进去：A1（无测试）、C1（实现被替换）、D1（未观测）、A4（无法判定）。A4 也可由状态直接推得，但两种写法必须一致。

**来源为「修改」的决策点必须填「断言随动」**：覆盖它的断言行也在本次变更行里 → 填「是」；断言没动 → 填「否」，并在「复核」列回答一句「既有断言凭什么还能拦住改动后的行为」。答不上来的，状态降到部分观测或无法判定。来源为「新增」的留空。

「改了代码、没改断言」是 DT 最常见的失效方式：断言还在验证旧行为，测试恰好绿。这一列就是用来把这种情况逼出来的。

既有测试计入证据，但报告里必须分列「新增 / 修改用例」与「既有用例」。

**完成标准**：

- 每个决策点都有触达结论和观测状态
- 已观测 / 部分观测 / 未观测都引用了断言或「无断言」证据；无测试 / 实现被替换 / 无法判定引用了各自的替代证据（检索范围、替换点、缺失前提）
- 每个「已观测」都有决策点、用例、断言行三元组，且能回答「改错什么会红」
- 条件被修改的决策点，已核对被删子句与新增子句的用例（见 [决策点规则](references/决策点规则.md) 的「条件变化的覆盖要求」）
- 来源为「修改」的决策点都填了「断言随动」；填「否」的都在「复核」列写了理由，写不出的已降档
- 每个决策点只有一个状态，同一事实不在两处取值不同
- 决策点总数为 0 时本步不适用：不判定，原因写入证据表
- 已写入 `evidence.md` 的决策点证据段

**待办**：按全局待办规则更新第 3 项。

### 步骤 4 抽样自查

从决策点里定点抽取：**3 个**「已观测 / 部分观测」项（验证断言是不是花架子），外加**全部证据薄弱项**——只写到用例名、拿不出断言行号的项。

对每个自查项构造一个合理的错误实现——条件取反、边界加减一、删分支、返回值替换、异常类型替换、分支顺序调换——判断现有断言是否会变红。

- 答不出「哪条断言会红」的已观测 / 部分观测项，降为部分观测或未观测，并回写证据表。
- 自查结论写进证据表的「复核」列，标明「捕获」或「未捕获」；未捕获的写清缺口方向。
- 不另立产物、不输出比率、不做分层随机、不设种子。

**完成标准**：自查项数 = min(3, 可自查项数) + 全部证据薄弱项；每个自查项都有「捕获」或「未捕获」的结论和理由；降档已回写证据表；未捕获明细写进证据表。可判定决策点为 0 时本步不适用，不抽样，原因写入证据表。

**待办**：按全局待办规则更新第 4 项。

### 步骤 5 出报告

先算数再出文：

1. 跑 `python "<skill_dir>/scripts/run.py" stats --evidence .dt-audit/<对象>/evidence.md --out .dt-audit/<对象>/stats.json`。它按 [报告结构](references/报告结构.md) 的指标定义算出全部指标、问题分布与占比、严重度升级，并校验合计与交叉关系。校验不过就修证据表，不要绕过、不要手改数字。
2. 按 [报告模板](references/报告模板.md) 的骨架填充：章节、表头、顺序照模板，不增删；只替换 `{{}}` 与表格行，数字逐项取自 `stats.json`。
3. 写入 `<工作目录>/.dt-audit/<对象>/DT-AUDIT-REPORT.md`；用户指定了路径就写到用户指定的位置。
4. 在对话里贴出结论区（检测对象、问题分布、数据、主要缺口），并给出报告文件的绝对路径；完整报告不重复粘贴。

按问题类型陈列命中数量，类型之间不做加权、不给总分。多个问题同时存在时全部陈列。

**完成标准**：

- `stats.json` 校验通过，报告里的计数与算式来自它，没有手改
- 10 类分布逐类核对过命中数量，A4 在证据不足行单列；没有重复计算
- 升级严重度的类型都写了理由
- 证据完整度低于下限时：1.2 只保留问题分布与证据不足提示，删去一句话判断
- 1.3 同时给出观测率与可拦截率，两者都来自 `stats.json`，不要只写一个、也不要合成
- 零决策点或可判定为 0 时，按 [报告结构](references/报告结构.md) 的 1.2 规则处理，不另立口径
- 三大章齐全，2.1 / 2.2 / 2.3 都是「总评 + 问题清单 + 补测建议」三段，每条问题都能回溯到位置
- 1.4 与 2.3 的条目按影响档排序：安全 / 金额 / 数据写入在前，日志 / 文案在后；影响档只在 1.4 与 2.3 判，不写进证据表
- 章节、表头、顺序与模板一致，3.4 已由静态文件注入，没有残留 `{{}}` 或 HTML 注释
- 报告文件已落盘，对话里贴出了结论区与文件路径

默认写入文件，不等用户要。用户指定路径时以用户为准。

## 中间产物

每一步的产出都写进**工作目录下的 `.dt-audit/<对象>/`** 里的这三个文件，不要另立文件、不要在上下文里攒着：

```
.dt-audit/
└── SR-1234/
    ├── evidence.md          # 唯一分析产物，步骤 1–4 共同写
    ├── stats.json           # 步骤 5 由脚本算出
    └── DT-AUDIT-REPORT.md   # 交付物
```

对象标识的取法：SR 用 `SR-1234`；MR 批次用 `MR-<首个MR编号>-<数量>`；提交批次用 `commit-<首个SHA前7位>-<数量>`；混合批次用 `MIX-<首个标识>-<对象数>`。

### `evidence.md` 的结构

一段概览 + 六张表，段名、表头、列顺序都固定，`stats` 脚本依赖它，不要改名或调序：

| 段 | 表头 | 内容 | 由哪一步写 |
|---|---|---|---|
| `## 变更概览` | 项 ｜ 值 | 对象类型与标识、原始输入、变更单元数、涉及仓、关联能力、三档来源的单元数、变更生产代码行数、生产/纳入/测试文件数、C/C++ 受限文件数；排除项按分类各占一行，键名写 `排除：<分类>`，值写文件数 | 步骤 1 |
| `## 范围` | 路径 ｜ 分类 ｜ 来源档位 ｜ 新增 ｜ 删除 | 只列纳入的文件，一行一个 | 步骤 1 |
| `## 用例清单` | 用例 ｜ 位置 ｜ 变更类型 ｜ 断言数 ｜ B3 | 新增 / 修改 / 既有三类用例；B3 列写「是」或留空 | 步骤 2 写清单，步骤 3 补 B3 |
| `## 断言清单` | 用例 ｜ 断言行号 ｜ 档位 ｜ 绑定决策点 | 只含新增或修改用例内的断言 | 步骤 2 写前两列，步骤 3 补档位与绑定 |
| `## Mock 清单` | 类型 ｜ 位置 ｜ 被替换方法 ｜ 情形类 ｜ 问题类型 | 情形类填 1–7；问题类型填 C2 或留空 | 步骤 2 |
| `## 决策点证据` | 编号 ｜ 位置 ｜ 类型 ｜ 条件摘要 ｜ 来源 ｜ 断言随动 ｜ 触达用例 ｜ 断言证据 ｜ 状态 ｜ 问题类型 ｜ 严重度 ｜ 复核 | 每决策点一行；来源填 新增 / 修改，断言随动只对「修改」填 是 / 否 | 步骤 2 写前五列，步骤 3 补其余（含断言随动），步骤 4 补复核 |
| `## 信号与问题` | 类型 ｜ 位置 ｜ 说明 | A2、A3 两类信号 | 步骤 2 |

写作要求：

- 用 Markdown 表格，表头与列顺序固定；`stats` 靠表头定位，改一个列名就会解析失败。
- 空单元格留空或写 `—`，不要写「无」「N/A」等其他占位。
- 目录不存在时先创建，不要因为缺目录就退回对话输出。
- `stats.json` 与报告对不上时，以 `evidence.md` 为准，改证据表后重跑脚本。
- 同一对象重复运行覆盖同名文件，不新建时间戳副本。
- 报告与证据表都在忽略目录里，要分享或留档时复制到别处。

如果工作目录是代码仓，提醒用户把 `.dt-audit/` 加进忽略清单，不要提交。
