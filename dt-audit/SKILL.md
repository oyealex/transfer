# DT 质量审计

审计一个检测对象的实现代码与 DT 之间的证据关系，回答两个问题：**代码被自己的测试盯住了吗？盯住的是真实实现吗？**

每条结论都要落到一个逻辑点编号和一处位置；证据原文只对命中的问题项要求。

## 输入与检测对象

从用户消息里取检测对象。只有两类：

| 标识形态 | 对象类型 |
|---|---|
| `SR-1234`、`AR-77` 这类编号 | SR / AR |
| 含 `merge_requests` / `pull` / `pulls` 的地址 | MR |

按标识形态判断。识别不出就追问，用户给不出就终止——**不要猜一个编号**。

SR 与 AR 的层级关系由脚本负责解析，Skill 不解释、不校验，只把返回的 MR 清单照收。

**变更单元恒为 MR**，没有提交批次这个概念。每个单元带：仓、首个提交、末提交。所有单元的改动并集就是检查范围。

报告开头必须写明检测对象；对象是 AR 或 MR 时，在 1.1 与偏差声明里写明对象类型，避免被读成 SR 结论。

## 前置条件：改动一律由脚本取

不管输入是 SR/AR 还是 MR，最后都归约成同一份东西：

1. 脚本拿 MR 元数据（`index` 或 `mr`）
2. 脚本取改动（`fetch`），产出 `<out>/manifest.json` 与 `<out>/<mr_id>/*.diff`

**检查以 manifest 与 diff 为主，两种输入没有区别。** 本地代码仓是可选的补充，不是改动内容的来源：

- 本地仓可达 → 允许按需读取仓内文件，补上 diff 里看不到的上下文（调用方、接口定义、既有测试方法体）
- 本地仓不可达 → 只看 diff 与 manifest

`fetch` 失败的 MR 记「无法获取」，不进分母、不计数、也不当作零。全部 MR 都拿不到时终止，不产出质量结论。

不要用「本地能看到」去推翻 diff 记录的改动，也不要把「没取到」当成「没问题」。

**工作目录**指会话当前工作目录；下文所有 `.dt-audit/...` 相对路径都相对它，执行命令前先确认 CWD。

## 边界

审计范围：检测对象中修改的 Java / Python / C / C++ 代码，以及为它们新增或修改的测试。

分析时可以按需读取未被改动的代码——调用方、接口定义、既有测试、构建目标——用作关联依据。它们只提供上下文，不进分母。

审计全程只读源码与 git 历史，不编译、不运行测试。改动内容一律来自 `fetch` 落盘的 manifest 与 diff；本地仓只用来补读上下文。读本地仓只用只读命令：`git show` / `git log` / `git cat-file` / `git remote -v`；不切换分支、不改工作区、不 stash。读文件一律用 `git show <提交>:<路径>` 读 MR 末提交的版本，不读工作区——工作区可能已经切到别的分支。

用例当前是否通过，本 Skill 无法判断：被禁用的能识别出来，跑起来会失败但没被禁用的不能。红色的用例和绿色的用例在证据上一视同仁，报告的限制说明里必须写明这一点。

以下内容不进结论：

- 需求设计阶段的用例覆盖
- 仓库历史 DT 质量
- 提交或评审过程
- DT 规范性（命名、目录、结构）

因此结论只覆盖**实现自证能力**：代码自己引入的分支，有没有被自己的测试盯住。漏实现、设计缺陷不在覆盖范围内，报告的限制说明里必须写明这一点，避免被读成需求质量结论。

断言质量只回答一个问题：**这条分支的产出有没有被断言读到**。不评估断言是否充分——同一分支还有没有别的错法没被覆盖，静态分析判不了，硬判只会制造误报。

## 贯穿全程的三个机制

### 证据来源三档

| 档位 | 条件 | 能读到什么 |
|---|---|---|
| 含本地仓 | `fetch` 成功，且本地仓可达、`git remote -v` 归一化后与 MR 的仓匹配 | manifest + diff，外加仓内任意文件 |
| 仅 diff | `fetch` 成功，但本地仓不可达或 remote 不匹配 | 只有 manifest 与 diff |
| 无法获取 | `fetch` 失败 | 什么都没有，只计未分析 |

档位以 `fetch` 成功为前提：`fetch` 失败一律记「无法获取」，即使本地仓可达。

remote 匹配的归一化规则：去掉 `.git` 后缀，把 `git@host:group/repo` 与 `https://host/group/repo` 都归一成 `host/group/repo`，忽略大小写后与 manifest 里的 `repo` 比较。

**档位只说明能读到多少上下文，不决定能不能判。** 判不了的唯一理由是「这个逻辑点需要的证据不在手上」：

- 一条分支的判断只需要 diff 里那一行条件与产出 → 两档都够，照常判。
- 需要读本 MR 没改、diff 里也没有的代码（既有测试的方法体、调用方、接口契约）→ 只有「含本地仓」能读，「仅 diff」读不到。
- 「仅 diff」读不到时才落「无法判定」，并在复核列写明缺的是哪一项。

每条「无法判定」都必须写清缺失项，不许只写「文件不全」。

### 逻辑点

全流程的原子计量单位。一个逻辑点 = 检测对象引入或修改的一条行为分支，不是文件、不是方法、不是行数。清单、不可解析占位点与语言能力档见 [逻辑点规则](references/逻辑点规则.md)。

### 状态六档

每个逻辑点最终落一个状态，定义只在这里出现一次：

| 状态 | 定义 | 计入断言覆盖率 | 计入有效断言率 |
|---|---|---|---|
| 无测试 | 没有任何用例执行到该分支 | 否 | 否 |
| 已断言 | 有断言读到这条分支的决定性产出项（有效档） | 是 | 是 |
| 断言偏弱 | 有断言读到产出，但只落在非决定性量上 | 是 | 否 |
| 实现被替换 | 覆盖该逻辑点的用例全部走假实现（至少一条；零覆盖落「无测试」），真实代码没有被执行 | 否 | 否 |
| 未断言 | 执行到了，但没有任何断言读到它的产出项 | 否 | 否 |
| 无法判定 | 所需的证据不在手上，或结构不可解析 | 否 | 否 |

「无测试」「实现被替换」「未断言」必须分开：无测试是一个用例都没执行到；实现被替换是跑的是假实现、真实代码没执行；未断言是跑的是真实实现，却没有断言读到它的产出。混在一起会把最该修的问题藏进覆盖率里。

判档按下面的顺序，落档即停：

0. **覆盖**该逻辑点的用例至少有一条，且这些用例全部执行假实现 → **实现被替换**。只要有一条覆盖该逻辑点的用例走真实实现，就对那条用例继续走 2–5 步。**一条覆盖用例都没有时跳过本步**——那不是实现被替换，是没测。
1. 结论依赖**本次拿不到的证据**（本 MR 没改、diff 里也没有，且本地仓也读不到的既有测试、调用方、接口契约），或依赖**没有验证过的运行前提**（测试会话是否初始化、旧 JAR 是否在类路径、环境变量、执行顺序），或结构不可解析、触达无法确认，且它足以改变本逻辑点的结论 → **无法判定**。缺失项写进证据表「复核」列，前缀 `缺失：`（不可解析占位点同样用 `缺失：结构不可解析`），并在「取数备忘」汇总。
2. 没有任何用例执行到该分支 → **无测试**。
3. 该逻辑点被执行过，且至少一条断言读到了它的**决定性产出项** → **已断言**。
4. 没有断言读到决定性产出项，但有断言读到它的产出（只落在长度、类型、非空、裸异常这类非决定性量上，或只确认了「协作发生了」而该分支的产出是参数值）→ **断言偏弱**。
5. 没有任何断言读到它的产出项 → **未断言**。

产出项、决定性、对账三步见 [断言与 Mock 判据](references/断言与Mock判据.md) 的「产出对账」。判档不问「断言够不够强」，只问「产出有没有被读到」。

判档只做一遍，不做重复判定。判档落定的状态由步骤 4 的定点自查回写。

## 开跑之前：建待办

进入步骤 1 之前，先用 `todo_write` 建一份五项待办，与五个步骤一一对应：

1. 确定范围与取数
2. 盘点实现与测试
3. 给每个逻辑点定状态
4. 抽样自查
5. 出报告

清单规则：

- 同一时间只允许一项是 `in_progress`，其余是 `pending`。
- 一项标 `completed` 的条件，是它对应步骤的**完成标准全部满足**，且 `.dt-audit/<对象>/evidence.md` 里对应内容已落盘；不满足就保持 `in_progress`，不要提前标完成。
- 某项跑得久、用户看不出进展时，只改这一项的说明文字（如「步骤 1 确定范围与取数（正在定位本地仓）」），待办列表保持五项不变。
- 中途终止时，把当前项文字改成「已终止：<原因>」，保留后面的项，让用户看到停在哪一步。
- 每完成一项，除了更新待办，用一句话说明本步产出落在 `evidence.md` 的哪一段。
- 每步只更新自己那一项，不要攒到最后一起改。
- 报告写完再标最后一项完成。

环境里没有待办工具时，用一段普通清单在对话里同步进展，规则相同。

## 执行步骤

五个步骤，前三步建立证据，第四步验证证据，第五步出结论。每一步的**分析产出**写进同一个文件 `.dt-audit/<对象>/evidence.md`，不另立中间文件；`_diffs/` 由脚本落盘，`stats.json` 由脚本生成，报告是最终交付物。

### 步骤 1 确定范围与取数

（1）–（4）按顺序做完，再判一次短路，本步才算完成。

**（1）取变更单元**

`<skill_dir>` 指本 SKILL.md 所在目录。

| 对象 | 命令 |
|---|---|
| SR / AR | `python "<skill_dir>/scripts/run.py" index --id <编号> --pretty` |
| MR | `python "<skill_dir>/scripts/run.py" mr --url <地址> --pretty` |

MR 状态处理：

- SR / AR 关联出来的 MR：只保留 `merged`（已合入）与 `opened`（开启中）；`closed`、`locked`、`unknown` 剔除，剔除数量与状态记入「取数备忘」。
- 用户显式给出的 MR 地址：照单全收。`closed` 在「取数备忘」备注「改动可能未合入，证据以其差分内容为准」。

各子命令共用的退出码处理（`scope` / `scan` / `assemble` / `stats` / `render` 只会返回 1 或 64，2 / 3 由三个取数命令产生）：

| 码 | 含义 | 处理 |
|---|---|---|
| 0 | 成功 | 继续 |
| 2 | 对象不存在或地址无法解析 | 终止，不产出质量结论 |
| 3 | 平台不可达 | 终止，不产出质量结论 |
| 1 | 脚本内部异常 | 保留已落盘的部分并记入「取数备忘」；全部失败则终止 |
| 64 | 命令写错 | 改正后重跑 |

**（2）取改动**

- 把全部 MR 地址一次传给 `fetch`，`<out>` 取 `.dt-audit/<对象>/_diffs`：

  ```bash
  python "<skill_dir>/scripts/run.py" fetch --url <地址1> --url <地址2> --out .dt-audit/<对象>/_diffs --pretty
  ```

  MR 数量超过命令行长度上限时，按批调用 `fetch`，每批用不同的 `<out>`，再合并 manifest。

- 读 `<out>/manifest.json`：每个 MR 的文件清单、变更类型、增删行数、二进制与截断标记、`diff_path`、`warnings` 都在这里。**文件清单以它为准**，不要靠列目录反推。diff 的完整路径 = `<out>/<diff_path>`。
- **失败单元**：`warnings` 里列出的、或输入地址里没有出现在 `mrs` 里的 MR，记「无法获取」。
- 变更生产代码量（KLOC）：**在范围收敛之后**再算。只累加分类为生产代码、且语言为 Java / Python 的文件的 `additions`；不含删除行、不含测试文件、不含 C/C++。多个 MR 改动重叠时直接累加，是近似值，只用于陈述与密度，不参与判定。不要自己跑 `git diff --numstat`——两种口径混用会让 KLOC 对不上。
- 先从变更单元按仓去重得到仓集合，再用**一次**批量提问（`ask_user_question`，一次列全）问出每个仓的本地路径，不要一个仓问一次；按上面的归一化规则校验 remote。匹配上记「含本地仓」，匹配不上或用户没有该仓记「仅 diff」。这**不影响改动内容的来源**，只决定能额外读到多少上下文。
- **截断**：`truncated` 为真的文件，其上的逻辑点一律标「无法判定」，复核列写 `缺失：diff 被平台截断`，并在「取数备忘」记文件数。
- **删除 / 重命名**：生产文件删除不产生逻辑点（没有新增侧）；重命名按新增侧判，用 `old_path` 判断是否纯搬移——条件文本未变的不计逻辑点。测试文件删除计入测试退化信号 2。

**（3）范围收敛**

按 [范围规则](references/范围规则.md) 的判定顺序给**每个**变更文件一个分类和一个结论。判不准的一律排除。**纳入的文件逐个落进证据表「范围」段；排除的只在「变更概览」里按分类汇总数量**，不逐个列路径、不逐个写理由。

**脚本**：`python "<skill_dir>/scripts/run.py" scope --manifest .dt-audit/<对象>/_diffs/manifest.json --out .dt-audit/<对象>/scope.json` 按路径与扩展名给出分类、排除计数与体量指标（生产改动行、KLOC、单文件改动行）。内容特征（`@Test`、生成代码文件头）它判不了，判不准的按「其余」排除，由你复核后修正；范围表与概览可用 `assemble --mode init` 从 scope + manifest + index 生成，不要手抄。

**（4）去重**

多个 MR 的改动可能重叠：后一个 MR 常常建立在前一个的分支上，会把前一个的改动一并带进来。**不要重建净差分，也不要逐段 `git blame`**，按身份去重：

1. 本步只对**变更文件与变更片段**去重，不枚举逻辑点——逻辑点的身份去重放到步骤 2 枚举冻结之后做。
2. 同一文件的改动来自多个 MR 时，来源档位取高者（含本地仓 > 仅 diff > 无法获取）。
3. 被后续提交 revert 掉的改动不产生逻辑点。判定方式：含本地仓档在末个 MR 的末提交上确认该条件仍存在（`git show <last_commit>:<path>`）；仅 diff 档无法确认，按证据计入并在「取数备忘」声明。

**（5）短路：没有生产代码变更**

范围表建好后先算**生产改动行**（分类 = 生产代码、语言为 Java / Python 的「新增」+「删除」）。**等于 0 就短路**：这次改动没有动到可审计的生产代码，跳过步骤 2–4，直接进步骤 5，定性记「合格」。

短路时仍要落齐结构：

- 用例 / 断言 / Mock / 逻辑点 / 信号五段写空表（保留表头与分隔行）。
- `取数备忘` 记「无有效生产代码变更（0 行），跳过步骤 2–4」。
- `narrative.json` 的 `偏差声明` 写明跳过步骤 2–4 及原因；三个维度的总评写「无生产代码改动，不评估」；Top3 给空数组。
- 有 C/C++ 受限文件时，报告的 1.2 与 3.1 仍要写出受限文件数，不能写「本次改动未引入行为分支」。
- 待办里的步骤 2–4 直接标完成，说明写「短路跳过」；不要留着 `in_progress`。

**完成标准**，下列内容全部满足，并把结果写入 `evidence.md` 的变更概览、变更单元与范围三段：

- `## 变更概览` 的表已写全，键名逐字使用「中间产物」一节的**精确键名**
- `## 变更单元` 每个 MR 一行，七个字段都填
- 每个变更单元都有唯一来源档位
- 每个变更文件都判过分类与结论，没有「未分类」
- 范围表只列纳入文件，每行有：路径、分类、语言、来源档位、新增、删除、结论
- 排除项在变更概览里按分类给数量，没有逐个列文件
- 变更生产代码行数 = 范围表里「分类=生产代码且语言为 Java/Python」的新增行之和（`stats` 会交叉核对，对不上会给 warning）

**失败处理**：单个单元失败记「无法获取」后继续；没有单元或全部无法获取 → 输出证据缺口提示并终止。

**待办**：按「清单规则」更新第 1 项。

### 步骤 2 盘点实现与测试

两侧同时盘点，缺一侧不算完成。本步**只产清单，不判定**：4 类问题的命中数量、断言的档位都留到步骤 3 绑定后再定，本步对断言只记行号与原文。分片时枚举片也只产清单，状态一律留给步骤 3。

按 manifest 的 `diff_path` 逐个读 diff，不要跳过。**读之前先按「检测对象过大时的处理」判分片**：超过阈值就派发子代理，本步变成派发与收口，主流程不再逐份读 diff。

**实现侧**：按 [逻辑点规则](references/逻辑点规则.md) 的封闭清单抽逻辑点，只算行为分支；C/C++ 不抽逻辑点（见该文件的「与语言能力的对应」）。每个逻辑点给编号、位置（文件 + 行号）、类型、来源（新增 / 修改），条件与分支写进条件摘要；来源为「修改」时把增删的子句一并内联进去。判不出结构的片段按「不可解析的占位点」折算，类型填「不可解析」。

**测试侧**：按 [测试框架识别](references/测试框架识别.md) 识别用例、断言、Mock。只收本对象**新增或修改**用例内的断言进断言清单；既有用例记进用例清单，其断言不进断言清单（但可在步骤 3 用于支撑状态）。用例名用 `<类名>#<方法名>`，同一对象内必须唯一。

盘点时必须单独标出**被测试替换掉的实现**：`@Override` 探针、被 Mock 的静态入口、被桩替换的生产函数、被链接替换的 C/C++ 符号。记住它们替换掉的方法体内有哪些逻辑点。

按 [问题类型](references/问题类型.md) 的测试退化六条信号做**字面扫描**，产出候选：位置、信号类型、引用到的生产符号。「计入 / 提示」留到步骤 3 定——只有基线有防护、改动后没了或弱了的才算计入，新增代码没写测试不算退化。

**脚本**：`scan --manifest .dt-audit/<对象>/_diffs/manifest.json --out .dt-audit/<对象>/signals.json` 扫出四条字面信号的候选（新增禁用、断言被注释、断言弱化疑似、测试文件删除）；枚举完成后用 `assemble --mode merge --evidence .dt-audit/<对象>/evidence.md --shards <片 JSON…>` 合并分片，去重、编号与「断言随动」都由它算，不要手抄表格。

**完成标准**：

- 每个纳入的 Java / Python 生产文件都产出逻辑点清单（可以为空），或产出「不可解析」占位点；C/C++ 文件只记受限文件，不进逻辑点表
- 用例、断言、Mock 三张清单齐全，被替换实现记在 Mock 清单里
- 用例清单区分新增 / 修改 / 既有，断言清单只含新增或修改用例内的断言
- 测试退化六条信号逐条扫过，候选写入信号与问题表，标出引用到的生产符号
- 逻辑点计数按固定规则一次冻结（见 [逻辑点规则](references/逻辑点规则.md) 的「枚举冻结」与「编号规则」），并按身份（文件路径 + 条件文本 + 改动后行号）去重，后续只引用编号，不重新计数
- 分片运行时：各片通过校验，或未通过的片已由主流程补读并在证据表标注；每个纳入的生产文件都至少被一片覆盖
- 已写入 `evidence.md` 的对应段

**仅 diff 档的豁免**：既有用例清单写空表，并在证据表「取数备忘」记「既有用例清单无法获取」；Mock 清单只列 diff 里可见的替换，未改动测试文件里的替换在「取数备忘」记「无法排除」。缺失项只在**足以改变本点结论**时按判档第 1 步落「无法判定」；本 MR 新增或修改的用例已经覆盖并读到产出的点，照常判档，不因既有用例清单缺失降档。

### 步骤 3 给每个逻辑点定状态

关联与裁定连着做，只做一遍。**先定谁判**：合并编号后逻辑点 > 50 个时，裁定按批派给**裁定片**（每 50 点一批，末批可少于 50 点），主流程只做关联、编号、打包与收口；≤ 50 个时主流程自己判。裁定片的输入输出契约见 [分片协议](references/分片协议.md)。

**（1）关联**

给每个逻辑点标一个关联结论，只有两种：

| 结论 | 含义 |
|---|---|
| 有 | 用例明确调用或经过该逻辑点 |
| 无 | 确证用例与该逻辑点无关，或确认没有任何用例会执行到它 |

「确认不了」**不要**归进这两种。跨仓不可见、动态派发无法排除、仅 diff 档看不到既有测试——这些直接按判档第 1 步落「无法判定」。

关联能力三档：

| 能力 | 条件 | 粒度 |
|---|---|---|
| 索引级 | 仓有 `.codegraph/` 索引 | 符号级 + 调用边 |
| 静态级 | 仓可达、无索引 | 静态启发式 + 语义推断 |
| 文件级 | 只有文件级信息可用 | 文件级 |

索引级用 `codegraph_explore(projectPath=<仓根>)` 查调用边；环境里没有该工具时降到静态级，不要因为查不到就判「无」。

C/C++ 不枚举逻辑点，关联也只到文件级。

关联时先标记被替换：如果该逻辑点所在方法被测试替换掉了，在「被替换方法」列记方法名、「断言证据」列记替换者位置，到裁定环节按判档第 0 步判——**只有全部覆盖用例都走假实现才落「实现被替换」**，不是「直接落」。**只有让用例拦不住缺陷的 mock 才计数**：被替换的方法体内含本对象的逻辑点、且覆盖它的用例全走假实现 → 测试对象偏移（实现被替换）；mock 的是外部还是内部依赖本身不是判据。

**（2）裁定**

判据见 [断言与 Mock 判据](references/断言与Mock判据.md)。断言的档位在这一步、**绑定到具体逻辑点的具体分支时**判一次，不做全文通档。由主流程判，或由裁定片按批判——裁定片只判状态、证据与 `只验交互`；触达、编号、被替换标记由主流程在派发前定好，随批次交给它。

对每个（逻辑点，触达用例）答三个问题——第 1 问由主流程在关联时答完，裁定片只答后两问：

1. 该用例是否真的执行了这条分支？
2. 这条分支的决定性产出项是哪几项？（只看分支代码）
3. 断言读到的是哪一项？（只看断言）

落六种状态之一：无测试、已断言、断言偏弱、实现被替换、未断言、无法判定。

一个逻辑点被多条用例覆盖时，只在**走真实实现的覆盖用例**之间取**断言最强**的那条定状态（已断言 > 断言偏弱 > 未断言）；走假实现的用例不参与定状态，只作为 2.2 的证据。

**（3）落表**

每个逻辑点在证据表里一行，带编号、位置、类型、条件摘要、来源、断言随动、触达用例、断言证据、被替换方法、状态、问题类型、复核。证据按状态给，不是所有状态都有断言可引：

| 状态 | 断言证据 | 被替换方法 |
|---|---|---|
| 已断言 / 断言偏弱 | 用例方法名 + 断言行号 + 读到的产出项 | — |
| 未断言 | 用例方法名 + 「无断言」 | — |
| 无测试 | 检索范围与结论（查了哪些测试文件、为何没有执行） | — |
| 实现被替换 | 替换者位置 | 被替换的方法名 |
| 无法判定 | — | — |

关联结论不单独占列：**「触达用例」为空即关联结论为「无」**，无法判定的同样留空，由「状态」列区分。

「问题类型」一列由状态推得，只填三种：场景覆盖不足（无测试 / 未断言）、测试对象偏移（实现被替换）、证据缺口（无法判定）。已断言与断言偏弱留空。这一列只用于让脚本校验状态与类型的对应关系；断言质量低由用例清单承载、测试退化由信号与问题表承载，报告仍按 4 类统计。

**「复核」列用固定前缀**，多个前缀用 `；` 连接：

- `随动：` 断言随动为「否」时的理由
- `缺失：` 无法判定的缺失项
- `自查：` 步骤 4 的自查结论

**来源为「修改」的逻辑点必须填「断言随动」**：覆盖它的断言行也在本次变更行里 → 填「是」；断言没动 → 填「否」，并在「复核」列写 `随动：<既有断言凭什么还能拦住改动后的行为>`。写不出的不直接降档，按对账重判：读到的是改动后分支的决定性产出项 → 维持「已断言」，复核列记 `随动：未确认`；读不到 → 按第 4 / 5 步落断言偏弱或未断言。来源为「新增」的留空。

「改了代码、没改断言」是 DT 最常见的失效方式：断言还在验证旧行为，测试恰好绿。这一列就是用来把这种情况逼出来的。

既有测试计入证据：既有断言可以支撑「已断言 / 断言偏弱」，但不进有效断言条数。报告里必须分列「新增 / 修改用例」与「既有用例」。

**（4）信号裁定**

对步骤 2 的每条退化候选，按「三段计入条件」逐条判，在「计入」列写「是」或「否」，在「说明」列写清是缺了哪一段。

- 三段全部成立 → 计入「是」，进 1.2 分布与定性。
- 缺任何一段 → 计入「否」，只作提示，报告 2.1 单列条数。
- **测试脱靶**：本对象有测试变更（新增 + 修改用例 > 0）且全部逻辑点的状态都是「无测试」时，在信号段写一行，类型填「测试脱靶」；否则不写。

**脚本**：裁定片返回后，用 `assemble --mode judge --evidence .dt-audit/<对象>/evidence.md --judges <裁定 JSON…>` 回填状态、断言证据、档位与「只验交互」；问题类型与档位汇总由它统一处理，不要手工拼表。

**完成标准**：

- 每个逻辑点都有触达结论和状态
- 已断言 / 断言偏弱 / 未断言都引用了断言或「无断言」证据；无测试 / 实现被替换 / 无法判定引用了各自的替代证据（检索范围、替换点、缺失前提）
- 每个「已断言」都有逻辑点、用例、断言行三元组，并写清读到的是哪一项产出
- 对条件被修改的逻辑点，已核对被删子句与新增子句的用例（见 [逻辑点规则](references/逻辑点规则.md) 的「条件变化的覆盖要求」）
- 来源为「修改」的逻辑点都填了「断言随动」；填「否」的都在「复核」列写了 `随动：` 理由，写不出的已按对账重判
- 每条退化候选都在「计入」列有「是」或「否」，并写了说明
- 每个逻辑点只有一个状态，同一事实不在两处取值不同
- 逻辑点总数为 0 时本步不适用：不判定，原因写入「取数备忘」
- 裁定片运行时：每批通过校验（或未通过的批已由主流程补判并在「取数备忘」标注），档位已按最高档汇总进断言清单，`只验交互` 已按「任一为是」合并
- 已写入 `evidence.md` 的逻辑点证据段与信号与问题段

### 步骤 4 抽样自查

从逻辑点里定点抽取：**min(3, 可自查项数)** 个「已断言 / 断言偏弱」项，外加**全部证据薄弱项**——即状态为「未断言」的逻辑点。抽样清单可直接取 `stats` 输出里的 `抽样.编号`：步骤 3 收口后先跑一次 `stats`，它算出来的就是这份清单。

只核一件事：**归属对不对**——断定「已断言」时，断言读到的那个值，真的是这条分支产出的吗？

- 对「已断言 / 断言偏弱」项：顺断言表达式往回找数据流，确认它读的标识符或字段来自本分支的产出，而不是同名变量、别的分支的产出、测试里另造的同类型对象。裁定片已给 `归属依据` 的，直接对照它，对不上才回读源码。
- 对「未断言」项：在触达用例里检索这条分支产出的标识符与字段，确认确实没有任何断言读到它；反过来，如果发现其实有断言读到了，就按对账结果改判。

- 归属不符 → 按对账结果改判：读到的是别的分支产出 → 未断言；读到了但只落在非决定性量上 → 断言偏弱；**发现「未断言」项其实被断言读到了，改判已断言或断言偏弱**。改判后同步改「问题类型」列（断言偏弱留空，未断言填场景覆盖不足，已断言清空）。
- 自查结论写进「复核」列，前缀 `自查：`，标明「归属成立」或「归属不符」；不符的写清读到的到底是什么。
- 不构造错误实现，不判断断言够不够强——那是充分性问题，本步不做。取反自检可以顺手做一次，结果只用来复核归属，不改判。
- 不另立产物、不输出比率、不做分层随机、不设种子。

**完成标准**：自查项数 = min(3, 可自查项数) + 全部证据薄弱项，其中可自查项数 = 已断言 + 断言偏弱的数量；每个自查项都有「归属成立」或「归属不符」的结论和理由；改判已回写证据表并同步问题类型；不符明细写进证据表。没有任何可自查项（全部逻辑点都是无测试 / 实现被替换 / 无法判定，且没有未断言项）时本步不适用，不抽样，原因写进「取数备忘」。

**待办**：按「清单规则」更新第 4 项。

### 步骤 5 出报告

先算数，再写判断，最后交给脚本装配。**不要手写 Markdown 骨架**。

1. **算数**：跑 `python "<skill_dir>/scripts/run.py" stats --evidence .dt-audit/<对象>/evidence.md --out .dt-audit/<对象>/stats.json`。它按 [scripts/README](scripts/README.md) 的「报告口径」算出全部指标、问题分布与占比、严重度升级、DT 质量定性，并校验合计与交叉关系。校验不过就修证据表，不要绕过、不要手改数字。

2. **写判断**：读 `stats.json`，把只有人能判的部分写进 `.dt-audit/<对象>/narrative.json`。固定 schema，只写这些字段：

   | 字段 | 内容 |
   |---|---|
   | `偏差声明` | 字符串；默认口径是 SR，对象为 AR / MR 或跳过某步时**必须**写，否则 `null` |
   | `范围一句话` | 首个提交、去重方式、文件数、增删行数 |
   | `一句话判断` | ≤50 字，点出数量最大或最严重的 1–2 类。证据完整度低于下限时这一块由 `render` 自动省略，但仍要写 |
   | `位置摘要` | 对象，键为命中的问题类型，值为「一处代表位置 + 一句话」 |
   | `top3` | 数组，每项 `{位置, 问题, 影响档, 建议}`，≤3 条；有命中时必须给内容，零命中给空数组 |
   | `维度.2.1` | 含 `总评`、`问题`（数组）、`建议`（数组） |
   | `维度.2.2` | 同上 |
   | `维度.2.3` | 含 `总评`、`未覆盖`（数组）、`建议`（数组）；**没有 `问题`** |
   | `3.1` | `{取数, 去重, 额外限制}`；素材取自 `evidence.md` 的「取数备忘」 |

   **二级结构（写错字段名会直接报错，不会静默忽略）**：

   - `问题` 每一项必须写全 8 个字段：`严重度`（只收「严重 / 高」）、`类型`、`子类`、`位置`、`标题`、`现象`、`证据原文`、`后果`。
   - `建议` 每一项是对象 `{位置, 动作}`，两个都不能空；**不要写成字符串数组**。
   - `未覆盖` 每一项写 `{编号, 影响档, 现象, 证据, 后果}`（`证据` 可省）。`位置`、`状态`、`子类` 由脚本按编号回查证据表，不要自己抄；编号必须能在「逻辑点证据」里找到，写的不是「无测试 / 未断言」的编号也会报错——实现被替换的走 2.2。
   - `影响档` 只收「高 / 中 / 低」。

   **报告是唯一交付物**：任何字段都不要引用读者拿不到的内部文件（`evidence.md`、`stats.json`、`manifest.json`、`narrative.json`）、内部目录（`.dt-audit/`、`_diffs/`）、脚本命令或 skill 文档；要指证据时写报告内的章节号（如「见 3.3」）或审计对象自身的文件路径。

   **判断类字段不许留空**：2.1 / 2.2 / 2.3 的总评、Top3、一句话判断都必须给出内容，没有问题的维度也要写一句「未命中」。

   **维度总评与影响档的口径**：

   - 2.1 不判高 / 中 / 低，只陈述断言条数与主要问题。
   - 2.2 用**实现被替换率**判水平，2.3 用**断言覆盖率**判水平；分档阈值取 `stats.json` 的 `水位` 块，不要另记数字。
   - 逻辑点为 0 时三个维度的总评写「无行为分支，不评估」；逻辑点大于 0 但全部无法判定时写「全部无法判定，不评估」。
   - `影响档` 只收高 / 中 / 低，只在 1.3 与 2.3 的条目上判，不写进证据表。判据：**高** = 安全 / 权限 / 鉴权、金额 / 计费 / 配额、数据写入或删除、状态迁移、对外契约；**中** = 业务计算、数据转换、字段默认值、缓存与降级；**低** = 日志、文案、埋点、调试开关、纯展示。

3. **装配**：

   ```bash
   python "<skill_dir>/scripts/run.py" render \
     --stats .dt-audit/<对象>/stats.json \
     --evidence .dt-audit/<对象>/evidence.md \
     --manifest .dt-audit/<对象>/_diffs/manifest.json \
     --narrative .dt-audit/<对象>/narrative.json \
     --out .dt-audit/<对象>/DT-AUDIT-REPORT.md --check
   ```

   模板默认取 `references/报告模板.md`。`--check` 会回读生成的报告，核对：1.2 的定性、三个率、未命中类数、证据缺口行与 3.3 合计行是否与 `stats.json` 一致；3.3 与分布表的行数；1.3 的影响档降序；3.4.1–3.4.7 是否齐全；有无残留占位符与 HTML 注释。**校验不通过就不要交付**——它不会覆盖已有报告，修完重跑；改了证据表要先重跑 `stats`，否则报告会对着旧的 `stats.json` 报数字不符。

4. **终检**（脚本判不了的六条，逐条过一遍）：

   1. 2.2 / 2.3 的总评档位是否与 `stats.json` 的水位一致；2.1 只核断言条数与主要问题，**不判高 / 中 / 低**
   2. 一句话判断是否只点 1–2 类；有命中时与分布表首位一致，零命中时明说未命中
   3. Top3 的影响档排序是否合理（安全 / 金额 / 数据写入在前）
   4. 补测建议与问题清单是否一一对应，有没有凭空建议
   5. 有无自相矛盾：2.2 说无替换而 3.3 有「实现被替换」；总评说覆盖良好而有效断言率 < 50%
   6. 措辞是否越界：不得出现「测试通过」「功能正确」这类本 Skill 无权给出的结论

5. **交付**：在对话里贴出结论区（检测对象、问题分布、数据、主要缺口），并给出报告文件的绝对路径；完整报告不重复粘贴。

按问题类型陈列命中数量，类型之间不做加权、不给总分。多个问题同时存在时全部陈列。

**完成标准**：

- `stats.json` 校验通过；`render --check` 通过；两者都没有被绕过
- 报告里的数字全部来自脚本，没有手改；`narrative.json` 只含判断类字段，没有混进统计数字
- 1.2 第一行的定性取自 `stats.json` 的「定性」，依据写清命中的规则与卡住的条件，没有自拟
- 1.2 的三个率齐全（断言覆盖率 / 有效断言率 / 实现被替换率），都来自 `stats.json`，没有漏项、没有合成
- 三个率与证据完整度同分母（全部逻辑点），因此必然有 `有效断言率 ≤ 断言覆盖率 ≤ 证据完整度`；不成立说明证据表有错
- 4 类分布逐类核对过命中数量，证据缺口在提示行单列；没有重复计算
- 严重度被升级的类型都写了理由；未命中的类型不升级、不写理由
- 1.1 按对象类型二选一：SR / AR 附 MR 清单，MR 不附；两组不同时出现
- 三大章齐全；2.1 / 2.2 是「总评 + 数据块 + 问题清单 + 补测建议」四段，2.3 是「总评 + 数据块 + 未覆盖清单 + 补测建议」四段，每条问题都能回溯到位置
- 1.3 与 2.3 的条目按影响档排序；影响档只在这两处判，不写进证据表
- 3.4.1–3.4.7 齐全，没有残留 `{{}}` 或 HTML 注释
- 3.3 的行数等于全部逻辑点数，合计算式能对上
- 上面「终检」六条逐条过一遍，没有留下矛盾
- 报告文件已落盘，对话里贴出了结论区与文件路径

## 中间产物

手写产物有两个：`evidence.md`（步骤 1–4 的分析与判定）与 `narrative.json`（步骤 5 的判断类文案）。其余由脚本产出：`_diffs/` 来自 `fetch`，`scope.json` 来自 `scope`，`signals.json` 来自 `scan`，`stats.json` 来自 `stats`，报告来自 `render`；分片输入（`shard-*.json` / `judge-*.json`）由子代理产出。全部放在工作目录下的 `.dt-audit/<对象>/`，不要另立文件、不要在上下文里攒着：

```
.dt-audit/
└── SR-1234/
    ├── evidence.md          # 分析产物，步骤 1–4 共同写
    ├── scope.json           # 步骤 1 由 scope 产出（可选，assemble init 读它）
    ├── index.json           # 步骤 1 的 index / mr 输出（可选，assemble init 读它）
    ├── signals.json         # 步骤 2 由 scan 产出（可选）
    ├── shard-*.json         # 枚举片 / 裁定片的输入输出（分片时才有）
    ├── stats.json           # 步骤 5 由 stats 算出
    ├── narrative.json       # 步骤 5 手写，只放判断类文案
    ├── DT-AUDIT-REPORT.md   # 步骤 5 由 render 装配，交付物
```

### `evidence.md` 的结构

一张 `项 ｜ 值` 概览表 + 七张表，共 8 段；另有一个可选的自由文本段 `## 取数备忘`。段名、表头、列顺序都固定，`stats` 脚本依赖它，不要改名或调序。**8 个段即使没有内容，也必须保留表头与分隔行**（写空表），否则脚本报「没有表格」。

| 段 | 表头 | 内容 | 由哪一步写 |
|---|---|---|---|
| `## 变更概览` | 项 ｜ 值 | 见下方键名清单 | 步骤 1 |
| `## 变更单元` | MR 地址 ｜ 标题 ｜ 作者 ｜ 仓 ｜ 来源档位 ｜ 首个提交 ｜ 末提交 | 每个 MR 一行；报告 1.1 的 MR 清单直接取这里 | 步骤 1 |
| `## 范围` | 路径 ｜ 分类 ｜ 语言 ｜ 来源档位 ｜ 新增 ｜ 删除 ｜ 结论 | 只列纳入的文件，一行一个；语言填 Java / Python / C / C++；结论填「纳入」或「无法判定」 | 步骤 1 |
| `## 用例清单` | 用例 ｜ 位置 ｜ 变更类型 ｜ 断言数 ｜ 只验交互 | 新增 / 修改 / 既有三类用例；只验交互只在「断言只落在假实现交互上、而被测分支的产出是本对象算出的值或状态」时写「是」，其余写「否」或留空 | 步骤 2 写清单，步骤 3 补只验交互 |
| `## 断言清单` | 用例 ｜ 断言行号 ｜ 原文 ｜ 档位 ｜ 绑定逻辑点 | 只含新增或修改用例内的断言；档位按产出对账判为有效 / 形状 / 存活，**未绑定任何逻辑点的断言档位留空**；绑定逻辑点可写多个 | 步骤 2 写前三列，步骤 3 补档位与绑定 |

`## 取数备忘` 没有表格，`stats` 不解析、也不要求存在；没有内容时整段省略。但凡是「记入 3.1」的信息，都必须先落到这里——否则跨到步骤 5 就只能靠上下文回忆。

`## 变更概览` 的键名**必须逐字使用**下列字符串，写成别的样子脚本会读成空值：

| 键 | 值 |
|---|---|
| `对象类型` | SR / AR / MR |
| `对象标识` | `SR-1234` / `AR-77` / `MR-1234` |
| `原始输入` | 用户消息里的原文 |
| `变更单元数` | 整数 |
| `涉及仓` | `2 个（a/b、c/d）` |
| `关联能力` | 索引级 / 静态级 / 文件级 |
| `含本地仓单元数` | 整数 |
| `仅 diff 单元数` | 整数 |
| `无法获取单元数` | 整数 |
| `变更生产代码行数` | 整数 |
| `生产文件数` | 整数 |
| `纳入文件数` | 整数 |
| `测试文件数` | 整数 |
| `C/C++ 受限文件数` | 整数 |
| `排除：<分类>` | 文件数；每个分类单独一行 |

写作要求：

- 用 Markdown 表格，表头与列顺序固定；`stats` 靠表头定位，改一个列名就会解析失败。
- 表头与分隔行必须用 **ASCII 的 `|`**。文档里为了排版写的全角 `｜` 只是示意，照抄会导致解析失败。
- **单元格内出现的 `|` 必须写成 `\|`**，条件摘要里的 `a || b` 尤其常见。不转义会把一行拆成多格，报错还指不到原因。
- 空单元格留空或写 `—`，不要写「无」「N/A」等其他占位。列表类条目（如 3.1 的清单）没有内容时写「无」，与表格单元格的规则不同。
- 目录不存在时先创建，不要因为缺目录就退回对话输出。
- `stats.json` 与报告对不上时，以 `evidence.md` 为准，改证据表后重跑脚本。
- 同一对象重复运行覆盖同名文件，不新建时间戳副本。

`.dt-audit/` 应在忽略清单里。若当前目录是代码仓，创建目录后检查 `.gitignore`，没有忽略规则就提醒用户添加，不要提交。

## 检测对象过大时的处理

步骤 2 开始前，用**生产改动行**判分片：范围表里「分类 = 生产代码且语言为 Java / Python」的「新增」+「删除」之和。它和「变更生产代码行数」（只算新增、用于 KLOC）不是一个量，不要混用。

| 生产改动行 | 处理 |
|---|---|
| ≤ 800 | 不分片，主流程逐个读 diff |
| 801–2,000 | 每片 ≤ 500 行，2–4 片 |
| 2,001–5,000 | 每片 ≤ 600 行，4–8 片 |
| > 5,000 | 先按 MR / 仓分组，组内再按上面的档细分 |

两条例外优先于行数：**单文件 > 500 改动行**的独占一片，允许超均值，一个类不拆；**单个测试文件 > 2,000 行**的只读命中变更类或变更方法名的测试方法，不整文件读。

切分单位是**生产文件簇**（同目录或同包），不按 MR、不按行切——按行会把一个方法拆到两片，两片都判不出分支结构。

枚举完之后还有一道分片：**步骤 3 的裁定**按逻辑点数量派给裁定片。

| 合并后的逻辑点 | 裁定 |
|---|---|
| ≤ 50 | 主流程自己判 |
| > 50 | 裁定片，每 50 点一批（末批可少于 50 点） |

裁定片只判状态与证据，分工见步骤 3（2）。

**调度不做规定**：什么时候派、一次派几片、用 `subagent` 逐个派还是用 `workflow` 扇出、要不要分批等待，由运行的 agent 按环境和工具自行决定。本节只约束切片标准与每片的输入输出，不约束并发。

枚举片只做盘点，裁定片只做裁定：编号、合并、落盘、抽样自查都由主流程做；子代理不嵌套，片内不再开子代理。切片规则、两份输出契约与提示词模板见 [分片协议](references/分片协议.md)；分片运行要在「取数备忘」记枚举片数与裁定批数，步骤 5 写进 3.1 的「额外限制」。

分片只降峰值，不降总量。低于阈值不分片，切了反而更贵。
